# 2 · 0号窗纪律

本节收:一个主窗(0 号窗)只派单、验收、跟子代理和设计者沟通,其余的活全交子代理——围绕这件事的纪律,也包括给 0 号窗派单的总监该守的那一半。读法:开 0 号窗、给 0 号窗写任务书、派子代理、收口验收、多窗并行上线之前,读对应条目——2.1~2.3 0 号窗只做什么;2.4~2.6 先对需求、临场拍板;2.7~2.9 给 0 号窗派单(总监那一半);2.10~2.14 子代理怎么派;2.15~2.20 验收与收口;2.21~2.23 并行多窗与权限;2.24~2.26 总监与总编同样不读原料。

### 2.1 0 号窗一行代码不写,亲手只做验收、派单、沟通三件

name: zero-window-no-code-three-duties
type: feedback
description: 开 0 号窗时,或 0 号窗想自己改一处、读一个文件时想起

1. 读码、写码、写测试、跑测试、解冲突、核验、并线、上线、写回报正文、查真源,全派子代理。
2. 0 号窗亲手只剩三件:验收(看结果行、逐名对账、定放不放行)、派单、与子代理和设计者沟通。
3. 窗里只产四样:派遣指令、决策、给子代理的并线上线指令、给设计者的话。
4. 不把原料读进窗:大文件派子代理读回摘要;全量测试、全仓搜索、长日志不在本窗跑;必须亲看的输出先落文件,只看结果行。
5. 设计者临时放宽成「父窗写码」时,照做,但把读写压到最小;窗里文本一大,就主动提议存断点换窗。

**Why:** 自己读码写码,窗就被文件撑满,后面的判断变成回忆而不是读到的事实;子代理带回来的是事实,窗里只存结论。更要紧的是,窗的上下文是设计者和 0 号窗之间的那条线,撑满了他就找不到人——窗干净比做得快重要。只有设计者不再需要随时插话改需求时,这条才可以放松。
**How to apply:** 0 号任务书固定带这一节;验收 0 号窗时除了看活,也看窗里有没有堆着本该交给子代理的东西。做对了的样子:窗里只有指令、决策和对话,找不到成段的代码与日志。
源案例:2026-09-19 某项目设计者定 0 号窗不许自己写代码、核验也交子代理,09-22 又把并线上线划给子代理;09-23 一窗被临时放宽后亲手写了九处改动,写到一半设计者收回:写代码也要交给子代理,否则窗里文本一大就会幻觉,于是立了本条。

### 2.2 0 号窗开工只读任务书,接棒加读交接件,不继承任何长期记忆

name: zero-window-reads-only-taskbook
type: feedback
description: 新开一扇 0 号窗,或 0 号窗收窗时想起

1. 每张单新开一扇 0 号窗;开工只读任务书,接棒时加读交接件,不读之前积下的任何长期记忆。
2. 单里的事写进任务书、进度件、交接件,不写进长期记忆;确有跨单通用的教训,写成一条交给总监落。
3. 收窗时把本窗往记忆目录写过的文件和索引行一并删掉,同一步做。
4. 交接件必须自包含:接棒者不带任何记忆也能开工。

**Why:** 老记忆里全是别的单的细节和已作废的口径,读进来就会拿别人的事当本单的事,这就是项目幻觉。接棒真正需要的只有现状和下一步,交接件足够。同一扇窗连做同一件事、中间口径没变过时,可以不清。
**How to apply:** 任务书第一节写「开工只读本书」;验收收窗报告时,看记忆目录里有没有残留本窗写的文件;四条细则按 规范.md §7.6。
源案例:2026-09-20 某项目员工窗开窗要先读岗位上积下的老记忆,设计者判断员工窗的记忆应该清理,否则会产生项目幻觉,定每张单新开窗、接棒只走交接件,当天把三位共 9 件员工窗记忆(最大一件 42KB)整体移入归档目录(只移不删),于是立了本条。

### 2.3 一个模块的并线、上线、最终验收全归它的 0 号窗,不另设把关岗

name: zero-window-owns-module-to-live
type: feedback
description: 决定一个模块的活由谁合进主干、谁上线、谁验收时想起

1. 0 号窗对一个模块一条龙:派子代理施工、合进主干、上线、最终验收;出了问题,定责在 0 号窗一人。
2. 总监只剩四件:出题、(项目有号段预分时)编号段预分与登记、跨窗不变量归谁、收报告;不逐单放行。
3. 验收权收归 0 号窗后,总监只跑一道事后审计:另起、用顶档模型;审计件首行固定「幻觉 N / 笔误 N / 漏做 N / 未核 N / 环境限制 N」。单子是用户看得见的界面,或审计报了漏做,总监才临时加一次核验。
4. 退回 0 号窗只看功能符不符需求;流程上的小不合规记一行,不退单。
5. 仍要停下问的两类:占用超出预分的编号段、要改别的单名下的文件。

**Why:** 把关在总监那儿排队是真瓶颈;0 号窗本来就是「依赖与合并顺序、整体回归、最终验收」的主人,把活交还给它不是降标准。省下的只是重复的自证,质量靠最终组合树兜住(见 2.16)。单子直接动线上数据又没有回滚时,这条要收紧。
**How to apply:** 任务书写明「本单由 0 号窗自并、自上线、自验收」;总监验收先读审计件首行,再读收口报告。
源案例:2026-09-15 某项目把关环节在总监那儿排队成了瓶颈,设计者当窗定两个模块剩下的窗全由各自 0 号窗并线、上线、验收,当夜两个模块全部上线,于是立了本条。

### 2.4 拍板题攒成一张清单一次问,设计者说开工才建工作树

name: zero-window-one-question-list-first
type: feedback
description: 0 号窗刚拿到任务书、还没建工作树时想起

1. 拿到任务书先通读,把所有拿不准的点攒成一张清单一次问完;设计者说开工,才建工作树。
2. 摆清单时预判他常追问的分支(分几档、要不要、间隔多少),用 A / B / C 一次列全;数值题不问开放式,把既有常量摆出来让他选。
3. 新撞到的拍板题继续攒清单一次问;不依赖它的活先做,不猜着做完再解释,也不停着干等;已有同类授权按宪法闸 3。
4. 沟通由 0 号窗本人做,不派子代理替它和设计者说话。
5. 纯技术取舍(字段形状、事务边界、错误码)自定,写进收尾的「自主假设」;设计者拍板的原话带时刻逐字记进进度件。

6. 设计者亲手激活的窗,仍按「无人在线确认」处理:激活句不等于他正在看;拍板题攒清单一次问,不当场空等,先做不依赖答复的部分。激活动作不能代替具体拍板答复。

- 拦:把亲手激活误认成人正在看或已拍板,当场空等或擅自替答。
- 回口:把待拍题攒清单一次问,继续已授权且不依赖答复的工作;答复原话按工单留痕。
- 拆除:只有对本次待拍问题取得明确答复时解除该问题的等待,亲手激活本身永不替代答复。

**Why:** 0 号窗有并线上线权,方向错了直接错到线上,不是错在一张草稿里;挤牙膏式一条条来回,既耗设计者的时间又撑满窗。任务书已把每个分支写死、设计者明说照书做、不必问时,可以直接开工。
**How to apply:** 0 号任务书里「先对需求」一节放在「建工作树」之前;验收时看进度件里有没有这张清单和他答复的原话。
源案例:2026-09-19 某项目设计者定下遇到问题由 0 号员工直接和他沟通,需求全部沟通完毕后再开工;09-25 总编把「拍板题开工攒一张清单一次问完」写进 0 号任务书通用模板,于是立了本条。

> 2.5(施工中发现文档、代码与设计口径对不上,直接问设计者拍板)已并入第 1 节 1.9,本节不重复。

### 2.6 归别的工位管、但顺手就能改的小项,0 号窗另起支直接改

name: zero-window-handy-fix-on-own-branch
type: feedback
description: 设计者当窗点名一处小改、而它按分工归别的工位时想起

1. 设计者当窗点名的小改,即使归别的工位管,只要「顺手」就直接做:另起一条支(不混进本单主支),派子代理改,随本单并线上线。
2. 「顺手」的边界:一两个文件、常量或形状这一级、不改接口与后台服务、不牵动别的工位在跑的单;超出就另开单。
3. 收口报告单列一节「设计者当窗追加」;进度件记一行知会对方工位,不等回复。

**Why:** 小改转给别的工位要排队,对方可能正满负荷;0 号窗手上子代理现成,当场做完最省。对方正在改同一个文件、或这处改动会影响对方在跑的单时,不算顺手。
**How to apply:** 设计者让顺手改就照做,不再回复这归别的工位管、请总监转告。
源案例:2026-09-23 某项目设计者试用时指出一个界面圈太大要改,0 号窗回复这归另一个工位管、请总监转告,设计者当窗回复只要顺手就直接改、那个工位眼下对接量极大,于是立了本条。

### 2.7 总监对一个模块只出一张需求单,0 号窗自己拆

name: director-one-request-per-module
type: feedback
description: 总监准备给一个模块写任务书、发现自己在逐窗写书时想起

1. 总监对一个模块只写一张给 0 号窗的需求单:要什么效果、硬数值与跨窗不变量、不能碰什么、怎么验收。
2. 0 号窗拿单后自己复核数值、自己写下游窗的任务书、自己开窗;总监给的切窗方案只能标「参考,可推翻」。
3. 定责天然收在 0 号窗一人;下游窗与子代理不做只给把关人看的自证测试。

**Why:** 总监逐窗写详细任务书,写的是自己不执行的细节,还得为每张书定责;员工侧的自证测试只在另有把关人、且他不能自己改代码时才有意义,把关人一撤就是纯损耗。一个模块跨好几扇 0 号窗时,总监仍要另写跨窗不变量。
**How to apply:** 总监发现自己在逐窗写书就停下,改写一张需求单;0 号窗写下游书时按 2.15、2.16 的验证口径。
源案例:2026-09-15 夜某项目设计者当面否掉「下游员工也该跑一遍测试以便分责」的提议;09-16 总监把一个模块切成七张详细任务书、每张 27KB,员工 80% 的额度烧在给已撤掉的把关环节做自证上,设计者点明总监的产出应是给 0 号窗的一张需求单、定责天然收在 0 号窗一人,同日另一张单照此验证:负责人只写 1 张需求单,0 号窗自己派了 6 张子任务、自己开窗、并线上线,全程没有另设验收关,于是立了本条。

### 2.8 0 号任务书引用通用模板,只写本单特有的内容和偏离项

name: zero-taskbook-cites-template
type: feedback
description: 起草一张 0 号任务书、想把上一张书的固定段整段复制过来时想起

1. 任务书开头一行写「本单遵守 0 号任务书通用模板,偏离项见下」,通用段不逐单手抄。
2. 模板管通用段:开工先对需求、子代理规矩、收口格式、产出件数;单子只写本单的目标、判据、不能碰的范围和偏离项。
3. 偏离项逐条列、写明为什么;模板与更高层的裁定冲突时以裁定为准,并写进偏离项。

**Why:** 通用段手抄会越抄越走样,还把本单特有的判据淹掉;读书的窗先要花一大半上下文读通用头。只有一两张单、还没有稳定通用段的新项目,可以先不立模板。
**How to apply:** 起草任务书的子代理只读模板和本单需求;验收任务书时看有没有整段重抄模板。
源案例:2026-09-16 某项目一位 0 号窗实测 182 张任务书,通用头占全文 59%,一半以上的书还在要求新流程下已无人要看的重复自证,09-25 总编落了 0 号任务书通用模板,于是立了本条。

### 2.9 口头授权不等于台面权限:授权与台面标记同一步改

name: verbal-grant-needs-desk-flag
type: feedback
description: 给 0 号窗授全权、或 0 号窗准备在工单台上收口结单时想起

1. 设计者口头授给 0 号窗的全权,不会自动变成工单台上的权限;台面认的仍是登记的位阶。
2. 总监建「0 号自结」的单时,同一步把台面的相应标记置好;流程撤掉把关岗后,台面要有一条 0 号窗一步落终态的收口通道,把关人一栏留空、写明「0 号自并」,不伪造签名。
3. 0 号窗开工时核一次自己的单带没带自结标记,别把「我有权并线」当成台面也认。
4. 撞上了按非业务闸处理:记一行、继续干活,把完整收口命令和事实原文写进进度件请总监代结;别做会让代结失效的操作(比如先把自己的员工号退掉)。
5. 够不到别的工位的对话线时,把裁定全文落在自己的母单上,注明请对方总监据此处理。

**Why:** 口头授权和台面的位阶校验是两套系统,改了一套另一套不会跟着动;0 号窗活全干完了,却卡在账面闸上收不了单。台面已按「0 号自结」建模、授权和标记出自同一处时,这条自然消失。
**How to apply:** 总监的建单清单里加一行「置自结标记」;0 号窗撞上了先记一行不停车,收口报告「需总监动作」里写代结命令原文。
源案例:2026-09-26 某项目一张单的任务书写明由 0 号窗自行结单,建单时台面标记没置,0 号窗上线后结单被拦,员工又不能代署总监名、跨工位留言也被拦,只能请总监代结,于是立了本条。

### 2.10 子代理按活分三档模型,判据是改不改文件、推不推翻结论

name: subagent-model-three-tiers
type: feedback
description: 每次派子代理、要填模型时想起

1. 顶档(不指定,继承父窗):独立审计、核验、解冲突与并线上线、推翻已判过或已上线的结论、多文件语义判断。审计用比施工更强或至少同级的模型,不把具体型号写死在产品规则里。
2. 中档:施工改码、起草任务书与交接件、跨文件但不是审计的复杂活。
3. 低档:扫盘、读文本做总结、抄数定位、格式转换与登记——一切「只产事实不产改动」的活。
4. 判据一句:会不会改文件、要不要推翻别人的结论——都不会就用低档。
5. 只选模型、不动推理档位;0 号窗开工第一句先报本平台子代理可选的模型,等设计者分配,不自定。
6. 子代理回报首行写自己的模型名留证:台面的「实际模型」一栏只记第一次开窗,后来换了不会更新。

- 拦:审计模型弱于施工,复杂判断无人可靠复核,或把会过期的具体型号当作长期规矩。
- 回口:按实际施工模型核相对能力,由有分配权的人选更强或至少同级的审计模型,再独立审计。
- 拆除:不拆;可用型号会变,审计相对施工的能力底线不变。

**Why:** 设计者按量付费;扫盘不需要推理,贵模型想得越多越容易出幻觉;不同平台的子代理机制不同,分配只能由开窗的人给。具体模型名几周就过期,档位不会。平台只剩一个模型可选时,这条退化成只看第 6 点。
**How to apply:** 派之前先判这活属哪档再填模型;评估某一波的质量时,先看回报首行的模型名,别拿台面字段当前提。
源案例:2026-09-22 某项目设计者按量付费,当天两次改子代理的选模口径,晚上定稿三档:扫盘读书一律低档,因为模型思考越多,很多时候反而越快产生幻觉,于是立了本条。

### 2.11 一个子代理只背一件一句话说得清的活,回报定死三行

name: subagent-one-sentence-per-agent
type: feedback
description: 把一张单拆给几个子代理、写子代理提示词时想起

1. 一个子代理只背一件「一句话说得清」的活;说不清,就是没切够。
2. 同一个文件只许一个子代理碰;单内共用的文件逐件点名归某一个子代理。
3. 提示词写死权限边界:只读不改,或只改点名的那几个文件。
4. 回报定死三行:一句结论 / 改了哪些文件 / 一行证据路径;不贴代码、diff、日志(首行另写模型名,见 2.10 第 6 点,不占这三行)。
5. 要细节就再派一个子代理问一个具体问题;子代理之间传路径,不传内容。
6. 执行模型不是顶档时,不是降标准,是切得更碎。

**Why:** 一件活里塞两件事,子代理会拿前一件的上下文猜后一件;两个子代理碰同一文件会互相覆盖;回报一贴代码,原料就又被带回 0 号窗。活本身是不可拆的一次性整体改动(如全仓重命名)时,仍由一个子代理包干,但要写明范围。
**How to apply:** 派单前把每个子代理的活写成一句话,写不成就再切;收到回报只取模型名和那三行,其余不读。
源案例:2026-09-19 某项目给 0 号窗配了非顶档的执行模型,设计者要求把活往上多拆分一些,即模型弱就把活切碎而不降标准,同日把子代理回报定成三行,于是立了本条。

### 2.12 调研另派只读扫盘子代理落 md,写码子代理只读那份 md

name: subagent-scan-separate-from-build
type: feedback
description: 派写码子代理前,发现还要先搜文档、查现状时想起

1. 搜文档、查现状、核既有逻辑这类调研,另派一个只读的扫盘子代理(低档),结论落成 md 文件。
2. 写码子代理只读那份 md 的相关节,不自己扫全仓;它的任务书里写「结论见 <md 路径>」。
3. 当窗追加的核实题也转给扫盘子代理,不塞给写码子代理。

**Why:** 写码子代理的上下文被调研塞满就会写错,和收口幻觉是同一个病根;扫盘不需要推理,低档更省也更少自由发挥。调研只有一两行、写码子代理顺手一查即得时,不必另起。
**How to apply:** 派施工前先把活拆成「调研项」与「施工项」:调研项交低档落 md,施工项交中档并附 md 路径。
源案例:2026-09-25 某项目设计者对 0 号窗指出,搜文档时可以另派一个子代理,因为写代码时要保持上下文干净才不会写错,于是立了本条。

> 2.13(子代理的底数一律对远端主干的指定提交量,不读本机共用检出)已并入第 3 节 3.1,本节不重复。

### 2.14 派子代理写死:只收拾自己起的进程,不按名字批量杀

name: subagent-kill-own-pid-only
type: feedback
description: 派会起进程、会做收尾清理的子代理时想起

1. 派子代理的指令里写死一句:禁止按进程名批量杀进程(如 `taskkill /F /IM <名>`、`pkill <名>`、`killall`);只许按自己启动的那个 PID 杀。
2. 清理放在 finally 里;自己起的临时库、临时服务、工作树自己收;杀不掉就照实报,不扩大打击面。
3. 子代理的临时文件只写临时目录,不写进仓内。
4. 收窗前扫一遍孤儿进程(启动时间异常久、命令行是本单起的),按具体 PID 停。
5. 出了误伤先核影响面,同轮告诉所有在跑的窗;账记在派单方,不记执行方。

**Why:** 子代理拿的是「自己起的进程要收干净」这个正确动机,而按名字杀最顺手——它不知道同一台机器上还跑着十几个别的窗。后果是静默的:被杀的窗只看到某趟构建或测试莫名中断,容易当成偶发红去查,甚至据此给代码定性。确定整台机器只有本窗一个会话时,风险才消失。
**How to apply:** 把这句放进每个子代理的固定提示;收窗报告里写「已扫孤儿进程 N 个」。
源案例:2026-09-20 某项目一个只读勘查子代理收尾时按进程名批量杀,误杀了 3 个属于别的窗的进程(本机当时同名进程 12 个);次日另一子代理留下的外壳卡在读管道上空跑了近 4 小时,是设计者发来画面追问才发现,于是立了本条。

### 2.15 施工子代理只构建、不跑测试

name: builders-build-no-tests
type: feedback
description: 给施工子代理写判据、想让它顺手把测试也跑一遍时想起

1. 施工子代理的书里只写「全量构建零警告零错误,贴最后两行」;测试一次都不跑。
2. 不另派子代理去启动应用看效果;要看效果,上线后设计者自己开。
3. 全套测试只在 0 号窗收口的最终组合树上跑一次(见 2.16)。

**Why:** 每个子代理跑一遍测试要一两分钟、几万 token,十几路叠起来是纯烧钱;而「屏上像不像稿子」这类判据,测试一条都判不了。测试又快又便宜、或单子本身就是修测试时,不适用。
**How to apply:** 施工书的判据只写「构建通过」一行;看到施工子代理在跑测试就叫停。
源案例:2026-09-19 某项目施工子代理每个都跑一遍测试(每趟约 1.5 分钟、几万 token,一批十几路),设计者叫停,理由是他的 token 额度虽然还剩 70%,也经不起大量的测试行为;当晚另几张单里只为自证而设的验证子代理工位也全部删掉,于是立了本条。

### 2.16 0 号窗收口的最终组合树,构建加全套测试一步不少

name: final-tree-full-suite-once
type: feedback
description: 0 号窗收口、几条支各自都绿、准备合进主干时想起

1. 省掉的只是各子代理重复的自证,不是质量;分批各自全绿,不等于合起来绿。
2. 收口时派子代理建最终组合树:把全部支重新合一遍(不是快进)、全量构建、跑全套测试,两棵树的用例清单求差集逐名对账。
3. 任务书写死三条:重并重跑,不快进;结构化文件的冲突不许取行并集;先全量构建(含所有工程)再跑全套测试。
4. 改了行为又顺手改了钉旧行为的断言,机器闸会全绿而判断是错的——这类改动回真源核。

**Why:** 有几类问题只在「把两个都绿的支合起来重跑」时才看得见,交板方自己再仔细也发现不了。整单只有一条支、且合进去之前主干没动过时,组合树就是那条支本身。
**How to apply:** 收口报告的结论行写「最终组合树:构建通过 / 全套 X 条 / 新增红 0」;缺这一行不放行。
源案例:2026-09-16 某项目同批几条支各自全绿,最终组合树没跑全套就上线,随后两个仓的主干红了 26 条,于是立了本条。

### 2.17 子代理的回报是线索不是证据,有意选择不做的答案要单拎出来裁

name: subagent-report-is-not-proof
type: feedback
description: 收到子代理说做完了、可以合并的回报,准备放行时想起

1. 子代理(包括施工方)自述做完了、可以合并,一律不采信,看结果行、证据路径和实物。
2. 要核就另起一个干净的核验子代理:只给「支名 + 要证的事」,不复用施工子代理的上下文,不拿施工方的结论当输入——谁执行谁不核。
3. 回报里凡是「有意选择/不做/拒绝」的答案,是设计决定不是自述,单拎出来逐条裁;拿不准就问设计者。

**Why:** 自述是执行方对自己的总结,错的时候和对的时候长得一样;有意不做的答案夹在一堆已完成里最容易被顺手放过。回报本身就是机器打出的结果行时,那一行可以直接采信。
**How to apply:** 收回报先找证据路径,再读结论;把回报里「不能」「不做」「有意」一类字样单列出来。
源案例:2026-09-05 某项目任务书问升级数据快照格式后老数据还读不读得回来,执行方明确答复读不回来、属有意选择,验收方没把这个答复当拍板项裁,放行后一上线就崩,于是立了本条。

### 2.18 收口是幻觉高发区:交接件由子代理起草,0 号窗只核事实

name: wrapup-handoff-drafted-by-subagent
type: feedback
description: 0 号窗收口、准备写交接件或收窗报告时想起

1. 收口是上下文最容易爆的一步:要读全部分报告、大对账表、进度件;爆了之后写的交接件会把下一棒整个带偏。
2. 交接件由子代理起草,0 号窗只核事实:哈希用 git 核、数字用命令核、文件名用 ls 核。
3. 交接件按体积写明「谁读」:>50KB 的一律只准子代理读,0 号窗只读它的结论段。
4. 交接件落本单任务书目录下,用本窗口吻,不写进总监的根目录;提交用本窗自己的署名。
5. 一窗做不完就分波,别让一窗一口气把整批做完。
6. 总监收到收窗报告,先派只读子代理核 git、台面、交付物三面,再决定要不要重整交接件;总监自己不读码。

**Why:** 施工子代理各自上下文小,代码是对的;0 号窗在收口时一口气读几百 KB,判断变成回忆,错全出在它亲手写的最后那份交接件上。单子小到收口只需读几 KB 时,可以由 0 号窗自己写。
**How to apply:** 0 号任务书的收口节写死「交接件子代理起草、本窗只核」;验收先核交接件里的哈希、数字、文件名,再核活;谁起草、谁核、核对记录怎么贴按 规范.md §7.2,收口报告四块按 §7.7。
源案例:2026-09-20 某项目一扇 0 号窗收口时读 410KB 对账表加 72KB 进度件,把窗撑到约 700K,交接件错了一串(文件名少字、写到不存在的字段、漏报生产改动、写进总监根目录、署名挂到别处),而两路只读子代理核代码面全部成立,于是立了本条。

### 2.19 收口报告限字限件,收尾只留三问

name: wrapup-report-four-blocks
type: feedback
description: 0 号窗写收口报告、或总监给任务书定收口格式时想起

1. 收口报告 ≤6,000 字,只四块:结论一行(上没上线、部署提交号、新增红几条)/ 事实段 ≤600 字 / 需总监动作 3~5 条 / 收尾三问。
2. 收尾三问:怎么打开它 / 最没把握的一处 / 自主假设。
3. 每单产出 ≤4 件:进度件 + 收口报告 + 审计件 + 可选 1 件(交接件或决策补登);各路分报告并进进度件,不单独成文件。
4. 同一批数只在一处写全,别处引用。

**Why:** 专给把关人看的收尾题撤掉后,长报告只剩重复:同一批数在收口报告、审计件、决策草稿里各抄一遍,读的人反而找不到结论。单子本身就是写文档的活、报告就是交付物时,不受字数限制。
**How to apply:** 任务书收口节照这四块给骨架;总监验收先看结论行,超字数退回重写。
源案例:2026-09-25 某项目流程扫盘发现一份收口报告 57,614 字、13 节,与审计件、决策草稿三处重复,同一工位不同单的产出从 2 件到 9 件,差 4 倍以上,于是立了本条。

### 2.20 核 0 号窗自并的活进没进主干,只认祖先关系

name: self-merge-check-by-ancestry
type: feedback
description: 要判断某张 0 号自并的单到底进没进主干时想起

1. 0 号窗自己并自己推(快进或直推),不产生 merge 提交;在主干历史里搜「merge(单号」零命中,不代表没并。
2. 判据只认祖先关系:`git merge-base --is-ancestor <提交号> <远端>/main`。
3. 搜关键符号只当「码真在里面」的旁证。
4. 流程一改(谁并、怎么并),各处任务书和章程里的旧判据同一步改掉。

**Why:** 旧判据的前提是有专人并线、并线会打 merge 提交,前提没了判据还在,照它判会得出相反结论,而且有命令有输出,看起来很实。项目改回只许 merge 提交进主干时,旧判据才重新成立。
**How to apply:** 任务书列判据时写死「以祖先关系为准」,否则执行方会按第一条停车。
源案例:2026-09-20 某项目一张 0 号自并的单收口在案、主干头就是它的提交,按旧口径搜 merge 提交却零命中,照判会判成没并,于是立了本条。

### 2.21 接手前先看远端有没有支;疑似两扇窗在做同一件事,立刻停下问

name: takeover-check-remote-branches
type: feedback
description: 接手一个模块的收口、或准备写「请开这些窗」的清单时想起

1. 接手任何模块级收口之前,先看远端有没有该模块前缀的支(如 `git ls-remote <远端> | grep <前缀>`),再信台面状态:支在,就是有窗在跑,不管台面写什么。
2. 发现疑似另一扇 0 号窗在做同一件事,立刻停下问设计者定属主,别两边都往主干写。
3. 不同平台的窗之间可能有你看不到的消息网;台面安静不代表没人在干。

**Why:** 台面状态是人记的,远端的支是真的;两扇 0 号窗互不知道时,一边写的清单全是白写,两边都往主干写会互相覆盖。所有窗在同一个消息网里、台面由机器自动同步时,风险才小。
**How to apply:** 接手第一步跑一次远端支列表;写任何「请开这些窗」之前,先核这些支在不在。
源案例:2026-09-15 某项目一个模块其实已有另一平台的 0 号窗在指挥,本窗只看台面写了一整份「请你开这8个窗」的清单,实际 8 条支早已推上远端,全是白写,设计者当场裁定收口归那扇窗、本窗停手,于是立了本条。

### 2.22 并行的 0 号窗直接用跨会话消息对上线先后与交集

name: parallel-zero-windows-direct-message
type: feedback
description: 同期有几张 0 号单并行、要上线或可能改到同一批文件时想起

1. 几张 0 号单并行时,用平台自带的跨会话消息直接互报,不走台面转述:同文件交集、部署提交号全号、谁先上线、停机窗口预告、上线后须知。
2. 开工核完同期单的交集就发一轮;撞冲突先商定「这块归哪个窗解」,只由一扇窗解。
3. 停机改库前预告窗口,等对方回复再动。
4. 发出去的命令、路径,先自己核一遍再发。

发送与送达细节见[宪法闸 34](../../宪法.md)。

**Why:** 台面留言要经总监转述,慢且会失真;跨会话直发当轮就回。平台没有跨会话消息、或设计者没授权窗之间直接沟通时,只能走台面。
**How to apply:** 开工第一轮就列出同期会话、发交集;上线前发一次部署提交号与后并须知。
源案例:2026-09-24 至 09-25 某项目五扇 0 号窗并行,直接互发消息提前撞出同一行常量互斥、整份重写存储文档会抹掉别单新字段、后上者拷旧部署脚本会把数据刷回三处冲突,五窗零冲突上线,设计者随后授权并线上线有冲突时窗口之间直接沟通,把冲突部分交给一个窗口处理即可,于是立了本条。

### 2.23 auto 模式会拦子代理推主干和上线,父窗的授权传不到子代理

name: auto-mode-subagent-deploy-blocked
type: feedback
description: 0 号窗开工报模型分配时,或子代理推主干、上线被拦时想起

1. auto 模式下,子代理推远端主干、停机改库、上线,都会被分类器当成生产部署拦下;设计者在父窗点的「授权继续」传不到子代理,分类器只看子代理自己的上下文。
2. auto 下连父窗自己推主干也会被拦;往本地设置里加放行规则同样被拦(算自我修改),只能设计者手动改,或切到 Bypass。
3. 切 Bypass 之前起的子代理,续派后仍停在 auto,照样被拦;要新起一个执行子代理。
4. 被拦时子代理不许换写法绕,也不许回报「请父窗亲自执行」转手绕权限;原样回报拦截原话,由设计者定。
5. 0 号窗开工报模型分配时顺带报权限模式;是 auto 就预告设计者:推主干、上线那一步子代理会被拦,需要切 Bypass 或他本人放行。

**Why:** 0 号模式下并线上线全交子代理,auto 会卡在最后一步;来回问既浪费停机窗口,又让设计者困惑为什么不是一直有权限。平台改成父窗授权能传给子代理时,这条作废。
**How to apply:** 开工第一句报模型与权限模式;推主干之前确认已是 Bypass,且执行子代理是切换之后新起的。
源案例:2026-09-23 某项目一次并线,子代理推主干两次被拒,设计者在父窗点了授权后仍拒,切 Bypass 才推成;09-25 再撞,切换之前起的子代理续派后停机改库仍被拦,新起一个才通,于是立了本条。

### 2.24 总监窗也不读原料:代码和大于 2KB 的清单一律派出去

name: director-reads-nothing-raw
type: feedback
description: 总监或总编想亲手 cat、sed -n 一个文件、一张清单或一棵目录时想起

1. 总监、总编窗同样不读代码:要知道某段逻辑,派子代理问一个具体问题,回一句结论 + 文件:行 + 一行证据命令。
2. 不只代码:任何 >2KB 的盘点、对表、目录扫描、大清单,一律派子代理落 md,本窗只读回报的几行。
3. 并线、推送、部署、构建也派子代理;本窗亲手只做台面记账、裁定、改自己的章程与任务书。
4. 想 cat 或 sed -n 之前先问一句:这是要我做决策,还是要我盘底数?盘底数就派出去。

**Why:** 上级窗读进半截原料有两个坏处:判断被最后读到的那段带偏;上下文本该记「谁在做什么、哪件归谁、哪条口径作废了」,装了文件就装不下台面。一条被细节带偏的裁定,会同时污染好几张在跑的单。上级窗亲自下场当施工窗时,它就是 0 号窗,按 2.1 办。
**How to apply:** 总监窗的产出只有派单、裁定、记账、收窗断点四样;验收总监窗时,看它有没有成段读原料。
源案例:2026-09-22 某项目一位总监为起草一张单,亲自 sed -n 读了 15KB 的完成计划清单和几个根目录,被设计者当场批评应该用子代理盘点、别亲自动手浪费上下文,而三天前设计者已定总监读码也必须派子代理,于是立了本条。

### 2.25 写进任务书的底数要当场核,附证据行

name: taskbook-facts-freshly-measured
type: feedback
description: 总监或 0 号窗在任务书里写底数,或换窗交接后旧窗被问状态时想起

1. 对系统现状的任何结论(某功能不支持、某开关未落、某件要等别人并线)都有保质期;实现每天在变。
2. 接管件的「现状」段是上一窗收窗那一刻的快照,读起来像刚核过,其实会过期。
3. 任务书里凡点名一个开关、字段、常量、路径、并线次序或前置依赖,必须附当场对远端主干核出的那一行(派子代理核);贴不出来就不写。
4. 锚点写文本不写行号;任务书写明底数是实测的、可引用,但接单方必须自核。
5. 员工拿现行代码顶回上级的底数,记功不记越界。

6. 换窗交接后,旧窗答状态前先用 git 核当前仓事实,再读本单最新进度件,核对下一窗之后发生的变化;不能凭旧窗记忆或接管时快照回答。核不到就报尚未核实,不报已完成或未完成。

- 拦:旧窗沿用过期记忆,把下一窗已经完成的说成没做或把未完成说成完成。
- 回口:先 git 核仓与读最新进度件,对不上就核差异,按本次证据答状态。
- 拆除:只有仓与进度均冻结且能证明交接后无变化时可免重复核查;恢复变化即恢复核查。

**Why:** 总监不写代码,对系统的认识全靠某一次调查的快照,而别的窗每天在改;拿快照当现状,既会错判员工,也会让任务书建在不存在的前提上。代码冻结、无人推送的时期,快照才等于现状。
**How to apply:** 接管后第 0 步,把接管件里每一条等别人并线、某某不支持之类的说法派子代理核一遍,就地改成实测结论,再派单;旧窗被问状态同样先按第 6 点核实。
源案例:2026-09-05 某项目总监照接管件的「现状」段写单,那块当天其实已经并线,整张单作废重发;同日另一条「服务端不支持 X」的结论两天后被员工拿现行代码顶回,于是立了本条。

### 2.26 要长期和设计者对需求的窗,重活开 0 号窗去做

name: designer-channel-window-spawns-zero
type: feedback
description: 一扇正在和设计者反复对需求的窗,撞上核验、并线、上线这类重活时想起

1. 需要持续和设计者核需求的窗,核验、并线、上线这类吃额度的重活不在本窗做,也不在本窗大批派子代理,改开一扇 0 号窗去做。
2. 本窗只出题、收报告、与设计者核需求;只读的小探活子代理可以派,报告要短。
3. 开 0 号窗时附一句给设计者的激活句。

**Why:** 本窗的上下文是设计者核需求的通道;核验、并线、上线要解冲突、构建、回读,吃额度大,放进 0 号窗定责也清楚。这是「代码类事都交子代理」再进一步:连子代理也不在本窗大批派。需求已经稳定、设计者不再频繁来回时,可以放回本窗派子代理做。
**How to apply:** 撞到重活先问一句「这要不要开一扇 0 号窗」;本窗的文本量留着对需求。
源案例:2026-09-21 某项目负责客户端打包的工位窗正和设计者反复对需求,设计者定后续核验、上线一律开 0 号员工窗去做,本窗不自己操作、文本量留着和他核对需求,于是立了本条。
