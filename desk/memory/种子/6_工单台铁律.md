# 6 · 工单台铁律

本节收:多窗、多子代理共用一张工单台时,怎么扫收件、往台面上写、推单子走状态、交板,以及台面上的闸、拒绝提示和验收判据怎样才不骗人——换一张工单台、换一个项目仍然成立的那部分。读法:开窗扫收件、往台面上写东西、交板收口之前读第一、二组;给台面加闸、写拒绝提示之前读第三组;给任务书定验收判据,或拿着「全绿」「别人说」准备下结论之前读第四、五组。

## 一 · 读写台面

### 6.1 扫自己的单不能只筛「在办」,「待答」也要算进去;开窗、收尾前、被唤醒后各扫一次

name: desk-scan-includes-awaiting-reply
type: feedback
description: 开窗第一步看自己名下有什么单、收尾前准备说「都处理完了」、或被一条新消息唤醒时想起

台面默认的「在办」列表不含「别人已经回复、在等你看」这一维;只筛在办,对方答复过的单会一直躺着没人看。
1. 筛自己的单时,状态里显式加上「待答」这一类,不信默认筛选。
2. 至少扫三次:开窗第一步;收尾说「都处理完了」之前;被新消息唤醒、准备接着干或收窗之前。
3. 扫到的待答单当轮处理,或至少回一句,不攒。

**Why:** 台面列表是某一刻的快照,开窗扫过不代表收尾时仍是那样;回复进来不会自动把单推回「在办」,只扫在办就等于看不见回复,对方只好再催,设计者尤其不愿同一件事被问两遍。台面能把「有新回复」主动推到眼前时,这条可放松。
**How to apply:** 开窗清单第一步写「扫在办加待答」,收尾报告前再扫一次;判做对了:收窗时自己名下没有一张「对方已回、你没看」的单。
源案例:2026-09-06 某项目一个工位筛自己的单只列了新建、已认领、返工等几种状态,漏了「待答」,别人已答复的单一直没人看,对方只好重复催办,于是立了本条。

### 6.2 往台面写之前先确认落点:写入报成功不说明落在了哪

name: desk-write-check-landing-spot
type: feedback
description: 在新环境里第一次操作工单台、设指向台面的环境变量、第一次用某条发单或提问命令时想起

工单台的写操作可能「成功」地落在你没想到的地方,不报错:
1. 指向台面的环境变量名差一个字,工具不报错,而是静默退回一份只读快照,之后每次写入都显示成功、其实都没进台面。
2. 提问、留言类命令里表示收件方的参数,若填成自己的位,单就躺在自己台面上,对方永远收不到;有的命令没有字面上叫「发给谁」的参数,收件方藏在别的参数名里。
3. 变量名、参数名从帮助或权威文档复制,不凭记忆敲;第一次用某条命令,先发一条无关紧要的试探,再按单号回读,看它落在谁的台面上。

**Why:** 写入命令的返回只说明「写了」,不说明「写到了哪」;落错和落对返回一模一样,等对方说没收到时已过去很久。工具遇到未知变量名、发给自己时能直接报错,这条可放松。
**How to apply:** 新环境里第一次写台面,写完立刻按单号回读状态和收件方;判做对了:能在对方台面上指出那一行。
源案例:2026-09-07 某项目一个工位做实测时,把指向沙箱台面的环境变量写成了另一个名字,工具不报错,测试用的假单静默写进了本应只读的快照,于是立了本条。

### 6.3 命令报「参数不对」有两个相反的方向:先用一次计数定方向,再选补救

name: desk-param-error-two-directions
type: feedback
description: 工单台命令报「参数不对」「没有这个选项」,或别人说新命令已上线、你这里却用不了时想起

同一句「参数不对」可能来自两种相反的版本不一致,补救也相反:
1. 服务器落后本机:本机代码里已经有这个参数,服务器上还是旧版;要等它上线,或先不用新参数。
2. 本机落后服务器:功能已经上线,却还没并进主干,本机按主干检出的那份代码里根本没有它;这时拉主干治不了。
3. 定方向的判据:在本机主干检出的工具代码里数一下这个命令或参数名出现几次,为 0 就是第 2 种。
4. 上线后不要写「已生效,可以用了」,先在一份普通检出里真跑一次再说。

**Why:** 两个方向的报错字面一样,用错补救不但治不好,还会让人以为「已经治过了」。报错能直接写出双方版本号时,这条可放松。
**How to apply:** 撞到这类报错,第一步只做定方向的那次计数;判做对了:补救之后同一条命令真的跑通。
源案例:2026-09-16 某项目三个刚上线的工单台命令和参数在本机报「参数不对」,在主干检出的工具代码里一数全是 0 次:功能已上线、还没并进主干,拉最新代码治不了,于是立了本条。

### 6.4 记时间、比先后,一律抄台面回执里的时间戳,不用本机时钟

name: desk-timestamp-from-receipt
type: feedback
description: 往正式记录里写时刻、判断台面上两件事谁先谁后、或觉得「台面时间不对」时想起

本机与台面可能不在一个时区:本机 -0700、台面 +08:00 时,本机下午 1 点是台面次日凌晨 4 点。写进正式记录的时刻、判断先后,一律取台面回执或接口返回里的权威时间戳;没拿到戳就不写时刻,不拿本机时钟估。

**Why:** 时区差能把结论整个翻过来(跨了日期),错的时刻写进裁定或记录后,要改好几份文档才纠得回来;估出来的戳看着和真的一样。所有机器和台面统一一个时区时,换算问题消失,但「用戳不用估」仍然成立。
**How to apply:** 写记录之前先做一次能拿到戳的台面动作,抄它返回的戳;判做对了:记录里的每个时刻都能在台面上找到同一个戳。
源案例:2026-09-09 某项目用本机时钟判断台面「快了 8 小时」,据此改错一条裁定的日期,又花两次文档提交才改回;09-23 用估出来的戳代替实测,三个文件返工,于是立了本条。

### 6.5 工单台是所有窗共用的约定:冻结后不为某一扇窗、某一种模型或一句捎来的口信改

name: desk-frozen-not-per-window
type: feedback
description: 有人捎话说「能不能把工单台的显示或用法改一下」,或某一种模型用不顺台面、想让台面迁就它时想起

1. 工单台的用法与显示一经正式裁定冻结,就不为某一扇窗、某一种模型的习惯,或一句聊天里捎来的口信改;真要改,走正式改裁定的流程。
2. 捎来的口信与台面上的正式裁定打架时,以台面为准;答复时直接引那条裁定,不重新出方案。

**Why:** 台面是所有窗之间唯一的共同语言,为一方改一次,其余各方的用法就跟着漂;口信没有记录、转述中会走样,却能让维护方白改一场。某种用法确实全员都不顺、要正式改裁定时,这条让位于那次裁定。
**How to apply:** 收到「能不能为某某改一下」,先查台面有没有对应裁定,有就引它答复并到此为止;判做对了:台面的每一次行为变化都能对到一条正式裁定。
源案例:2026-09-14 某项目为迁就一类模型,开窗指令一上午来回改三次,设计者与总编各一句口信,维护台面的位夹在中间改了一小时,设计者最终裁定还原,于是立了本条。

### 6.6 台面上有的字段只在第一次写入,之后不跟着变,证明不了后来的情况

name: desk-first-write-fields-go-stale
type: feedback
description: 想拿台面上某个字段(比如「实际模型」)说明后来某一波的情况,或有人说「照上一波同样的配置」时想起

台面上有的字段只在单子第一次开窗时写入,之后同一张单重开、换窗、换模型都不更新。拿它说「这一波用的是 X」,说的可能是第一波。要知道后来某一波实际怎样,看那一波自己的进度件、回执,或直接问当时的窗。

**Why:** 字段名读着像「当前值」,其实是「首次值」;照它推「上一波用的是什么」会说错,下一波照抄就配错。台面改成每次重开都覆盖写并留历史时,这条才不需要。
**How to apply:** 引任何台面字段当证据前,先弄清它什么时候写、会不会被后来的动作更新;判做对了:报告里「某一波用了什么」都附着那一波自己的记录。
源案例:2026-09-21 某项目设计者告知第七、八两波实际跑的是另一个模型,而台面「实际模型」一栏仍写着第一波开窗时的模型,台面上完全看不出换过,于是立了本条。

## 二 · 单子的状态与交板

### 6.7 状态流里每个中间态都要有一条走得到关闭的路;没有路时别拿别的转移硬凑

name: desk-every-state-reaches-close
type: feedback
description: 给工单台加「返工」「阻塞」这类状态、撤掉流程里的某一环、或一张单卡在某个状态收不了口时想起

1. 加中间态、撤掉流程里某一环时,同一步把「从这里怎样走到关闭」的路补上;撤掉的环节,状态流里不能还等着它。
2. 单子卡住时不拿别的状态转移硬凑,例如为了「往前挪」去解除阻塞一张只欠记账的单,那常把它推进更没出路的格子;记一行,找维护台面的位补路。
3. 看到有人伪造签名、写与事实相反的收口说法来交差,先查是不是缺了路。

**Why:** 状态流缺一条路不会报错,只会让走到那里的单永远停住;人为交差做的补偿动作往往比原问题更难收拾,还让记录失真。每个状态都有出口且有测试钉住时,这条不用额外操心。
**How to apply:** 改状态流时列一张「每个状态能走到哪个终态」的表,空格就是缺口;判做对了:任何状态的单都能说出一串走到关闭的操作。
源案例:2026-09-16 某项目修掉工单台一处缺口:已上线的单一旦落进「返工」,就没有任何路能走到关闭;修好之前还有人为了往前挪,去解除阻塞一张只欠记账的单,反把它推进更没出路的格子,于是立了本条。

### 6.8 解除阻塞时,同一轮把那本任务书从头到尾重读一遍

name: desk-unblock-rereads-taskbook
type: feedback
description: 一张阻塞了一段时间的单要解除阻塞、重新派出或重新开工时想起

阻塞中的单几乎没人再读它的任务书,建单时粘错的通用条款会一直藏到解除阻塞那天。解除阻塞不能只看「阻塞原因清了没」,同一轮把任务书通读一遍:核通用条款是否适用本单、里面的前提现在是否还成立,改完再放出去。

**Why:** 建单时粘错的条款,阻塞前没人开工、也就没人发现;阻塞期间别的单在推进,前提也可能已变。阻塞期间有人定期重读任务书的流程下,这条可放松。
**How to apply:** 解除阻塞和重读任务书写在同一步;判做对了:解阻塞的留言里附一句「已通读,改了哪几处」或「已通读,无需改」。
源案例:2026-09-20 某项目一张单的任务书整段从另一张单粘来、连单号都没改,单子阻塞期间没人重读,直到解除阻塞那天才暴露,于是立了本条。

### 6.9 交板闸要实机证据时,不拿内部豁免参数换放行;本窗取不了证就记阻塞、转交

name: desk-evidence-gate-no-bypass-flag
type: feedback
description: 交板被「要真实运行证据」的闸拦住、想加一个内部参数把改动标成「用户看不见」好放行时,或写任务书而执行窗未必能取证时想起

1. 改动用户看不看得见,有客观判法:改没改用户能看到、摸到的东西;看得见的改动,交板就要真实运行的证据。
2. 本窗取不了证时,不拿内部豁免参数把它改标成「看不见」;先去仓里确认活已经落地(远端有对应的支、代码里有改动),把单记成「阻塞在取证」,转给有取证环境的一方。
3. 任务书写清「本窗取不了证时怎么办」这条兜底路,不假设执行窗一定能自己取证。

**Why:** 证据闸就是为了挡「说做了但没真生效」,拿豁免参数绕过去,闸就等于不存在,账面上还看不出是绕的。改动确实是纯内部、用户看不见时,用豁免参数是正当的。
**How to apply:** 被这类闸拦住,先按客观判法判一次看得见与否;判做对了:每张看得见的改动,要么附着真实证据,要么挂着「阻塞在取证」并写明转给谁。
源案例:2026-09-14 某项目一处用户看得见的范围参数从 27 改成 50,交板闸要真实运行证据而当时的窗取不了证,单卡在「已认领」;最后是去代码里找到改动已落地的原文才解开,没有拿豁免参数硬放,于是立了本条。

### 6.10 交付项登记到具体文件,不登记目录

name: desk-deliverables-are-files
type: feedback
description: 交板时登记交付项、产出是一整个目录时想起

交板闸对交付项逐个文件核对在不在,登记一个目录它核不到,会直接拦下。产出是一整个目录时,登记一份列出目录里每个文件的清单文件、一个代表性文件,或打好的包文件。

**Why:** 目录没法按单个文件核在不在,闸只能当它核不到;逐个文件登记也让事后审计能一项一项对。闸支持按目录展开逐个核对时,这条可放松。
**How to apply:** 交板前把交付项列表逐项看一遍,是目录的都换成文件;判做对了:交板一次通过,没有「核不到」。
源案例:2026-09-21 某项目一次交板登记了 4 个目录当交付项,4 个全被闸以「核不到」拦下,于是立了本条。

### 6.11 替别人交板时,在证据第一句写明谁代谁交、为什么

name: desk-proxy-submit-says-who
type: feedback
description: 负责人替实际干活的窗交板、或替员工收口时想起

台面会把这次交板记在该单「指派给」那位名下,看不出是别人代交的。代交时,在证据第一句固定写明:代交人、实际完成人、代交原因。

**Why:** 不写,台面看着就像被指派的人自己交的,审计分不清谁代交、为何代交。交板命令本身有代交人字段时,改填那个字段。
**How to apply:** 代交前先看交板命令的帮助里有没有代交字段,没有就用首句写明;判做对了:只读证据首句就知道是谁代谁交的、为什么。
源案例:2026-09-21 某项目代别人交板时发现交板命令没有代交人参数,记账一律挂在该单「指派给」那位名下,台面上看不出是谁代交的,于是立了本条。

### 6.13 按字面匹配的闸连注释也拦:解释「为什么不能写 X」时,别把 X 抄进去

name: text-gates-match-comments-too
type: feedback
description: 在注释或文档里解释某个被禁止的写法,或看到文本闸命中、想直接判违规时想起

1. 按字面搜的闸分不清正文和注释:在注释里写「这里不能用 X,因为……」,X 本身就会被命中。解释时改用描述或同义说法,不把被禁的字面抄进去。
2. 看到文本闸命中,先打开文件看命中在哪:是真残留的写法,还是一段溯源用的解释;后者不算违规,但也要改写掉,免得下次再撞。

**Why:** 字面闸不懂语境,解释得越认真越容易被拦;验收的人见命中就判违规,会冤枉写解释的人。闸改成只看代码本体、跳过注释时,第 1 点可放松,第 2 点仍成立。
**How to apply:** 写注释前想一句「这段字会不会被哪道闸搜到」;判做对了:闸零命中,解释的意思仍在。
源案例:2026-09-08 某项目维护工单台的位在一扇窗里连撞三次:注释里抄了被禁的字面,按字面匹配的闸照样判红,于是立了本条。

### 6.14 遍历一份名单做检查的闸,会跟着名单一起悄悄缩水:名单本身要另有一条钉死

name: list-driven-gates-pin-the-list
type: feedback
description: 写「对名单里每一项检查一遍」式的闸或测试,或按一段文本范围切出来做检查时想起

1. 「对名单里每一项检查」的闸,名单被删掉一项就少查一项,结果照样全绿,不会报「名单变短了」。
2. 所以名单本身要另有一条断言钉死:项数等于一个写死的数,或逐项与一份独立清单比对。
3. 按一段文本范围切出来检查时,范围切窄;切太宽会把不相干的内容一起纳进来,造成误判。

**Why:** 名单既是被检查的一部分、又决定检查范围,形成自指:被检查的一方把自己缩小就更容易通过,这个动作本身不会被发现。名单由外部权威源生成、改名单要单独审批时,风险才小。
**How to apply:** 每写一个遍历名单的闸,同时写一条钉名单的断言;判做对了:删掉名单里任意一项,至少有一条断言变红。
源案例:2026-09-14 某项目工单台新加第十四个位,那些遍历名单做检查的闸一条都没红:闸跟着名单一起变,名单本身改得对不对没有任何一条在管,于是立了本条。

### 6.15 统计上从没被打破的规律只是约定,别写进机制当不变式

name: convention-not-invariant
type: feedback
description: 写缓存判据、跳过刷新、省掉某步检查,理由是「这种情况从来没发生过」时想起

「关闭的单从不重开」这类规律,哪怕样本是关闭 254 次、重开 0 次,也只是大家的习惯,不是系统强制的。一旦写进机制(比如缓存判据写成「状态名是已关闭就永不刷新」),后来加了会回头改的状态,机制就静默显示过期数据。判据改用约定被打破也仍然正确的东西,比如版本号、事件序号。

**Why:** 约定没有代码替它守,新状态、新流程一来就可能被打破,硬编码的假设不会报错。规律本身由系统强制(状态流里根本没有回头的那条边)时,可以依赖它。
**How to apply:** 看到「按状态名跳过」的逻辑,问一句「这个状态将来会不会回头」;判做对了:状态回头时判据自动失效、重新取数。
源案例:2026-09-08 某项目设计者提出关闭的工单没必要每次都重读,查实关闭 254 次、重开 0 次,他说得对;但「已答」「实机验过」这类状态会回头改,若把「关闭即不变」写进缓存判据就会静默显示过期数据,于是立了本条。

### 6.16 拒绝提示里给的命令,就是会被照抄去跑的代码:写完真跑一次

name: refusal-hint-commands-must-run
type: feedback
description: 给工单台或任何工具写报错、拒绝提示,里面附了「请改用这条命令」时想起

拒绝提示里附的出路命令,用户会原样复制去跑;功能测试只测「该不该拒绝」,碰不到那段文字的字面。
1. 新写之前,先在仓里找一版写对了、确实能跑的同类提示照着写。
2. 写完把命令抠出来,真喂给解析器跑一次,确认它合法、能到达提示所说的结果。

**Why:** 命令躲在字符串里,测试全绿也不代表它能跑;它若是唯一出路又跑不起来,单子就被锁死,而一切看着正常。提示文字由代码从真实命令定义自动生成时,这条可放松。
**How to apply:** 收尾时对每条新写或改过的拒绝提示,跑一次里面的命令;判做对了:照抄提示里的命令,能把被拒的那一步走通。
源案例:2026-09-14 某项目工单台「缺实机截图」那一拦的拒绝提示,把唯一出路指到一条走不通的命令,测试全绿,撞上的单被锁死,于是立了本条。

### 6.17 拒绝提示不能只给一种解释:附底层原话,并列可能原因,一种病一句话

name: refusal-hint-names-real-cause
type: feedback
description: 写报错、拒绝的兜底提示,或照着一条提示排查一次没好时想起

1. 兜底提示必须附上底层的原始报错(例如参数解析器的原话),不能只留一句人话总结把原话吞掉。
2. 同一处拒绝可能有几种原因时并列列出,不挑「最常见」的那个写死。
3. 不同的病配不同的提示,不用一句笼统话盖住好几种情况。
4. 照着提示排查一次没好,就去看底层原话,别照同一条提示再跑。

**Why:** 只给一种解释,等于把诊断提前写死;诊断错了,人会照着走,又看不到自己重新诊断需要的原话。提示与原因一一对应、且被测试钉住时,这条自然满足。
**How to apply:** 写兜底提示时问自己「原因若不是我想的那个,看到这句的人能自己查出来吗」;判做对了:提示里看得到原话和所有可能原因。
源案例:2026-09-16 某项目工单台一句兜底提示写成「参数不对,多半是检出旧了」,吞掉了参数解析器的原话,一扇 0 号窗照着它排查,两笔已上线单子的记账一直清不掉,这句话已是第二次把人引错路,于是立了本条。

### 6.18 「这是预期内的」一类提示,要写清它在什么条件下就不再是预期

name: expected-failure-note-needs-expiry
type: feedback
description: 在脚本、钩子、提示里写「这里失败是正常的」「这是预期内的」,或读到这类话想放过一个失败时想起

一句不带条件的「这是预期内的失败」,会把以后真正的失败也一起盖住。
1. 写这类话时一并写明:在什么条件下它是预期的,出现什么就说明它不再是预期(例如「产物为空就不是预期」)。
2. 读到这类话,先核它写的条件现在还成不成立,再决定放不放过。

**Why:** 这类话写下那天是对的,环境一变就过期,却还在替失败打掩护。条件被写成代码里的断言、失效即报错时,这条自然满足。
**How to apply:** 在仓里搜「预期」「正常」「可忽略」一类字样的提示,逐条补上失效条件;判做对了:每条这类提示都答得出「什么时候它就不对了」。
源案例:2026-09-08 某项目查出一条仓库镜像钩子已经坏了好几天,它那句「这是预期内的失败」提示早已过期、却一直替它打掩护,于是立了本条。

### 6.20 新分支的测试绿了,把那条分支临时短路再跑一次,转红才算测试真跨过它

name: short-circuit-branch-once
type: feedback
description: 新写了一条分支和对应测试、测试全绿、准备交板时想起

新测试绿,不证明它经过了新分支:分支可能从没被触发、断言钉在了别处、判据本身恒真。
1. 最便宜的证法:把新分支临时短路(强制走另一条路或关掉触发条件),重跑测试,看它由绿转红;确认后恢复代码再提交。
2. 选验证场景时,别选被测方法对该对象返回空的场景——那里断言钉不到东西;要选它真会产出东西的场景。

**Why:** 绿色本身不带「执行到了这条分支」的信息,不做这一步,新分支可以一直没被测到而全绿。测试框架能报出每条分支被哪些测试覆盖时,可以用那份报告代替。
**How to apply:** 交板说明里写一句「短路某分支后某测试变红」;判做对了:能指出是哪条测试因短路而红。
源案例:2026-09-21 某项目新开一条服务端发帧路径,新测试全绿却证明不了走过它;把发帧处短路后测试转红、放回即绿,不到一分钟排掉三类假绿,于是立了本条。

### 6.21 几个指标全变好,可能盖住「那条分支一次都没走到」:关键分支每次单独数命中

name: good-metrics-hide-dead-branch
type: feedback
description: 用几个汇总指标变好来证明一处改动生效时想起

几个汇总指标一起变好,不证明你改的那条分支起了作用:它可能一次都没被走到,指标变好另有原因。给关键分支单独打点,每跑一次记下它命中几次;命中为 0,指标再好也不算改动生效。

**Why:** 汇总指标的口径往往覆盖不到具体分支,好消息又最容易让人停止追问。分支本来就有独立计数、并被判据引用时,这条自然满足。
**How to apply:** 判据里除了汇总指标,再加一行「分支某某命中次数大于 0」;判做对了:报告里每条关键分支都有自己的命中数。
源案例:2026-09-20 某项目一次改动后,进入画面那一段的三个指标全部变好,关键分支的就绪事件却是 6 次里命中 0 次,说明那条分支一次都没走到,于是立了本条。

### 6.22 静态检查、单元测试、独立抽查全过,也要真跑一次,并看运行时错误日志

name: run-once-read-runtime-error-log
type: feedback
description: 改了界面结构、对象挂载关系这类运行时才组装起来的东西,准备只凭测试全绿交板时想起

对象生命周期、挂载关系这类错误,只在真正实例化运行时出现,静态检查和单元测试都碰不到;顺手做的连带小改最容易挂错挂载点。
1. 这类改动收尾前真启动一次,把「运行时错误日志是否非空」当作一条独立判据。
2. 平时错误日志一直是 0 字节,一旦非空本身就是信号。
3. 日志有错不等于程序崩了(见 6.26),要看是什么错。

**Why:** 测试证明的是逻辑,不是运行时的组装。纯逻辑改动、不涉及运行时组装时,这条可放松。
**How to apply:** 判据写「真跑一次,运行时错误日志为空或只含已知项」;判做对了:交板附着一次真跑的日志尾。
源案例:2026-09-20 某项目一处改动四组构建、2,774 条单元测试和另一方独立抽查 40 条全过,真跑一次客户端才在运行时日志里看到「子节点已有父节点、不能再挂」的报错;此前两批共 15 次运行的错误日志一直是 0 字节,这次非空本身就是信号,于是立了本条。

### 6.23 上线后已经开着的页面可能还是旧的:先强制整页刷新,再判「改动没生效」

name: hard-refresh-before-judging-deploy
type: feedback
description: 工单台或任何网页上线后看改动效果、觉得「没生效」时想起

页面若按「有新事件才拉新数据」增量刷新,而这次上线只改了计算方式(派生字段怎么算)、没产生新事件,上线前就开着的页签会一直显示旧结果。判「改动没生效」之前,先强制整页刷新或开新页签;验收不拿早就开着的旧页签当依据。

**Why:** 增量刷新默认「没新事件就没新数据」,纯代码改动恰好不触发它;旧页签上的旧结果与「没改好」看起来一模一样。上线会主动推一个让页面全量重拉的信号时,这条可放松。
**How to apply:** 验收步骤第一步写「强制刷新」;判做对了:结论所依据的截图或数值来自上线后新打开的页面。
源案例:2026-09-14 某项目改了工单台网页上显示的开窗指令并上线,上线前开着的旧页签仍显示改前的样子,拿它看就会判成没生效,于是立了本条。

### 6.24 抓失败清单别给名字设字符类:会静默漏掉一整类行,剩下的还恰好自洽

name: failure-list-regex-drops-rows
type: feedback
description: 用正则从测试输出里抓失败测试名、文件名,或转用别人给的「已修正」抓法时想起

1. 给测试名这类自由文本设字符类(如「非空格」「字母数字下划线点」),会静默漏掉带空格的参数化测试行、含中文的名字;剩下的样本恰好能互相印证出一个看似合理的错结论。
2. 抓法改成不设字符类的宽松匹配,或直接读结构化的测试结果文件,不对文本输出做搜索。
3. 别人给的「已修正版」抓法,转述或使用前先在一份已知答案的输出上自己跑一遍。

**Why:** 被漏掉的恰是会打破结论的那部分;第二次踩坑时人往往不去查,而是给错结果编一个解释。输出本身就是结构化格式、按字段取值时,这条不需要。
**How to apply:** 抓完清单核一次「抓到的条数 = 汇总行里的失败数」;判做对了:两个数相等。
源案例:2026-09-21 某项目同一个坑连踩两次:字符类先漏掉参数化行、又漏掉中文名,剩下的样本自洽出错结论,第二次还给它编了解释;连 0 号窗也照抄了一份同样错的「更正版」抓法,于是立了本条。

### 6.25 判「现在是什么行为」,顺着真正读它的那条链走到底:名字、同名、上游修好都不算

name: trace-the-reader-not-the-name
type: feedback
description: 凭字段名、层名、列名判断行为,或子代理报「某行为已改变」,或上游修好了某个值准备收口时想起

1. 名字不等于行为,见 3.5。
2. 子代理报「行为变了」,先问一句「变之前那个行为真的存在过吗」。
3. 上游(服务端)的权威值修好了,下游显示层可能自己另算了一份、根本没读它;要看显示层实际读的是哪一份。
4. 两个同名的列或概念可能是两件事;要证「是同一个」,去找一个两者不一致的反例,比收集一堆一致的样本更管用。

**Why:** 名字是给人看的,没有机器保证它和行为同步;大多数样本恰好支持错结论时,错会显得很自洽。名字由同一份定义自动派生、与行为绑死时,名字才可信。
**How to apply:** 写「X 现在是 Y 行为」之前,附上读取它的那条调用链末端的位置;判做对了:结论能指到实际读值的那一行。
源案例:2026-09-20 某项目把一个界面从名叫「模态」的层挪进普通窗口层,子代理报成「行为改变」,查下来那个层从来就不是模态、挪前挪后行为一样,于是立了本条。

### 6.26 静态推演和别人报的崩溃能一起错:真跑之前,「会崩」只写成未证推断,不拿它卡别人

name: unrun-crash-claim-unproven
type: feedback
description: 读码推断「这里一定会崩」,又有人报过崩溃,准备据此阻塞别人的单或改排期时想起

1. 两条独立来源指向同一结论,不自动升格成「已证实」:它们可能共享同一个盲区。
2. 真跑之前,「会崩」只能写成「未证推断」,不许拿它卡别人的排期、阻塞别人的单;有零成本的试运行模式就先跑一次。
3. 现场已删、再也重演不出来的崩溃报告只是线索,不是判据。

**Why:** 推演和观察可能漏掉同一处,比如异常被回调里的捕获吞掉、后面又有一次补救调用把事做对了;拿未证推断卡人,代价由别人付。能低成本真跑时,就没有理由停在推断上。
**How to apply:** 凡写「会崩」处一律加「未证推断」,并附「怎么真跑验证」;判做对了:阻塞别人的理由都附着一次真跑结果。
源案例:2026-09-20 某项目一份完整的静态推演,加上另一处「连跑三次全崩」的报告,都指向必崩;真跑发现异常确实抛了、程序却没崩:信号回调里的捕获吞掉了异常,同一函数往后 26 行还有一次补救调用把事做对了,于是立了本条。

### 6.27 「五处都说交了」可能是一句话被转述了五遍:交付物在不在,只看文件本身

name: many-mentions-may-be-one-chain
type: feedback
description: 交接件、进度件、几份报告都说某份关键输入已经有了,准备据此开工时想起

几份文档都说某交付物存在,可能全是同一句话一层层抄过来的,源头从没验过。开工第一步直接查那个文件本身(列目录、打开看内容);不在,就派子代理对着代码重建,不沿着转述链往下传。

**Why:** 互相引用造出「多方印证」的假象;引用再多也不增加可信度,源头错了就全错。文档之间有机器可核的链接(如文件哈希)时,这条可放松。
**How to apply:** 开工清单里把最重要的输入逐个列出,每个附一次存在性核对的结果;判做对了:开工前就知道缺哪份,而不是做到一半才发现。
源案例:2026-09-20 某项目一份交接件钉死的「最重要输入」,在好几处文档里都被说成已经交了,开工全盘一搜零命中,它从未存在过,于是立了本条。

### 6.28 接手现成的优化方案,先量收益能否兑现再照做

name: measure-before-optimising
type: feedback
description: 接手交接件或别人写好的现成优化方案、准备照着做时想起

接手现成的优化方案,先小范围实测它的收益能否兑现,再决定照不照做;兑现得少,就回头看真正的消耗在哪、换一个针对它的做法。

**Why:** 「听起来应该有效」和「证明有效」差得很远,照抄的方案可能只兑现一小部分收益。方案已在同样的负载下被实测证实时,可以直接照做。
**How to apply:** 照做前先报「改前多少、小范围试后多少」;判做对了:决定照做的依据是实测收益,不是方案里写的预期。
源案例:2026-09-08 某项目照接管件里的现成方案做只降了 10.7%,改按消费端实际用量裁剪降了 63.3%,于是立了本条。

### 6.29 别人报的「一个数加一个归因」要分开验:数可能对,归因可能错

name: verify-number-and-cause-separately
type: feedback
description: 收到「某处慢了多少,是因为某某」这类报告,或有人报「慢」「卡」、准备照着那个原因去改时想起

报障描述的是症状,不是病因;报告里的数和归因是两件事。
1. 先核数:自己量一次。
2. 再单独核归因:按这个归因、用现有机制复算一遍,看能不能算出这个数;算不出来,就是归因错了。
3. 归因不成立时,分段量(算、传,还是别处),找到真正的瓶颈再动手。

**Why:** 数对了,人会顺手连归因一起信,照错的归因去改就白改。归因已被一次对照实验单独证实时,可以直接用。
**How to apply:** 回复这类报告时分两行写「数:核了没有」「归因:核了没有」;判做对了:两行都写得出核法。
源案例:2026-09-08 某项目设计者判断刷新慢是因为关闭的单每次都在传,方向没错,但一量,当时 5 秒里有 4.93 秒花在传对话线上,真凶另在别处,于是立了本条。

### 6.30 派单必填真源指针、消费者、交付项三样,填不出不发车;一个员工同一时间只持一张已认领单

name: dispatch-three-fields-one-claim-per-staff
type: feedback
description: 起草任务书、在工单台上建单派活,或员工手上已有一张单、又想去领别的单时想起

1. 派单必填三样:真源指针;消费者(本单产物被谁加载、谁用);交付项(已存在的文件,不是目录)。填不出任何一样,就是任务书不完整,不发车。
2. 建单后要另设的字段(如免判卷标记),建完回读核一遍。
3. 一个员工同一时间只持一张已认领单,做完或退回才领下一张;员工不扫队列、不领别的单。

**Why:** 三样缺一样,执行的窗就不知道照什么做、做给谁用、交什么,做完也没法逐项核;交付项写成还没有的文件或目录,建单的闸当场就拦。一人同时持两张单,哪张在做、哪张在等说不清,派单方排不准;员工自己扫队列领单,派单方就不知道谁手上是什么。建单与认领都由台面强制校验时,人工这一步可放松。
**How to apply:** 发车前逐项过三样:真源指针打得开,消费者写得出是谁,交付项每一项在盘上列得出且不是目录;建完单按单号回读另设的字段;派新单前先看这个员工名下有没有已认领未结的单。判做对了:建单一次过闸,另设字段回读与预期一致,任一时刻每个员工名下最多一张已认领单。
源案例:2026-09-04 某项目派单时把还没产出的新文件写成交付项,建单当场被闸拦下,于是立了本条。
