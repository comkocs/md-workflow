# 5 · 闸的哲学

本节收:验收判据、放行条件、审计与退回这类把关环节该怎么设——一道闸该拦什么、责任记给谁,判据怎么立才真,怎样确认闸本身在干活,证据怎么收、放行前看什么,把关该留几道、验证做多少。读法:立一道新闸或改一道旧闸、给任务书写验收判据、验收一批活并决定放不放行、想加或想撤一道检查之前,翻对应那一组;一道闸红得莫名或绿得可疑时,先翻第三组。

## 一 · 闸拦什么、责任记给谁

### 5.1 闸只拦「活没做好」,不拦「字没写对」:撞上账面类的闸记一行,接着干

name: gates-block-bad-work-not-paperwork
type: feedback
description: 立一道闸、在任务书里写停车条件,或执行方被一道与活本身无关的检查拦住时

1. 该拦的只有「活没做好」:真源缺、接口对不上、判据不达、测试红。
2. 时刻、账面、交付项的路径或后缀、任务书的校验状态、镜像或远端滞后、本机工具版本落后、脚本不认某个参数——这类非业务闸不停车:在回执里记一行「撞到非业务闸 X,已按 Y 继续」,把不依赖它的活全做完,交付时由闸的维护方改闸放行。
3. 任务书里不写「遇 X 即停」这类条款。
4. 判据一句:这道闸拦住的,是「活没做好」,还是「字没写对」。

**Why:** 执行窗多半是一次性的,卡在半路的代价是整窗作废、设计者被叫来审批、下一轮重读整张单,换来的只是一处账面对齐。只拦业务问题的闸,执行方停下来时一定有东西要修。项目进入「账面本身就是交付物」的阶段(例如合规归档)时,相应的账面检查才升格为业务闸。
**How to apply:** 写闸或写任务书时先问「这道闸拦住的,是不是执行方能控制、且关乎活本身的东西」;不是,就改成在建单那一刻拦出题方,或在报错里直接给出继续的办法。判做对了:翻一周的停车记录,每一次停车背后都有一处活没做好。
源案例:2026-09-06 某项目设计者定下:今后不再额外加任何影响员工干活的东西,活做得不好或因任务本身阻塞可以接受,因其他客观原因阻塞不行;09-08 他又点病:近两天停下的窗几乎全是被账面类的闸拦住,没有一件是活没做好,于是立了本条。

### 5.2 立一道新闸,同一笔写清三样:拦哪种「活没做好」、拦下之后的回口、什么时候拆

name: new-gate-needs-reason-exit-and-sunset
type: feedback
description: 出了事想加一道检查、写一个「不够就不许做」的资源闸,或给任务书写前置阻塞条件时

1. 三样缺一不立:①拦的是哪一种「活没做好」;②回口——拦下之后谁、跑哪条命令、怎么继续;③拆除条件——什么情况下这道闸可以删。
2. 拒绝语是闸的一部分:拦下时写明「若是 X 情形,请谁跑哪一条命令」,那条命令先自己跑通;兜底文案带底层原话,并列出几种可能原因。
3. 资源类闸(「不够就不许做 X」)先查那个资源的全部写入点,确认有回口;没有回口就同批补上,或明说这是死锁。
4. 前置阻塞逐条问「这件事由谁、什么时候做完」;执行方开工后要做的第一件事不是前置,写成前置就是一道永远解不开的闸。

**Why:** 每出一次事就加一道闸、从来不拆,闸越叠越多,最后拦下的几乎全是闸与闸之间的缝;没有回口的闸不是难度,是死锁。三样写全了,闸的去留就有据可查。整个项目只有一两道闸、人人都记得它为什么在时,可以不单写拆除条件。
**How to apply:** 新闸的提交或章程条目里固定三行「拦什么 / 回口 / 拆除条件」,缺一行不合入;巡查阻塞状态时把每个前置重新核一遍还成不成立。判做对了:任意指一道闸,都能当场说出它拦什么、撞上怎么办、哪天能拆。
源案例:2026-09-13 某项目一位负责人把本该由本单完成的一次数据同步写成了前置条件,造成一道数学上永远满足不了的阻塞,被下游来问才暴露;09-15 设计者又点出另一个沿用同一套模式的项目每次出事就加一道闸、从不拆,于是立了本条。

### 5.3 退回一张单,第一句先标责任:出题责任还是执行责任

name: rejection-opens-with-responsibility
type: feedback
description: 验收不通过要退回、写退回意见,或按退回次数统计执行方合格率时

1. 退回意见第一行以「出题责任:」或「执行责任:」开头;两类都有就逐条各标。
2. 任务书漏步骤、底数错、口径晚到、判据写反、要求超出执行方权限,都算出题责任。
3. 缺责任标注的退回,上一级打回给写意见的人补标。
4. 执行方照书做完却拿不到预期结果,先查出题有没有漏,再看执行方。

**Why:** 退回会被计进执行方的合格率;出题的缺陷不标出来,就被记成执行方的缺陷,既冤枉了执行方,又让真正的病根(书写错了)继续复制到下一张书,看合格率换人换模型,换来的还是同一种退回。出题与执行是同一个人时,这条自然消失。
**How to apply:** 写退回意见前先把任务书与判据对一遍,问「照书做能不能做对」;不能,就是出题责任。判做对了:退回意见首行都带责任标,出题责任的那几条后面跟着改书的记录。
源案例:2026-09-04 至 09-05 某项目一位总监退回四张单,事后看三张是出题责任,同一类退回错误两天里共出了七次,出题缺陷全被记在执行方头上,于是立了本条。

### 5.4 停不停车跟着档位走:要自己拿主意的活不写停车条款,不许拿主意的档撞到意外就停

name: stop-rules-follow-autonomy-tier
type: feedback
description: 给任务书定档、写「遇到什么就停下」的条款,或执行方停下来报障碍时

1. 定档的判据是「结果和预期不一样时,要不要执行方自己拿主意」,不是改动量大小;要拿主意,就不能定最严的档。
2. 高自主档的书只写红线,不写停车条款:遇到口径冲突或前置没清,自己判、做完,把「自主假设」逐条写进收尾;假设事后被推翻只触发补改,不记执行方的账。
3. 最严档(不许取舍、不许自己找文件)按写死的步骤做完、结果对不上,正确动作是停下报告;这时先假设它做对了,回头查是不是档定错了。
4. 真想严管某件事,就把它降一档,不在高档书里加停车条款。

**Why:** 停车条款放在高档书里,执行方能做的都做完了还在空等答案,时间被条款本身吃掉;反过来,把需要判断的活定成最严档,执行方停下来暴露的是分档错了,不是活有问题。两种错的根都是没按「要不要拿主意」分档。只有一个档位的项目不需要这条。
**How to apply:** 定档前问一句「结果不对时,他需要自己拿主意吗」;高档书写完搜一遍「停」「等」字样,有就删或降档;收到最严档的停车报告,先查书。判做对了:高档单的收尾里有自主假设清单,最严档的停车报告里没有一次是出题漏了。
源案例:2026-09-06 某项目一张三行小改的最严档单做完后,一个不相关的断言意外变红,执行方正确地停下报告,复盘认定是档定错了;09-12 两张高自主档单又按旧规在「等四个问题的答案」上停了很久,其实能做的都已做完,设计者当场改为先做完再汇报,于是立了本条。

### 5.5 执行方第二次撞上同一类过不去的闸,别再一处处开口子,自己跑一次探针拿全貌

name: second-block-run-a-probe
type: feedback
description: 执行方因权限或只读限制停下、你准备再给它开一处口子时

1. 第一次撞上,可以就地开这一处。
2. 第二次撞上同一类,停止一处一处地开:自己打一个最小补丁,模拟「全部放开之后」的状态,跑一次完整探测拿到全貌。
3. 按探测出的病因分组一次放开,或据此重新拆单。
4. 给执行方写一句「撞到权限够不着的地方就如实报,不计你的责任」,让它敢报而不是硬闯;这是对权限边界的说明,不是 5.1、5.4 所说的停车条款,两者不冲突。

**Why:** 开口子是单向的,每次只解决眼前这一处;下一处马上又撞上,每次都是执行方停一次、你往返一整轮。第二次撞上本身就说明问题不是局部的。障碍确实只有一处,或探针的成本高于再往返一次时,不必跑。
**How to apply:** 开口子之前问自己「这处开完,还会不会有第三处」;答不上来就去跑探针。判做对了:同一张单上开口子的动作不超过两次。
源案例:2026-09-12 某项目一张单连续一处一处开了四次口子,执行方每次都正确停下,第四次改为自己打补丁跑探针,三次探针就查清是结构性问题(失败从 94 条降到 36 条证明是级联,再补一处冒出 445 条失败、测试运行中止证明此路不通),当场改为拆单,于是立了本条。

## 二 · 判据怎么立

### 5.6 写「用户能看到 X」之前,先证明它能被满足:值有消费端,屏上有承载它的地方

name: criterion-must-be-satisfiable
type: feedback
description: 给任务书写用户可感知类的验收判据,或执行方回报「拿不到预期证据」时

1. 写判据前三问:这个值在消费端有没有读它的地方(搜得到调用);项目里有没有把它标成「用户不可见」、与判据冲突;屏上承载它的那个部件本身存不存在。
2. 三问里有一个答「没有」,这条判据从一开始就满足不了:先补链路或改判据,再派单。
3. 书里写一句:拿不到预期证据时,查清为什么拿不到,比凑出一份证据更有价值。

**Why:** 后台有不等于屏上有;一条满足不了的判据,执行方怎么努力都会失败,而责任在出题一方,执行方被逼着凑证据还会凑出假证据。判据只涉及后台行为、不涉及呈现时,第三问可省。
**How to apply:** 写完用户可感知类判据,附上三问的答案与证据行;收到「拿不到证据」的回报,先回头做三问。判做对了:没有一张单因为「本来就显示不出来」被退回。
源案例:2026-09-07 某项目回头查出此前连续三批任务书的判据都写错:一个文案键在前端零消费、一个面板从没接上数据协议、一个「格子数」其实是清单长度而不是界面上的格数,执行方全部白跑,于是立了本条。

### 5.7 判据立之前先在基线上跑一次:基线自己都过不了的绝对判据,改成「差额不许扩大」

name: criterion-must-pass-on-baseline
type: feedback
description: 定一条「两边必须一致」「必须为零」式的判据,或执行方报判据在改动之前就不成立时

1. 新判据先在未改动的基线上跑一次,看基线过不过。
2. 基线就过不了的绝对判据(两边一个不差、失败数为零之类)是一道谁也过不去、只能被绕开的假闸;改成相对判据:以基线为准,差额不许扩大、新增为零。
3. 执行方发现判据在基线上就不成立、主动改成相对判据,记为质量信号,不记越权;改动写进交接件。

**Why:** 绝对判据在基线上不成立时,要么永远红,要么逼人放宽到恒真,两条路都让这道闸失效;相对判据只盯「这次有没有变坏」,正是一张单能负责的范围。基线确实干净、历史欠账已清时,绝对判据才重新可用。
**How to apply:** 写判据时附一行「基线上的值」;基线不为零的,判据写成「不超过基线」。判做对了:每条判据都能在基线上给出一个具体数。
源案例:2026-09-20 某项目一批活的一条判据原定两种语言的键一个不差,实测基线本来就对不上,该批主动改成「差额不许扩大」并写进交接件,这一改被记为质量加分,于是立了本条。

### 5.8 先问覆盖对不对,再问测得准不准:验收场景按真实用户最常走的路写死

name: coverage-before-precision
type: feedback
description: 给行为类修复写验收场景,或验收方准备按一组漂亮数据放行时

1. 判定前逐条问四个维度:输入方式对不对(默认操作,还是特殊触发)、路径形状对不对(最简单的那条,还是用户常走的那条)、起始状态对不对(从空白或静止开始,还是接着上一步做)、中途有没有状态变化。
2. 任务书把场景写死,不写笼统的「操作几次」「跑一遍」。
3. 最简单、最好测的那条路,往往不是缺陷出现的那条路。

**Why:** 判据再硬、数据再漂亮,覆盖面错了也是白判;验收方亲自重算过的数,也救不了走错的路径。缺陷与操作路径无关(纯数据校验、纯计算)时,这条可省。
**How to apply:** 写场景前先问报缺陷的人「你当时是怎么操作的」,把他的操作写成场景;验收回报里写明走的是哪条路径。判做对了:修复单的验收场景与报缺时的操作一致。
源案例:2026-09-06 某项目连续两次放行一个移动卡顿的修复,实测都只走横平竖直的直线,真正的缺陷只在斜着走时出现,两次放行的修复都没碰到问题真正发生的路径,于是立了本条。

### 5.9 引用现成的判据公式或阈值前,先核它成立的前提;基础参数一改,派生的判据全部重算

name: recheck-premise-before-reusing-criterion
type: feedback
description: 沿用旧单的验收公式、容错阈值、预期数值,或某个基础常量刚被改过时

1. 「算式套上去和实测对得上」不等于前提还成立;先回真源确认这个预期是设计上就该发生的。
2. 基础常量(速度、频率、分辨率、时钟节拍之类)一改,把由它推导出来的判据与阈值列出来,逐条重算,不只改那一个数。
3. 任务书留一句:本书给的数表若与你的实测对不上,以实测为准,并报回不一致之处。

**Why:** 验收公式带着隐含假设,假设不再成立时,闸要么永远过不去,要么永远拦不住;没人重算的阈值,会让执行方怎么做都通不过。常量冻结、无人改动的阶段,这条风险最小。
**How to apply:** 改基础常量的单,交付项里加一张「受影响的判据与阈值」清单;引用旧公式时写明它的前提。判做对了:常量改动之后,没有一张单被旧阈值卡住。
源案例:2026-09-06 某项目连续两次踩坑:沿用一个只在直线移动下成立的补偿公式,而实际路径几乎全是斜步,改前改后毫无差别;速度常量调高后,一条容错余量掉到 33 毫秒、再被逻辑帧量化砍到 16.67 毫秒,没人重算这条阈值,执行方怎么做都过不了,于是立了本条。

### 5.10 两条各自成立的红线在交叉处打架时,由出题人写死交叉处怎么办

name: define-where-two-rules-cross
type: feedback
description: 任务书里同时有「缺数据就留位占位」与「屏上不许出现开发字样」这类两条都对的要求时

1. 写两条可能相交的红线时,在同一句里写死交叉地带的处理(例如占位一律显示中性符号),不留给执行方选。
2. 「缺失时显示什么」要写具体呈现,不许把内部键名、枚举名、字段名直接显示出来。
3. 产品代码里内置的回落默认值同样受红线约束;审查时专门搜这类默认值的内容。

**Why:** 交叉地带没写死,执行方守一条必犯另一条,照做也会踩线,而责任在立规则的一方;回落默认值藏在代码里,只看新写部分的审查看不到它。两条规则不可能同时触发时,不需要写交叉处。
**How to apply:** 立一条新红线时,把现有红线逐条过一遍,问「这两条会不会在同一处同时成立」;会,就在新红线里写交叉处的处理。判做对了:执行方没有一次因为「守了 A 违反了 B」被退回。
源案例:2026-09-06 某项目一个面板任务的数值占位合规,标签占位却直接显示了内部键名,踩了「屏上无开发字样」的红线;09-09 又查出框架代码内置的回落文案本身就是给开发者看的占位句,且直接进了用户阅读的语言文件,92 条全部命中,于是立了本条。

### 5.11 拆活时每一项都要正面写进某一份书;在自己书里写「这项归别人」,不产生任何指派

name: every-item-assigned-positively
type: feedback
description: 把一件活拆给几个执行单元,或在一份书里写「这项不归你」时

1. 在 A 的书里写「这项归 B」的同一刻,去 B 的书里补一条正面条目。
2. 拆完另立一张总清单,把需求逐条对到「哪份书的哪一节」;对不上的就是漏项。
3. 收口时拿最终落地的产物逐条对总清单,不只看代码审查和测试。
4. 派活用范围(哪几个文件、哪几节、哪几行)描述,不用动词(「换皮」「清理」「修适配」);动词会被理解成最省事的那种做法。

**Why:** 每个人只对自己书里正面写了的事负责;覆盖面等于各份书正面条目之和,否定句不产生指派。漏掉的那部分没人做,所以也没有任何测试会为它变红。只有一个执行单元时不存在这道缝。
**How to apply:** 搜自己写的书里「归」「别碰」「不归你」一类字样,每一处都在对方书里找到对应的正面条目。判做对了:总清单每一行都指向一份书的一节。
源案例:2026-09-18 某项目把一件活拆给两个执行单元时,为防误改在其中一份书里写「某参数改动整项归另一方,你别碰」,另一份书从头到尾没有这一项,结果参数表改了、代码默认值没改,全量测试全绿、两个执行方都报没问题,漏项没人发现,于是立了本条。

### 5.12 书里每条要求都要有执行方够得着、跑得出来的核法;核不出来的要求只是纸面

name: every-requirement-needs-a-runnable-check
type: feedback
description: 起草任务书、写验收判据,或执行方回报「这一步我做不到」时

1. 站在执行方的权限与工具上写:它调不了的通道、改不了的标记、拿不到的环境,不写成它的步骤。
2. 写进书或判据的每一条要求,都要有一条执行方权限内能跑的核法(命令、脚本、查询);「不许与现有内容重复」这类约束写进可跑的检查,不只写成一句话。
3. 要求的产物若现有工具链根本产不出来,先补工具再派活。
4. 上游转来的前提(字段类型、取值范围、号段)写进书之前自己核一遍装不装得下;命令写进书之前先跑一次它的帮助或真跑一次。

**Why:** 执行方只照书做,做不到的步骤要么硬凑、要么停下报阻塞,两种都浪费一轮,还会被记成执行方的缺陷;核不出来的要求,执行方无从自证,验收方也无从判定。派单方与执行方权限完全相同时,第 1 点自然成立。
**How to apply:** 派单前逐条问「他用什么核这一条」,答不上就补核法或删这条;建单后改不了的一次性标记,建单时一次填对。判做对了:执行方的停车报告里没有「权限不够」「工具产不出」。
源案例:2026-09-05 某项目两天内同一类「书超出执行方权限」的错误发生七次,都被执行方正确顶回;其中一次把一个取值范围不够大的字段类型硬套给取值更大的业务量,执行方动手前就看出装不下而停工,于是立了本条。

### 5.13 判据只有落进章程并升了版号才生效;只写在交接资料或工单正文里的,不能拿来判别人

name: criteria-valid-only-in-charter
type: feedback
description: 引用一条判据去退回别人的活,或接手一个岗位、发现它的判据散在交接资料里时

1. 凡改判据、红线、生效条件的裁定,同一笔落进章程(项目级落最高治理文件,岗位内落该岗位章程的判据节)并升版号。
2. 只写在交接资料、口头传承或工单正文里的判据不生效,不得用来判别人的单。
3. 接手一个岗位先查它的章程有没有判据节和版号;交接资料只留沿革,注明「以章程为准」。

**Why:** 判据的效力来自正式落地,不来自被反复引用;散在交接件里的判据各窗各记一版,判人时谁也说不清依据的是哪一版,被判的一方也无从事先知道。项目只有一个人既立规又验收时可以放松,但升版号仍有助于追溯。
**How to apply:** 退回意见里引用判据时带上章程节号与版号;引不出来的判据,先落章程再判。判做对了:任一退回意见里的判据都能在当前版章程里搜到。
源案例:2026-09-06 某项目新规生效当天自查,发现一个岗位近期答过的六条判据口径在最高治理文件里全部零命中,更早的判据也一直只存在于接管资料里,按新规全部不算数,于是立了本条。

### 5.14 只数条数的检查藏在你改的文件之外:出题时主动想一遍,更新计数写死成一道加法

name: counting-gates-live-outside-your-diff
type: feedback
description: 往一张登记表里加条目、加一组编号、加一类数据行,或给这类活派单时

1. 有一类检查不看内容、只数数:某张表一共应有多少条、分成几类、几项加起来应等于多少。它们不在你要改的文件里,而在你改完才会跑的测试里;事前勘查时看不见,只能出题时主动想一遍。
2. 改一张被别处按条数登记的表之前,逐件问:会不会让某个「总数应为 N」的检查变红。
3. 需要更新这类计数时写死做法:只按这次实际增减的条数改,执行方要答出「原来 N 条,加了 k 条,现在 N+k」;对不上就查原因,不去改数迁就;不许改成永远成立的写法(例如拿同一处现数出来的数跟它自己比),也不许直接跳过这项检查。
4. 一个值真正生效可能要改好几处(常量定义处、手工维护的登记行、另一个仓里的镜像副本);出题时列全。

**Why:** 这类检查在别处变红,最省事的修法是把期望的总数改成当前数,检查从此永远成立;写死「加法对得上」才保得住它。项目里没有任何按条数卡的检查时不需要这条。
**How to apply:** 任务书里凡会改变条数的,写一行「预期 N → N+k,受影响的计数检查是哪几条」;验收时看执行方的加法对不对。判做对了:每次改期望总数都附一道对得上的加法。
源案例:2026-09-19 某项目一天撞两次:一张单只交了参数文件,可这个值真正生效还要改常量定义处、手工维护的登记行、另一个仓里的镜像副本三处;另一张单新增一组协议编号,把别处四个「编号总数应为 N」的检查打红了,于是立了本条。

### 5.15 「缺值时不替人代填」和「缺值时不拦人」是两件事:未定稿给一个显式状态,默认拦

name: missing-value-must-block-by-default
type: feedback
description: 写一个遇到空值、未定稿字段时的兼容分支,或数据里有一批行标着「未定」时

1. 数据缺失时如实标注、不替决策者瞎填,是对的;但标注之后的判定走向要单独定,不能顺手写成跳过。
2. 未定稿单设一个显式状态,在门槛判定里默认拦截,不默认生效。
3. 引用一个「某类缺口还剩几条」的历史数字之前,用真源当场重数一遍。

**Why:** 为「不代填」写的兼容分支顺手用了跳过,结果变成「缺值即生效」:两种语义混在一个分支里,谁也不报错,满足其余条件的对象全被点亮。缺值本来就应当生效(纯展示、可选字段)时,默认放过才对,但要写明。
**How to apply:** 写兼容分支时分开答两句:这里不填对不对;不填之后该拦还是该放。判做对了:每个缺值分支旁都有一行注明它默认拦还是放、为什么。
源案例:2026-09-08 某项目实核发现,一批门槛字段标着「未定」的条目,对所有过了前一道门槛的用户都显示为可用;同日还查明记忆里「还剩 23 行未定」的数字早已过期,实际只剩 1 行是有意保留的标记,于是立了本条。

## 三 · 闸到底在不在干活

### 5.16 没验过的闸视为不存在:造一次它该拦的场景真跑,两侧都验

name: untested-gate-does-not-exist
type: feedback
description: 刚立了一道闸、在用一道老闸,或靠「它没报东西」判了一次过时

1. 凡靠「没报东西」判过的闸,构造一次它该报的场景真跑:该放时放、该拦时真拦得住,两侧都验;只验放行那侧,只证明它不碍事。
2. 用了几周的老闸,也要回头验一次。
3. 改闸本身的单,必须证明闸还拦得住:把断言改成恒真照样全绿,所以至少故意改坏一次被测代码(例如短路掉新分支),确认测试转红,证明它真跨过了新分支。
4. 闸只在一部分输入上工作(例如只认英文路径)也算没验过;构造场景要覆盖另一部分。

**Why:** 一道恒真的检查,与一个真没问题的系统,输出一模一样;闸不响,你还可能觉得「今天怎么这么顺」,闸给了绿灯,你连怀疑的由头都没有。故意改坏一次只花几分钟,换来的是闸确实在工作的证据。闸自带自测、且自测包含该拦场景时,可以引用自测结果。
**How to apply:** 立闸、改闸、验收闸的单里固定一行「该拦场景真跑结果」,缺这一行不放行。判做对了:每道闸都有一次被故意触发、真的拦下的记录。
源案例:2026-09-15 某项目一道路径前缀闸遇到版本库把中文路径转义成八进制,永远匹配不上,英文路径照常能认,这道闸「一半在工作」却一直给绿灯,于是立了本条。

### 5.17 「命中 0 条」必须配一条「输入非空」:真零命中与根本没读到,输出一模一样

name: zero-hits-needs-nonempty-input
type: feedback
description: 用搜索、日志查询、计数判「没有问题」「零失败」「零残留」时

1. 每个「命中 0」旁边配一个证明输入非空的量(读到的行数、扫到的文件数、日志的时间跨度)。
2. 怀疑判据恒真,就故意把输入弄坏(塞一条必中的样本)跑一次,看它报不报。
3. 查日志先确认被查的服务真往那里写;日志写在服务自己的文件里时,查系统日志永远是零。

**Why:** 空输入、读错位置、权限不够、编码不对,都会让检查安静地返回零;零本身不带任何「我真读了」的信息。检查自带「已扫描 N 项」输出、且 N 被一起核对时,这条已被满足。
**How to apply:** 判据里凡写「零命中」,改写成「扫描 N 项(N 大于 0),命中 0」。判做对了:每个零旁边都有一个大于零的分母。
源案例:2026-09-21 某项目一次上线判据去查系统日志里的报错,而该服务的日志写在自己的文件里,好也是 0、坏也是 0,判据形同虚设,于是立了本条。

### 5.18 闸给了肯定答复,多问一句「它是拿什么算的」

name: ask-what-the-gate-computed-against
type: feedback
description: 一道闸说「已处理」「是最新」「已包含」「没问题」,准备据此放行时

1. 闸说「是」,追问它拿什么算的:日期、路径、单位、时区、编码、对着哪个提交。
2. 把这几样逐一与本次要判的对象对一遍;有一样对不上,这个「是」就不作数。
3. 闸的基准挂在会自己移动、或与本单无关的对象上的问题(当前头、别人正在改的工作树、仓库历史存量),按第 7 节 7.5 办。

**Why:** 肯定答复最不容易被怀疑,而它背后的一个时区或基准错了,整个答复就翻过来;闸给了绿灯,人就不会再去看它是怎么算的。闸的输出本身带着「对着什么量」的完整说明时,这条已被满足。
**How to apply:** 读闸的输出时,把「对着什么量的」补上再下结论。判做对了:闸的每个肯定答复都能说出它的比较基准。
源案例:2026-09-15 某项目一道日期闸用本机时区算出了昨天的日期,去查「今天处理了没有」,昨天的当然已经处理,闸给了肯定的绿灯,于是立了本条。

### 5.19 自检的期望值不能取自被检的那一方:拿同一个变量比,写坏了照样过,要从外面回读

name: self-check-baseline-from-outside
type: feedback
description: 给任何「写完再自己检查一遍」的动作(生成配置、改开关、落数据)写自检,或看到一道自检从来没红过时

自检拿来比的期望值,不能从被检的同一个变量、同一份文件、同一套默认值里取;否则写坏了,期望值也跟着坏,自检照样通过。要从一个独立的来源回读实际结果(运行中进程的实参、落盘文件里的那一行、对方系统查回来的值),再与事前定下的期望比。

**Why:** 这种自检的输出与真没问题的系统一模一样,返回码、日志都正常,只少打印一行;它比没有自检更坏,因为它让人以为已经核过。期望值与实际值确实来自两个互不依赖的来源时,这条已被满足。部署场景下的回读细则(五样回读、目标机脚本同步、开关被刷回、带上别人的提交)见第 7 节 7.19、7.21、7.24、7.25。
**How to apply:** 读一道自检时先问「它的期望值是从哪儿取的」;与被检写的是同一个变量,就改成从外部读。判做对了:每道自检都能指出期望值与实际值各自的来源,且两者不同。
源案例:2026-09-20 某项目一次上线没带保开关的参数,部署脚本整份重写配置,把另一扇窗 7 分钟前刚打开的功能开关刷回关,脚本的自检拿同一个默认值当基准照样通过,没有任何报警,于是立了本条。

### 5.20 结果比上次好得离谱,先怀疑量法;有利方向的异常与不利方向的一样是异常

name: suspiciously-good-numbers-check-method-first
type: feedback
description: 一次测量比上次好出几倍,或全绿、零缺陷、一次过,准备记功或放行时

1. 先问「这一版有哪一处改动能解释这个提升」;解释不了,就假设两次测量的取点或口径不同。
2. 即使判过,结论里也注明「引用此数须说明与上次测量口径可能不同源」,免得后人拿它当新基准。
3. 核验技巧:把别人报的数代入几条已知的真实公式,看它落在哪条曲线上;恰好落在某一条上本身就是强证据,不必让对方重测。

**Why:** 不加说明地记下一个口径不同的漂亮数,后人会拿它当新的验收基准,造出下一层错闸;只因方向有利就放过,等于只对坏消息设闸。两次测量出自同一脚本、同一环境、同一基点时,可以直接比。
**How to apply:** 验收回报里凡出现倍数级的改善,旁边写「能解释它的改动是 X」或「口径待核」。判做对了:没有一个倍数级改善在没有解释的情况下进了基准。
源案例:2026-09-06 某项目一次测量比另一张单在同一路径上测的快七倍,中间那一版却没有任何能解释提速的改动;09-14 另一次把下游转述的「约 73 秒」代入两条候选公式,精确落在「等待冷却」而不是「执行耗时」那条上,判定对方把两个概念说混了,而这两个数会导出完全相反的后续动作,于是立了本条。

### 5.21 静态估出来的「这处改动会打红几条」只是下界:同一个用例里第一条断言失败会挡住后面的

name: static-red-count-is-a-lower-bound
type: feedback
description: 估一处改动会连带打红几条测试、决定要改哪些断言时

1. 同一个测试方法里,遇到第一条失败就抛出,后面的断言一条都不执行;数出来的「红几条」是下界,不是全集。
2. 可靠的办法是真跑组合树,再把每个红行所在的整个测试方法通读一遍,列出同方法里依赖同一真源的全部断言;或按方法过滤,修一条跑一次,直到不再冒新的。

**Why:** 这是测试框架的结构上限,不是谁不仔细:两个人各自真跑,也只会看到同样的前几条。按下界去修,修完再红一轮,又多一次往返。框架支持一次报出全部失败的软断言时,这条可以放松。
**How to apply:** 任务书写「预期红 N 条」时注明「N 是下界,逐方法核」;执行方回报修了几处时,附上逐方法读过的清单。判做对了:修完之后真跑一次,不再冒出新的红。
源案例:2026-09-14 某项目一次键名合并,静态查找报「红 2 条」,真跑组合树也只报 2 条,真正要改的是 3 处,第 3 条被同方法里前一条挡住没跑到;当天两个独立角色各自真跑复现都只报 2 条,于是立了本条。

### 5.22 对齐检查先查自己最近立的闸有没有被悄悄削弱,再看对方点名交代的那几行

name: recheck-own-recent-gates-first
type: feedback
description: 一批活在免外部把关的安排下并进来之后,你要做对齐检查时

1. 检查顺序:①本岗位最近落地的闸有没有回潮(被重新写死、被绕开、被删);②跨岗位冻结件的字段有没有被改;③行为口径有没有被简化;④最后才看对方点名交代的行。
2. 结论「不用改」也写明查了哪几条、判据是什么。
3. 对方改得更好、但验收意见或任务书里还写着已不存在的东西时,当轮改掉,免得后来的人照抄出错。

**Why:** 别人的改动最可能静默破掉的,正是你最近立下、别人还不熟的闸;对方点名交代的那几行,恰恰是对方已经想过的。只看点名范围,等于只检查对方愿意给你看的东西。
**How to apply:** 维护一张「本岗位近期落地的闸」小清单,每次对齐先逐条过。判做对了:对齐记录的第一段是自己那几道闸的状态。
源案例:2026-09-08 某项目一批免外部把关的活删掉了本岗位刚判过的三个公开接口、改用真源表的新行,结果更好,但验收意见与任务书里仍写着已不存在的接口,后来的执行方照抄就会编译不过,于是立了本条。

## 四 · 证据与放行

### 5.23 「交了」只认进了版本库的提交,不认磁盘上有文件;只核「在不在」的闸证不了交的是这一版

name: delivered-means-committed-not-on-disk
type: feedback
description: 验收一张产物要入库的单,或核交付项齐不齐时

1. 交付项列出提交号,并要求推到权威远端;验收先看工作区状态(干不干净)与日志(分支是不是零提交),再核远端哈希与本地逐字相同。
2. 只比较已跟踪文件的差异命令,看不到未跟踪的新增文件;不能拿它判「是否已提交」。
3. 只核路径在不在的闸,对「改现有文件」的单会假过关,对「新建文件」的单反而可能拦错;这种闸要配一条内容级或提交级的核对。
4. 验「只改注释、不改逻辑」类的单,把两版的注释全部剥掉再逐行比。

**Why:** 没提交,就只存在于某台机器的某个目录里,到下一环并线时才被发现;浅层判据(磁盘上有、差异里有变化)与深层事实(真的入库、本体逻辑没被改)可以完全脱节。产物本就不入库(例如临时报告)时,这条不适用。
**How to apply:** 验收清单第一项固定为「状态、日志、远端哈希」三样;交付项路径写仓内相对路径。判做对了:每张放行的单都能从远端按提交号取出交付物。
源案例:2026-09-05 某项目一张单规格、帧数、自检、样张全核了,唯独没查提交状态,整个目录是未跟踪文件,到下一环并线时才发现;09-06 又因只比较已跟踪文件的差异,把一张新增目录完全没提交的单误判为只量未改而放行,于是立了本条。

### 5.24 证据只从唯一登记处取、亲自打开看;统计数和别处的拷贝都不作数

name: evidence-from-registered-source-opened
type: feedback
description: 验收要靠看或听判断的产出,或要引一份证据下结论时

1. 判「用户可感知」类产出,第一步打开登记目录里的原件,逐件记下看到了什么;统计指标只能辅助,不能代替打开。
2. 证据只从唯一登记的根目录取;工作树里的暂存件、过期的内嵌样本、别人转存的拷贝都不可信。
3. 判朝向、细节,放大或按外接框裁剪后再判,不看缩略图。
4. 继承上一级的结论之前,自己重新开一次原件。
5. 拿一种证据定阈值之前,先报它自身的测量摆幅;报不出摆幅的量,不当闸用。

**Why:** 数字能自洽地错,眼睛不会;多份拷贝让「看过了」也可能看的是错的那一份,被拉伸、标注相反的拷贝能把结论整个判反。证据链带自动哈希校验、且只指向登记的根目录时,第 2 点天然满足。
**How to apply:** 验收记录里每一条可感知类结论都附原件路径(在登记的根目录下);引用别处的文件前先比一次哈希。判做对了:所有结论的证据路径都在登记的根目录下,且附「看到了什么」的描述。
源案例:2026-09-04 某项目连续几轮只凭颜色统计判一个三维模型的面部异常,从没开图,没发现模型本身多出一处重复部位;后来三次引了非登记目录里的拷贝,其中一份被拉伸、标注含义相反,把朝向判反,换回登记目录后 179 份逐字节相同,结论完全反转,于是立了本条。

### 5.25 没有机器判据的交付(版式、视觉一致性),由设计者在最终产物上比对;执行方不为每一项截图,也不把截图当交付物

name: no-machine-criterion-designer-compares-final
type: feedback
description: 派或验收「按设计稿落地版式」「统一视觉风格」这类测试判不了的活时

1. 这类活全量测试全绿、读代码也看不出对不对;对不对,由设计者打开最终可运行的产物、与设计稿对照着判。
2. 执行方不为每一项截图,也不把截图当交付物;取证口径按 5.34。
3. 派单前做一份逐条台账:每个文件是什么、规定了什么、落地没有、归谁;用范围(文件、行号、页面)描述,不用动词描述。
4. 收口前扫一遍「建了但全仓没人用的变量、样式、组件」:这是漏做的机器指纹,执行方自己就能跑。
5. 设计稿与规格文档是与代码同级的交付依据,不是参考资料。

**Why:** 版式对不对没有任何机器判据;基础设施建好了与界面上真用上了是两件事,测试只能证明前者。派活用「换皮」这类动词,会被理解成迁移变量名,而不是按稿重排。设计者本来就要在最终产物上看,执行方再为每一项截图,只是把同一件事做两遍。项目为这类产出建了可靠的自动比对闸时,第 1 点可由它承担。
**How to apply:** 这类单的验收项写两样:逐条台账、零消费变量扫描结果;交给设计者的是能直接打开的最终产物。判做对了:台账每一行都有落地状态,扫描结果为零,设计者开产物时没有一处「还是老样子」。
源案例:2026-09-19 某项目一张界面换新样式的单全量测试全绿、代码审查也没报,9 个新样式变量全仓零消费,设计者亲自开图判定每个地方都还是老设计,整整返工一波,于是立了本条。

### 5.26 闸的检查条件与任务要求的做法在结构上打架时,是出题缺陷:执行方原样上报,不造假通过、不冒用别人身份改登记

name: gate-vs-taskbook-conflict-is-author-defect
type: feedback
description: 执行方照要求做完却过不了一道提交或交付检查,或检查条件与要求的工作方式对不上时

1. 触发后改不回的闸(一提交状态就前进、材料补不进去),提交前主动把它要查的每一项核齐;名字、路径逐字照登记的写,写岔了就改自己的去迁就登记。
2. 要求的工作方式与闸的检查条件结构性冲突(例如要求在隔离的目录里干活,闸却去主目录下找产物),是出题缺陷:执行方用自己的身份报阻塞,写明应改成什么,由出题方改。
3. 不许用假材料通过检查,不许冒用他人身份改登记。
4. 在错误的目录或环境下提交导致的「找不到」,是环境造成的假阴性,不记执行方的账。

**Why:** 造假通过一次,这道闸从此不可信;冒用身份改登记,责任链就断了。结构性冲突只有出题方能消,执行方绕过去,只会把缺陷藏起来留给下一张单。闸的检查条件与任务要求由同一处生成时,这类冲突不会出现。
**How to apply:** 开工先把闸要查的项逐条抄下来,与要求的工作方式对一遍;对不上当场报,不等到提交那一刻。判做对了:每一次被闸拦下,记录里都是真实材料与真实身份。
源案例:2026-09-05 某项目一张单因漏写一项证据说明被提交检查拦下,总监补一句话后一次通过;次日另一张单要求在独立的工作目录里干活,交付登记的却是主目录下的路径,活做完了结构性地交不了,只能报阻塞请上级重登路径,于是立了本条。

### 5.27 代核报告只报事实与疑点、不写判定;终审人只亲核几样决定性的事

name: delegated-check-facts-final-judge-decides
type: feedback
description: 让别人或子代理代跑一次验收,或自己接手一份代核报告准备定放不放行时

1. 验收拆两半:机械可重复的部分(构建、批量测试、加总核对)可以委托,结果行全盘采信;决定性的部分(关键事实变没变、责任归谁)终审人自己过。
2. 代核方只报事实与疑点,不写「通过」「不通过」,不落最终裁决。
3. 终审人亲核三样:权威分支与交付编号是否仍未变;报告里「对不上」的疑点中会影响判定的那一条;收尾的硬性检查项是否齐全。

**Why:** 机器面的重跑是验收里成本最高、最不需要终审人重做的部分;判定靠的是决定性事实与责任归属,这两样一旦也委托出去,终审就成了盖章。与第 2 节 2.17(施工方的自述不采信)的差别:那条管「施工方说做完了」怎么对待,本条管验收本身怎么切分。验收本身只有机械部分时,整份可以委托。
**How to apply:** 派代核时写明「只报事实与疑点、不写判定」;收到报告只读疑点段,再亲核三样。判做对了:终审记录里有三样亲核的原文。
源案例:2026-09-14 某项目设计者安排的代核交接实测成立:代核报告准确指出任务书本身把判据方向写反了(应为 11 而非 86),接手方复核后确认是出题错误而非执行错误,省下了整轮机械重跑,于是立了本条。

### 5.28 放行、作废、报「对方卡住了」之前,当场重查一次实时状态;几分钟前的列表不作数

name: recheck-live-state-before-gate-decision
type: feedback
description: 要作废一张单、改派、放行,或回答「某某是不是卡住了」时

1. 同一串操作里先查一次目标的当前状态,再动手;列表快照几分钟就过期,从可领取到被领取开工往往只要几十秒。
2. 已被领取的不作废,改用实时对话通道通知当事人,或另开续单、在原单上追加说明。
3. 回答「对方卡住了吗」之前先重查,并问自己「它是不是在等我处理」;是自己的积压就如实说。

**Why:** 通知通道与状态查询是两条异步的流,中间必有时间差;拿旧快照作废,等于把正在跑的活抽掉,执行方要到交付时才发现;拿旧快照报「对方卡住」,是把自己的积压说成对方的问题。状态由单一进程同步维护、读写原子时,这条风险才小。
**How to apply:** 作废与改派命令前面固定紧挨一条状态查询;报别人卡住时附上当场查询的时刻。判做对了:没有一次作废落在已开工的单上。
源案例:2026-09-05 某项目一张单在几分钟前的列表里显示未领取,据此被作废重开,其实它已被领取、并按旧书做了一项不可逆的归档;09-08 又有人拿本轮开头的旧扫描回答「对方还没交」,而对方早已交付、单已在等他验收,于是立了本条。

### 5.29 作废与阻塞不会推送给正在跑的执行方:长工序每段做完、任何不可逆动作之前,自己回查任务还在不在

name: executor-recheck-before-irreversible-step
type: feedback
description: 执行一个耗时长的工序,或即将推送、归档、切状态、登记资源这类做了收不回的动作时

1. 控制面上的作废、阻塞是单向的,不会通知在跑的会话;查询命令照常应答,执行方会一路做到底才发现单早没了。
2. 每完成一段、每个不可逆动作之前,重查一次任务状态。
3. 发现已失效立即停手:不覆盖替代任务的产物,把已完成部分另存并说明,上报。
4. 交接记录写清副作用与残留(新建的资源、挪过的状态、终止的进程),分不清就如实说分不清。

**Why:** 不可逆动作恰恰常被排在最容易忘了查状态的收尾阶段;一次作废晚到一分多钟,就可能让替代方案开工时数据已不可复现。控制系统对在跑会话有硬通知时,这条可以放松。
**How to apply:** 任务书在每个不可逆步骤前加一行「先查状态」;子代理的收尾清单第一项是查状态。判做对了:没有一次推送、归档发生在单已被作废或阻塞之后。
源案例:2026-09-05 某项目一天三例:归档动作发出 98 秒后单被作废,替代方案开工时数据已不可复现;一次约 12 分钟的完整基线跑完才发现单早被阻塞;另一执行方按阻塞令本不该推送,却到收尾才查状态,推送已经发出,于是立了本条。

## 五 · 把关留几道、验证做多少

### 5.30 每道检查先问它为谁而设:价值只建立在「有个只能看、不能自己改代码的把关人」之上的,把关人一撤就整体撤

name: drop-checks-that-served-a-removed-reviewer
type: feedback
description: 流程里撤掉了一道外部把关,而任务书与模板里还留着一堆给把关人看的检查时

1. 逐项问:这道检查是为了发现问题,还是为了向一个外部把关人证明自己没做错。
2. 后者的价值全在「有个只能看、不能自己重写代码的把关人」这个前提上;前提撤了,这类检查(重复自证的测试、给把关人读的长串收尾题、为方便翻看而做的证据加工)整体撤,一样不留。
3. 撤的只是重复自证,不是质量:最终组合树的构建加全量测试一步不少(见第 2 节 2.16),收尾只留三问(见 2.19)。
4. 责任收到谁身上,谁的那一道最终验证就不能省;撤了外部把关又省了这一道,等于没有闸。

**Why:** 检查有成本,成本由执行方的额度出;为已不存在的读者做的检查只剩成本。与第 2 节 2.7 的差别:那条讲派单形态(一张需求单交给 0 号窗),本条是判任何一道检查去留的通用问法。外部把关恢复时,这类自证检查要随之恢复。
**How to apply:** 撤一道把关的同一天,把模板与在跑的书里给它准备的检查逐条列出,按第 1 点的问法分成「撤」与「留」。判做对了:留下的每道检查都能说出它要发现什么问题。
源案例:2026-09-15 某项目撤掉外部把关后,执行方八成额度仍烧在给把关人看的重复自证上,设计者指出保持这三样任务就不可能完成;次日统计 182 张任务书里一百多张要求这类自证,通用头占近六成,于是立了本条。

### 5.31 撤一道自证类检查,同一笔保住一道能看到真实行为的检查;撤什么按模块分清单

name: cut-self-proof-keep-real-behavior-check
type: feedback
description: 为一类模块定验证口径、准备砍掉一批检查时

1. 总纲一致、清单按模块分:先问这类模块原有的检查里,哪一道是唯一能看到真实行为或真实产物的,那一道保住,其余只为自证的才撤。例如某项目:后台类由最终组合树的全量测试兜底;界面类撤了单元测试,就必须保留真实环境里走一遍(单元测试看不到渲染那一层);素材类不再为归档加工证据,但保留母版完整留存与只从登记目录开原件核对。
2. 减测试与加真实验证是一对,只减不加等于裸奔。
3. 审美判断与规格判断交给不同的角色,不压在同一个人身上。
4. 写撤销清单时,反查每个被撤的词在同一份书的别处是不是作为要求出现;同一个词一处是要求、一处是禁令,会让执行方怎么做都被说错。

**Why:** 不同模块原有的验证方式能证明的东西不同,一刀切会把某类模块唯一能看到真实行为的那一道也砍掉;措辞撞车是撤销清单最常见的副作用。模块类型单一的项目只需要一张清单。
**How to apply:** 每类模块的任务书模板里写一节「撤了什么 / 保了什么」,两栏都不空。判做对了:每类模块都至少有一道能看到用户真实所见的检查。
源案例:2026-09-15 深夜某项目设计者当场定验证口径按模块分;09-16 同一张任务书里一个表示「重复跑几次」的词既是采样测量的要求、又出现在测试禁令里,双方对不上,执行方被质疑做错,查明是措辞撞车,于是立了本条。

### 5.32 叠起来的把关层按「抓到了什么」留撤:第二道只抓得到文书小错,就并成一道事后审计

name: gate-layers-earn-their-keep
type: feedback
description: 流程里对同一张单有两道以上的外部把关,或准备再加一道时

1. 每一道把关层都统计它这段时间抓到了什么:退回了几张,退回的是活没做好还是文书小错。
2. 抓到的多是文书小错、同一批数又在几份件里各抄一遍时,把几道并成一道事后审计:另起、用顶档模型、首行固定几个计数(格式见第 2 节 2.3)。
3. 用户看得见的面,或审计报了漏做,才临时加一次独立的核验。

**Why:** 每多一道把关,就多一轮排队、多一份重复文书;一道把关层的价值,只在它抓到了别的层抓不到的东西。与第 2 节 2.3 的差别:那条讲验收权归谁,本条讲把关层数按什么定。刚上线的新流程还没有统计数据时,先保留两道跑一段,再按本条收。
**How to apply:** 每个阶段末把各把关层的退回记录拉一次,按「活 / 文书」分类;连续一段抓不到「活」的层提议合并。判做对了:剩下的每一道把关层都有它独有的抓获记录。
源案例:2026-09-25 某项目流程扫盘:六份事后审计无一次判返工,原先的两道把关抓到的多是文书小问题,同一批数在收口报告、审计件、决策草稿里各抄一遍,于是立了本条。

### 5.33 贵的验证只在被量的东西可能变了时重跑:首次上真链路或相关结构大改才跑,其余写「沿用某次」

name: rerun-expensive-checks-only-on-change
type: feedback
description: 给任务书写判据时想顺手加一条大规模基准、长时压测、占人设备的实机测,或上一轮刚跑过同一项时

1. 高成本的验证(大规模性能基准、占用设计者设备的实机测)只在首次上真链路、或与该指标相关的结构大改时跑一次。
2. 返修、换装、纯逻辑修改不重跑,判据里写「沿用某次的结果」并注明是哪次。
3. 确要重跑,先写清与上次相比变了什么。
4. 判据里的每一条都能说出是谁要求的;是自己按条款加的,先问一句有没有必要。
5. 不占任何人环境、可无人值守的自测不受此限。

**Why:** 已经验证过、又没有实质变化的高成本验证,重复安排是纯浪费,尤其当它要占设计者本人的设备与屏幕;按条款机械地往每张书里加,没人会回头问它还要不要。被量的指标已经贴着预算边缘、对小改动也敏感时,要放宽「需要重跑」的判定。
**How to apply:** 写高成本判据前先查上一次是哪天、对哪个提交跑的、之后动没动过相关结构。判做对了:同一项高成本验证,在两次结构改动之间不出现第二次。
源案例:2026-09-23 某项目一张进行中的单的任务书里又写了一条「500 实例不低于 60 帧」的判据,设计者指出配套的样例早已测过这一规模,追问是谁安排每一轮都测试,查明那条判据是总监按章程条款自行加进去的、并非他要求,于是立了本条。

### 5.34 证据的量跟着「谁看、看了能不能判」走:看的人会拿最终产物自己验时,整批只留一张总览

name: evidence-volume-follows-its-reader
type: feedback
description: 给任务书定取证要求,或执行方准备为每一处改动都启动一次应用去截图时

1. 静态可核的判据(文件列表、字节数、哈希、版本库查询、针对性测试)永远是主判据,不因截图减少而减少。
2. 截图类证据只给要看的人看,不替代判据;看的人本来就会拿最终可运行的产物自己验时,整批只由收口环节取一张主界面总览。
3. 前置条件本该实机验证而暂不满足时,写清推到下一轮,不当场硬凑证据。
4. 真要截图,放在不占用验收人正在使用的那台设备的环境里跑,并写明失败时不许退回到他的设备上重试。

**Why:** 每处改动都启动应用截图,时间成本极高,截图链路本身还可能有缺陷;设计者查看证据消耗的是他自己的注意力与额度,而他本来就会在最终交付物上自己验。没有人会去看最终产物(纯后台、无人验收)时,截图才值得多取。
**How to apply:** 任务书的取证节写「本件不截图,判据见静态项」;收口节写「整批一张总览图」。判做对了:一批活的截图不超过一张,且每条判据都有静态证据。
源案例:2026-09-21 某项目先定「免客户端取证,整个流程最多 1 次」,当夜设计者又说取图不重要、浪费他的 token,一个批次取一张大界面就可以,把取证口径收成整批一张,于是立了本条。

### 5.35 评一批活的质量,用人人能独立复现的机器指标,再看三个行为信号

name: audit-a-batch-by-reproducible-signals
type: feedback
description: 要评价一波或一批活做得好不好,或要给执行方、模型打分时

1. 六条速查,每条都有唯一答案:①提交笔数与归属对不对,有没有混进别批的提交;②提交卫生:日志、二进制、临时文件为 0;③自报的增删行数与独立统计对不对得上;④全量测试的自报数,派子代理在同一基线上复跑一遍;⑤一个能反映「合并时是否悄悄丢了改动」的不对称指标(例如两种语言文件的条数差),拿基线值与合并后比;⑥上线积压了几笔。
2. 三个行为信号:有没有发现并改正自己立错的判据;红了之后是按判据真修,还是删测试、加跳过、把断言改成恒真;有没有如实标注「未验证」、主动承认自己的失误。

**Why:** 「质量如何」很容易滑成印象分;六条每条都能对得上或对不上,三个信号检的是并线纪律与如实报告,这两样最难教,也最决定一波成败。评价对象只有单个改动时,六条里的笔数与积压两项可省。
**How to apply:** 评一波活就贴六条的原始数与三个信号的证据行,不写形容词。判做对了:换一个人按同样的命令跑,得出同样的六个数。
源案例:2026-09-20 某项目用这六条加三个信号核一批活,条条有唯一答案、全部通过,其中那批活主动改正自己一条在基线上就不成立的判据,被单独记为行为信号的加分项,于是立了本条。
