# 7 · 并线铁律

本节收:多扇 AI 窗、多个子代理并行改同一批仓时,派单前怎么切属主才不撞、闸的基准怎么定、共用检出上哪些 git 动作会静默毁掉别人的活、解冲突与重建组合树的规矩、一笔改动凭什么算能进主干、怎么推送,以及项目有线上服务时怎么部署与回读。读法:派一批并行的单之前、并线解冲突之前、推送之前、部署前后,翻对应那一组——7.1~7.4 派单前切属主;7.5~7.6 闸的基准;7.7~7.8 共用检出与工作树;7.9~7.12 解冲突与组合树;7.13~7.16 能不能进主干;7.17~7.18 推送;7.19~7.27 部署与回读,只在项目有线上服务时适用,没有线上服务的项目整组跳过。

## 一 · 派单前切属主

### 7.1 并行的单按「改不改同一批文件」分族,不按主题分

name: split-parallel-work-by-file-overlap
type: feedback
description: 要把一批缺陷或需求拆给几扇窗、几个子代理并行做,正在写分族表或属主表时想起

并行的单怎么分族,只看它们改不改同一批文件,由子代理逐文件实测决定,不凭主题相近去猜;分族表附一张「族 × 文件」重叠表,零重叠也明写「零」。
1. 写分族表之前先派子代理量每个族的真实文件面(要改的文件清单,含测试文件与登记文件)。
2. 分族理由只许写「因为改同一批文件」;主题相近而文件不交的可以分开并行,主题不同而文件相连的必须同族或排先后。
3. 同期别处在跑的单也进重叠表(见 7.2)。
4. 已经写进任务书的错分族当场改掉,不让执行方照做。

**Why:** 并行最贵的事故是两族改同一个文件,解冲突时一侧的改动被静默吃掉却全绿(见 7.10);合不合得拢由文件面决定,主题只是人脑里的归类,常被一个公共文件串成一片。下一批还没派出去时重新分族是免费的,派出去之后就是返工;只有各族天然落在互不相交的目录里时,这一步才可省。
**How to apply:** 派单前先要一份「族 × 文件」表;看到分族理由写的是「同属某功能」就退回重量;判做对了的标志是重叠表里每个共同文件都能指出唯一属主。
源案例:2026-09-20 某大型多人在线项目凭「主题相近」把一批缺陷分成三族,派子代理逐文件实测后全部推翻:一个公共文件把几个不同主题的族串在一起,真实分族与主题几乎不对应,还漏了与另一张在跑单共用同一个文件的交集,于是立了本条。

### 7.2 切属主要把同期在跑、还没进主干的单也量进去

name: ownership-table-includes-running-work
type: feedback
description: 一次开几扇窗、切文件属主表时想起;只量新单之间的交集,会漏掉同期在跑、还没并进主干的单

切文件属主时,交集要量三类来源:本批新单之间、同期在跑还没进主干的单已改的面、已经验收但还没并的支;在跑的单还没建工作树时,读它的任务书全文,不看看板上的「交付项」摘要。
1. 从主干新起的支看不见在跑单占住的面,只有派单方同时知道两边。
2. 看板上的「交付项」是交付时要核的产物清单,不是改动面清单,两者可以差一个数量级。
3. 拆单不会自动消除交集;拆完重量一次,细到文件里的段。
4. 判能不能并行,看每个共同文件能不能定出唯一属主,不数共同文件有几个。

**Why:** 属主表只覆盖新单,等于假定主干就是全部现状;在跑的单正在改的东西不在主干上,新支撞上它时两边都以为自己是唯一属主。所有在跑的单都已并进主干、没有未并的支时,这条才可省。
**How to apply:** 切属主前先列出同期在跑、未并的单,逐张读任务书里的改动面;属主表加一列「来源:新单 / 在跑 / 已验收未并」;判做对了的标志是表里出现过在跑单占住的文件,或明写了「在跑单交集为零」。
源案例:2026-09-09 某大型多人在线项目一次开五扇窗,属主表只切了五窗之间,写完才发现同期一张在跑、未并的单已占住 4 个文件和 5 个多单共用的登记文件,幸好都还没派出去;09-19 又撞第二种形态:一张单看板上的交付项只有 4 个文件,任务书写明的真实改动面却是 78 个文件加 12 个连带文件,照交付项切属主表必然漏,于是立了本条。

### 7.3 写「只许碰某一段」之前,先核那一段是不是一个独立的代码结构

name: verify-owned-segment-is-a-real-unit
type: feedback
description: 属主表想细到「某文件只许碰某一段」、让两张单各碰同一文件的不同位置时想起

属主表写「某文件只许碰某一段」之前,先派子代理核那一段在语法结构上是不是独立的(一个完整的函数、方法、类或配置块,有明确的起止行);它若只是别人方法体里的几行,就改写成「只许动自己那一句调用及紧邻语句,不许重排该方法体的其它语句、不许改签名」。

**Why:** 属主表可以细到段,但那个「段」可能是凭描述想象出来的;两单「各碰各的段」在文件面上根本不成立时,编译、测试、git 没有一道会响,只能靠出题人自查。文件天然按独立单元拆开、一单只碰整文件时,这条不需要。
**How to apply:** 子代理回报写「该段在 <文件> 第 a~b 行,属于 <哪个结构>」;任务书不写死行号,让执行方现算;判做对了的标志是每个「只许碰某段」都能指出一个有起止行的独立结构。
源案例:2026-09-20 某大型多人在线项目属主表写「某文件只许碰某一段」,实测那一段其实是另一个方法体收尾的最后一行,两张单「各碰各的段」的切法从文件面上一开始就不成立,实际处理是把那句许可改写成「只许动自己那一句调用及紧邻语句」,于是立了本条。

### 7.4 全仓单调递增的号必须有属主;两支抬到同一个值,所有常规闸都抓不到

name: global-monotonic-number-needs-owner
type: feedback
description: 同一批并行的单里有人要抬持久化格式版本号、迁移号、协议号、编号段这类全仓单调递增的号时想起

同一批并行的单里,全仓单调递增的号(持久化格式版本号、数据迁移号、协议号、编号段)必须在属主表里有唯一属主;两条支各自把它从 N 抬到 N+1、却对应两种不同的含义,是编译、测试、git 冲突都抓不到、部署那一刻才炸的冲突。
1. 派同一批单前,列出本批可能动到的这类号,每个号定唯一属主;不靠「主干是 N 我就占 N+1」的默认约定。
2. 任务书里凡涉及这类号,要求执行方现查一遍「同期还有谁在动这个号」,并在收尾写明占用理由。
3. 发现两支占了同一个号时不判谁错,只能二选一:同批并、同批部署;或后并的一方改用下一个号,另派一张适配单。

**Why:** 这类冲突在 git 里只是赋值那一行「几乎一样」的小冲突,随手一解就过;合并后代码自洽、测试全绿,错在运行时对存量数据的解释上,字节没坏,校验和也拦不住。项目没有持久化格式、没有对外协议时,这条只管编号段。
**How to apply:** 属主表固定一节「全局号」;并线前搜本批各支对这类常量的改动,命中两支以上就停;判做对了的标志是每个被改的全局号在属主表里都只挂一个名字。
源案例:2026-09-10 某大型多人在线项目两张并行单各自把同一个持久化格式版本号从 6 抬到 7,对应两种不同的二进制布局,git 只在赋值行报了一处小冲突、随手解掉,合并后测试全绿;部署后按「版本号 ≥7」去读并不存在的字节,服务一加载就崩,根因是属主表没给这个号指定属主,于是立了本条。

## 二 · 闸的基准

### 7.5 闸的判据不许挂在会自己移动、或与本单无关的对象上

name: gate-must-not-track-moving-target
type: feedback
description: 给并线、交付写判据(拿什么当基准比、要求「零命中」「零差异」)时想起;判据两端若有一端自己会动,闸就不可信

闸的判据不许挂在会自己移动或与本单无关的对象上:主干的当前头、开工时钉死的老基点(又同时要求「交付前先合主干」)、别人正在改的活工作树、整个仓库的历史存量。判据要能自证:两端取同一个钉定的提交,或都在同一棵合并树里现算。
1. 「本单改了什么」只用 `git diff --name-only $(git merge-base HEAD <远端>/<主干>) HEAD` 现算。
2. 新鲜度(落后主干几笔)另走只报不拦的提示,不进判据。
3. 怀疑闸挂错对象时用三数对比:同时量「整棵树 / 基点 / 本支新增」;基点等于整棵树,说明命中与本单无关;本支新增为零,说明执行方没欠账;处置是把判据改成「本支新增为零」。

**Why:** 这类闸绿不说明对、红不说明错,只说明两个各自在动的东西此刻恰好对上;更坏的是它会绿着把错的基准钉住,给人一种「已被保护」的错觉。两端都是冻结对象(例如都是发布标签)时,这条不适用。
**How to apply:** 写判据时逐端问一句「这一端明天会不会自己变」,会变的换成钉定提交号或合并树现算;判做对了的标志是同一个提交无论哪天跑、谁来跑,闸的结论都一样。
源案例:2026-09-09 某大型多人在线项目同一天撞上三种「闸挂在会动的东西上」:镜像对比拿主仓当前头当基准,执行方做完主仓已前进;固定老基点全量对比与「交付前先合主干」两条要求数学上不能同时满足;钉值测试读另一个仓的活工作树;09-14 又撞第四种,仓库卫生闸要求「零命中」,命中的 1306 处全是仓库历史存量,判据永远满足不了,代价落在验收方头上,于是立了本条。

### 7.6 新加钉值类检查,并线前把钉值和真源当前状态逐条比一遍;它变绿只证明自洽

name: pinned-value-gate-check-current-truth
type: feedback
description: 新加一道「钉住真源哈希、字节数、行数」的检查并准备并线时想起;这类检查一直全绿、没人怀疑时也想起

新加一道钉值检查(把真源的哈希、字节数、行数写死在检查里)时,并线前把写死的钉值与真源在远端主干上的当前状态逐条比一遍;检查变绿只证明「被钉的文件与钉值自洽」,不证明「钉值等于当前真源」。

**Why:** 钉值若取自某张单交付那一刻的真源,而真源之后又往前走了,检查的名字就开始说谎:它把「已经落后」钉成「正确」,以后真漂了也报不出来,比没有这道检查更坏。钉值由脚本在并线时从真源现算、不靠手写时,这条自然满足。
**How to apply:** 钉值的来源写「真源当前头」,不写某个具体单的提交号;并线前现算一遍真源的值与钉值逐条比,不一致就把正确的完整值算好一并交给对方,让对方少走一轮;顺手做一次全量比对并留档;判做对了的标志是能拿出一张「钉值 = 真源现值」逐条相等的对照。
源案例:2026-09-08 某大型多人在线项目新加一道「镜像文件哈希必须等于真源钉定值」的检查,合并后全绿,其中两个文件其实已与当前真源不等,因为真源在这张单交付之后才并进主干,检查反把「镜像已落后」钉成了正确状态;顺手全量比对,四分之一的镜像文件与真源不一致,现有检查一条都没报,于是立了本条。

## 三 · 共用检出与工作树

### 7.7 多扇窗共用一份检出时,有六个 git 动作会静默毁掉别人的活

name: shared-checkout-six-git-hazards
type: feedback
description: 在几扇窗、几个子代理共用的一份检出上要跑 reset、commit、amend、push、worktree add 之前想起

多扇窗共用同一份检出时,reset、commit、amend、push、建临时树这些日常 git 动作都会静默毁掉别人的活,下面六条一律守:
1. `reset --hard` 前先 `git status --porcelain`,有不是自己的未提交件就不跑,改用 `merge --abort` 或挪到独立的临时树;要回退只用 `reset --mixed`(只动分支与索引,不碰工作树)。判断「有没有人在这份检出上干活」,先按源码扩展名过滤再数,不看 status 的原始行数(编辑器生成的缓存文件能常年堆上千行)。
2. commit 一律带路径(`git add -- <路径>` 逐个加),不用 `-a`、`add -A`,否则会卷走别人已暂存的文件。
3. 共用分支上不用 `--amend`:会顶掉别人刚提交的那一笔。
4. push 被拒,先看 HEAD 是不是自己那一笔,不直接 reset 或 rebase;reset 会把别人已提交、未推的一笔从分支上摘掉。
5. 建临时验证树用提交号:`git worktree add <路径> <提交号>`(游离 HEAD),不写分支名。
6. 合并在临时树里做完、核完,共用检出上只做最后一次真并。

**Why:** 共用检出不是一个人的;这些动作都不报错也不显眼,内容一件不丢,丢的是「谁为什么改」,或自己那一笔悄悄从分支上消失。写了分支名的临时树尤其隐蔽:分支是共享资源,临时树里一跑 merge,共享分支当场前进,共用检出的索引与工作树还停在旧头,status 会把整批新文件显示成「已删除」,像有人删了东西。一单一棵独立工作树、没有任何共用检出时,这条才可省。
**How to apply:** 把这六条写进 0 号任务书通用模板的并线节;已经把分支签进临时树的回退法:临时树 `git checkout --detach` 让出分支,共用检出 `git reset --mixed <原头>`,核实后再真并;判做对了的标志是每一笔提交的文件清单只含自己点名的路径。
源案例:2026-09-08 某大型多人在线项目为「把主干挪回去重做一次合并」在共用主检出上跑了 `reset --hard`,连带清掉两处未提交的修改,事后查明那是另一个角色推进主干后残留的旧文件、不是真在做的活,纪律照留;09-14 多窗共用的办公文本仓一天撞三起:普通 commit 卷走别人暂存区的文件、`--amend` 顶掉别人刚提交的信息、reset 把别人已提交未推的一笔从分支上摘掉;09-15 又有人建临时验证树时写了分支名,共享主干被当场推进,共用检出把整批新文件报成「已删除」,前后两次独立撞上,于是立了本条。

### 7.8 给别人长期用的本机服务或长跑进程,起在它自己的工作树上

name: long-running-service-own-worktree
type: feedback
description: 要在本机起一个供别的任务长期使用的服务、测试夹具或长跑探针时想起;构建突然全报「文件被占用」时也想起

给别的任务长期用的本机服务、测试夹具、长跑探针,起在它自己独立的工作树上,不和用来并线、构建、跑测试的工作树共用。

**Why:** 长跑进程会一直持有它加载的构建产物,同一棵树再构建时全部报「文件被进程占用」,看起来像构建坏了,构建工具的重试也救不回来;这不是代码错,是编排错。进程不加载、不锁住构建产物时,这条可以放宽。
**How to apply:** 这类进程的工作树单独命名(名字里带用途),任务书写明路径;构建报文件被占用时,先看报错里点名的进程号与路径,是不是这棵树里起着的常驻进程;判做对了的标志是并线用的树里没有任何常驻进程。
源案例:2026-09-08 某大型多人在线项目把一个供别的任务使用的本地夹具服务起在了正在跑并线与测试的工作树上,服务进程一直占着生成的程序库,随后四个工程的构建全部报文件被该进程锁定、重试 10 次后失败,报错里点名了占用的进程号与路径,不是代码错,只能把服务挪到独立的工作树,于是立了本条。

## 四 · 解冲突与组合树

### 7.9 git 报零冲突只说明两边没改同一行;语义冲突落在测试不覆盖的路径上,git 和测试一起沉默

name: zero-conflict-is-not-mergeable
type: feedback
description: git 合并报零冲突、准备据此认定「能合」时想起;一支要退役或改签名一条旧链、另一支可能还在用它时尤其要想起

git 报零冲突只说明两边没改同一行,不说明合起来编得过、跑得通:一支删了另一支还在引用的常量、改了字段能不能为空,git 一声不吭;冲突点若落在测试不覆盖的路径上(只在某个编译开关下才编进来的代码块、调试专用的驱动、测试辅助工具),测试也一起沉默,只有真把那条路径构建出来才抓得到。

**Why:** git 只比文本行,测试只走它覆盖的路径,两者的盲区恰好叠在「不常编译、不常运行」的代码上;而「零冲突」这三个字最容易让人跳过构建直接下结论。项目没有条件编译、调试专用代码和测试辅助工程时,盲区只剩前半句说的语义冲突。
**How to apply:** 零冲突不作结论,合并结果照样构建,且构建要覆盖所有编译开关组合与辅助工程;一支要退役或改签名一条旧链时,先派子代理到上面三类盲区里搜调用方,回报附搜索模式与命中数;判做对了的标志是回报写的是「构建通过(含哪些变体)」,而不是「零冲突」。
源案例:2026-09-08 某大型多人在线项目两支合并 git 零冲突,一支删了另一支还在引用的常量、又改了字段可空性,组合树构建报 28 个错;09-14 又有一次冲突点恰好落在只在某个编译开关下存在的代码块里,整套测试一条不响,只有产品的真实构建抓到,于是立了本条。

### 7.10 行并集只能用在每行独立成条、两边都只追加的纯行式清单上;一侧有删除或改正,它会把删掉的、改掉的原样装回来

name: union-merge-restores-deleted-lines
type: feedback
description: 解追加式登记文档、逐行清单这类纯行式文本的冲突,想「两边都留」(行并集)时想起

行并集(两边的行都保留)只在两个条件同时成立时可用:文件是每行独立成条的纯行式清单(追加式登记文档、逐行清单),且两边相对合并基点都只是追加;结构化文件(键值文件、JSON、语言包、工程文件、CSV、多行初始化写法)不在此列,一律不取行并集。纯行式清单上只要有一侧删了行或改正了旧内容,并集就会把被删的、被改掉的原样装回来。
1. 解之前先数两侧相对合并基点的删除行数;都是零才能取并集。
2. 删除行非零,按「谁改的归谁」逐行解:支上删的真删,支上改的取支上的值,支上增的追加,不是两侧都留。
3. 多支共改的文件用脚本逐行核存活:逐支算出相对基点的新增行与删除行,到合并结果上核「新增的都在、删除的真没了」,有差异就逐条对上是不是有意的替换。
4. 解完按字面回头核:错误写法出现 0 次、正确写法出现 1 次;判据是内容在不在,不是测试绿不绿。

**Why:** 并集这个动作只表达「两边都加了东西」;一侧是删或改正时语义就反了,被删、被改掉的内容会被当成对方的新增留下。常规测试抓不到,登记类文档根本不进任何断言;肉眼看 diff 也抓不到,看到的是「两侧都保留了」这个看似正确的结果。两侧确实都只追加时,并集是对的。
**How to apply:** 任务书的解冲突节写明「纯行式清单先数删除行,非零不许并集;结构化文件一律不并集」;把逐行存活核对做成随手能跑的脚本,回报写「多支共改文件 N 个,丢失 0、复活 0」;判做对了的标志是被删的行、被改正的错句在合并结果里搜不到。
源案例:2026-09-15 某大型多人在线项目两单同往一份追加式登记文档的尾部写,其中一单其实是在改正另一单早先写错的一句数据,另一单的支是从改正之前的主干分出去的、还带着原错句,两侧都留就会把错句带回主干且测试全绿,那次没出事只因 git 恰好把那一行判给了改正方;09-20 并线子代理对 11 个多支共改文件逐行核存活,并线刚完成时丢失为零,后续 3 行差异逐条对上全是有意的替换,于是立了本条。

### 7.11 合并树里的生成物不手解冲突:退回主干版,在合并树上重跑生成脚本

name: regenerate-artifacts-not-hand-merge
type: feedback
description: 合并树里撞上由脚本生成的文件(打包清单、汇总 JSON、索引)冲突,或一条押了很久的支终于要并时想起

合并树里凡是由生成脚本产出的文件,冲突一律不手解:先退回主干上的版本,再在合并树上重跑一次生成脚本,由脚本产出最终文件。
1. 并线前先分清支上改动面里哪些是真源、哪些是生成物;只有真源才解冲突。
2. git「看似自动合并成功」的生成物同样不可信,一样重跑。
3. 重跑后把产物解析成对象逐字段对账,不看行数(这类产物常常整份一行);不该被本次改动波及的部分必须零差异,否则就是把别人此前的改动静默退回去了。

**Why:** 手解生成物等于手改构建产物;即使编得过、闸也绿,下一个人一重跑生成脚本就会得到不一样的文件,那才是真正的漂移。生成物的属主是生成脚本,不是任何一张单;支押得越久,并线那天越不是在解冲突,而是在重新生成。生成物不进版本库时,这条不适用。
**How to apply:** 并线清单固定一步「列生成物 → 退回主干版 → 重跑脚本 → 逐字段对账」;押单时就告诉交付方「并线那天会重新生成」;判做对了的标志是生成物的最终内容等于在合并树上重跑脚本的输出。
源案例:2026-09-15 某大型多人在线项目一条押了很久才放行的支并线那天,改动面 4 个文件里只有 1 个是真源(一行 CSV 数据),另 3 个全是生成物;真源之间有真冲突,另一个 git 自动合并成功的生成物其实是不能信的中间状态,只能退回重新生成,于是立了本条。

### 7.12 一个仓的目录是另一个仓的镜像时,两仓配对的改动同批并,合没合逐仓核

name: mirrored-dir-paired-merge
type: feedback
description: 一个仓里有一块目录是另一个仓某目录的逐字节镜像,要并碰到这块的支,或要判一张跨仓单「并完没有」时想起

一个仓的某个目录是另一个仓某目录的镜像时,碰到镜像目录的支,并线前先到源仓找到配对的那一笔,两仓同批并;判「并完没有」逐仓核祖先关系与内容,不信看板上一个笼统的「已合并」。

**Why:** 镜像是隐式的强耦合,现有检查往往只覆盖一小部分镜像文件、只核单仓自身一致(落后的镜像自身照样自洽),跨仓漂移可以长期无声;只改文档的跨仓单连测试都不触发。两个仓合成一个、或镜像改成构建时自动从源仓拉取之后,这条作废。
**How to apply:** 并线前对每条待并支跑一次「改动碰没碰镜像目录」(`git diff --name-only <基点> <支头> -- <镜像目录>`),命中就去源仓找配对支;跨仓的单收口时逐仓写「<仓> 在 <提交号> 上已并」;判做对了的标志是镜像目录与源目录在两个仓的主干头上逐字节相等。
源案例:2026-09-06 某大型多人在线项目一笔改动只在镜像所在的仓并了,源仓没有配对更新,两边出现字节差,两道现有检查都照不出(一道只扫几个关键词、扫不到镜像文件,一道只核单仓自洽);09-14 又一张跨两仓的单看板只记了一条「已合并」,实际只有一个仓并了,另一个仓的支还挂着,改的只是文档、不触发任何测试,于是立了本条。

## 五 · 能不能进主干

### 7.13 合进去会让主干变红的支不并,主干不许红着过夜;红了用隔离对照定责

name: never-leave-main-red-overnight
type: feedback
description: 一条支功能已验收、但合进去主干会红几条,正在犹豫放不放时想起;主干红了要查是谁带进来的时也想起

合进去会让主干变红的支不并,哪怕功能已经验收、红了几条也已如实报出;主干不许红着过夜。退回时一次给齐四样:
1. 隔离归因:基点单跑一遍,基点单并 A 再跑,再叠上 B 跑,逐步定出红是谁带进来的;也可能谁都没错,只是先后顺序问题。
2. 逐条的期望值与实得值,不只报总数。
3. 每条红落在哪一块的责任面上。
4. 该改测试还是该改真源:失败断言的提示若写着「结论已变化,需要人工复核」,它就是在要人去核真源,不能当成数对不上直接改断言。

**Why:** 主干一红,之后在它上面开工的所有人都分不清哪些红是自己的,协作成本连锁放大;「功能做对了」和「能进主干」是两件事。红的若是基点上本来就有、已单独登记的存量,判据是「红集只能是基点红集的子集、新增为零」,不在本条之内。
**How to apply:** 并线判据写成「组合树新增红 0」;红了不并、不推,按上面四样给回;判做对了的标志是远端主干任一提交的红集都不比它的父提交多。
源案例:2026-09-07 某大型多人在线项目一条支合进去会让主干红 13 条,执行方如实、及早报了数,仍被两次退回,理由是别的单会在红着的主干上继续开工、分不清哪些红是谁的;三轮排查后红数降到 5 条仍未清完,于是立了本条。

### 7.14 支头下面压着没验收的提交,不整支并;支上有谁的提交自己数

name: unaccepted-commits-block-whole-branch-merge
type: feedback
description: 要把一条支整支并进主干,或有人告诉你「这条支可以整支并、里面是某某几张单」时想起

支头下面压着还没验收的提交时,这条支不能整支并;别人说「这条支可以整支并、包含哪几张单」只是线索,并之前自己数支上到底有哪些提交、各属哪张单、各是什么状态。
1. 数法:`git log --oneline <远端>/<主干>..<支头>`,从提交信息里抽出单号去重计数,逐张查状态;有「在做 / 待验收 / 返工中」的就不整支并。
2. 解法不是给共享支做变基(会让别的在办窗漂移),而是从远端主干另起一条干净支,只 cherry-pick 已验收的提交;只许手改因挑拣而冲突的文件;新支重新构建、跑测试后再推。
3. 实在挑不开时,找一个下面不含未验收提交的中间提交点先并,再单独挑拣自己的。

**Why:** 验收人核的是「这张单做得对不对」,不负责核「这条支上还挂着谁的提交」,他写的拓扑断言天然不可靠;量测、探针类的提交与功能提交堆在一条支上,状态混在一起就无法整体处理。每张单一条支、支上只有本单提交时,这条自然满足。
**How to apply:** 并线前固定跑一次「支上单号计数」,写进并线记录;判做对了的标志是并进主干的每一笔提交都能对上一张已验收的单。
源案例:2026-09-05 某大型多人在线项目一条支的支头下压着一批未验收的提交,四张已验收的单被整批挡在主干外;同日另一份验收结论写「某支头可以整批合并、含三张单」,并线方照信,实际数下来支上有 8 个单号,其中一张还在执行方手里、从没验收过,它的 4 笔提交(含大量测试数据)压在被信任的提交下面,险些被带进主干,于是立了本条。

### 7.15 能不能并别人的提交,看内容冻结没有,不看推没推到远端;按冻结的提交号并,不按分支名

name: merge-frozen-commit-not-branch-name
type: feedback
description: 要并的前置支在远端上找不到、或只在本机看得见时想起;几个工作树共用一个对象库时尤其要想起

能不能并别人的某笔提交,分界是内容冻结了没有(对方已交付并给出了具体提交号),不是它有没有推到共享远端;没冻结的不并(随时会变),已冻结的按交付记录里的提交号并,不按分支名并(分支名还在动),并完推自己的支,把它一起带上远端。

**Why:** 几个工作树共用一个对象库时,别人没推的提交在本机也能 `git show`、能 merge,「看得见」变得很廉价;真正要管的只有两件:内容还会不会变,下游能不能拿到。前者由「已交付 + 冻结的提交号」保证,后者由推自己的支解决。各窗互相看不见对方的对象库时,只能等对方推。
**How to apply:** 撞上「前置支在远端上找不到」先分清两种:未交付的,停;已交付未推的,按冻结号并、推自己的支;残留的分歧(对方要不要补推自己的支)报给上一级定,不自己处理;判做对了的标志是并进来的那一笔提交号与交付记录里的逐字相等。
源案例:2026-09-06 某大型多人在线项目几个工作树共用一个对象库,第一次对方的支还没交付,被正确拦下;第二次对方已交付但还没推到远端,本方照任务书字面「支找不到就停」险些白等一轮,而两个真正的顾虑在「按交付的提交号并、推自己的支」之后都已解决,于是立了本条。

### 7.16 叫停别人、发紧急纠正之前,先 fetch 重跑判据,拓扑关系用祖先命令核

name: refetch-before-blocking-others
type: feedback
description: 要叫停别人的窗、开退回单、发「某值在主干上还没生效」一类紧急纠正之前想起

叫停别人、开退回单、发紧急纠正之前,第一步先 `git fetch` 取最新,再重跑判据;「两支会不会分叉、是不是在重复做」这类拓扑判断,用 `git merge-base --is-ancestor <甲> <乙>` 核,不凭交付文件清单有重叠去推。

**Why:** 几十分钟前算出的结论可能已经过期;越紧急越容易忘了重取,而错误的紧急通知让对方改一遍再改回来,返工翻倍。文件路径重叠不等于分叉:后一支完全可能是把前一支整体并进来再加一笔的线性接续,只有跑命令才看得出。
**How to apply:** 叫停令、退回单里每一句事实判断后面附证据命令、输出和远端主干短号;顺手核对方提到的那一笔是不是真已在主干里;要求对方做的事要在对方的权限之内;判做对了的标志是发出去的纠正在对方重取之后仍然成立。
源案例:2026-09-05 某大型多人在线项目仅因两个执行方的交付清单都提到同两个文件,就断定两人在重复做、会造出第二条分叉支,叫停了一个正常推进的窗,实际后一支是整体并入前一支后的线性接续,被叫停的改动里还有一处真实的缺陷修复,险些被当重复工作删掉;09-06 一个工位没重取就给另一工位发紧急通知说某数值在主干上还是旧值,实际主干早已前进几笔、该值已生效,对方险些返工,于是立了本条。

## 六 · 推送

### 7.17 并完就推,推送不逐笔事前请批;推完以远端真值为准

name: push-right-after-merge-no-per-push-approval
type: feedback
description: 并完了要推共享主干、正在想「要不要先请示一下」时想起;下游抱怨在旧基点上解冲突时也想起

谁并线,谁核完祖先关系与差异就直接推,推送共享主干不做逐笔事前请批;拍板的人改为事后抽查。推完只认远端的真实值。

**Why:** 共享主干一直在动,逐笔请批会「刚提请就过期」:主干每前进一笔,前一张请批单就作废,全程空等;更贵的是主干迟迟不推,其它窗 fetch 到的都是旧头,在过期的基点上解冲突白做一轮,甚至据此误判「冲突还不存在」。拍板的人该管的是全局把控,不是每一笔的流程锁。推送会直接触发生产部署且没有回滚手段时,推送前的人工确认仍要保留。
**How to apply:** 并线后自己用命令核祖先关系与差异,不采信别人的自述,然后直接推;推后跑 `git ls-remote <远端> <主干>` 核远端真值,不看本地的远端跟踪引用;事后抽查靠合并记录这类可追溯的痕迹;判做对了的标志是并线记录里的提交号与 `ls-remote` 的输出一致,且从并完到推上远端之间没有等待。
源案例:2026-09-06 某大型多人在线项目为推送同一件事一天连建四张请批单,主干每前进一笔前一张就过期,没有一张被否决,全程空等;期间其它工位在旧主干上解了一轮冲突白做,还有工位据此判「冲突尚不存在」险些判错,设计者当面裁定推送不再逐笔请批、由负责并线的一方核完自主推送,理由是该做的是全局的把控而不是全局的流程锁定,于是立了本条。

### 7.18 有多个远端时,推送状态逐个远端核真值;镜像同步会静默坏掉

name: verify-each-remote-separately
type: feedback
description: 仓有两个以上远端(如内网主远端加公开托管平台镜像)、要报「已推送」或下游说拿不到某条支时想起

有多个远端时,「推到主远端会自动镜像到另一个」只是假定;报推送状态逐个远端查真值(`git ls-remote <远端>`)、分开报,不合成一句「已推送」;补推只推快进、不带 `--force`,两个远端各自领先对方的分叉支不强推,留给人判原因。

**Why:** 镜像钩子、定时同步一坏通常是静默的:错误被吞掉,日志里还是很久以前的旧信息,定时任务的方向甚至可能是反的;团队长期不知情,直到某个下游流程拿不到本该存在的支才卡住。出现分叉说明有人绕过流程直推了另一个远端,强推会抹掉那边的提交。只有一个远端时,本条不适用。
**How to apply:** 推送回报写成「<远端甲> 头 = <短号>,<远端乙> 头 = <短号>」;给镜像同步配一个定期比对两边支头的检查;判做对了的标志是每个远端的支头都有一条带时刻的查询记录。
源案例:2026-09-08 某大型多人在线项目实查发现,长期以为推主远端会自动镜像到公开托管平台,实际负责镜像的服务端钩子早坏了,真实错误被吞、日志里留的是早已解决的旧错误,定时轮询的方向还是反的,两个仓大量支只在主远端上,卡住了一次部署检查;修好钩子、补推之后实测仍有 9 条支两边各自领先、真正分叉,于是立了本条。

## 七 · 部署与回读(项目有线上服务时)

### 7.19 部署上去的是远端主干的整段历史:部署前数清线上头到主干头之间差几笔、各是谁的

name: deploy-ships-whole-main-history
type: feedback
description: 项目有线上服务、准备部署时想起;尤其是听说「别的单会先部署」「这次只上我这一段」时

项目有线上服务时,部署上去的是远端主干头的整段历史,不能只取自己那一段;部署前最后一步读线上实际在跑的版本,数清「线上部署头..远端主干头」之间差几笔、各属于谁,带了别人的就告知对方,不替对方下结论、不替对方建验收记录。
1. 线上实际版本从线上读(服务自报的版本、部署目录指向的提交),不信看板上记的值;用 `git merge-base --is-ancestor <线上头> <待部署提交>` 核两者关系。
2. 几扇窗先后部署时,后部署那一方的部署提交必须包含先部署那一方的提交。
3. 只想上自己那一段,三条同时满足才行:支的基点等于当前线上部署头;支上只有自己的提交;有明确理由不带别人的改动。而且必须先把支并进主干,再部署这个支头;反过来先部署后并,线上跑的版本不在主干历史里,下次从主干部署时这段修复会静默消失。
4. 部署后立即告诉被带上线的各方:带了哪几笔、有没有首次触发的数据迁移、请自行验收。

**Why:** 「对方会先部署」是对未来的预期,不是可核实的事实,一旦写进正式文档就被下游当成定论转述;真正能核的只有线上部署头与远端主干头这两个随时在变的值。没有线上服务的项目不适用;一次只有一张单在部署、中间没有别人的提交时,只剩第 1 点要做。
**How to apply:** 部署步骤固定最后一行「线上头 <短号> → 部署 <短号>,中间 N 笔:本单 a 笔,其余各属……」;判做对了的标志是每次部署后,被带上线的每一方都收到过一条告知。
源案例:2026-09-20 某大型多人在线项目负责人口头预告另外几张单会先于本单部署,本单据此判断不用等、不用带,并写进了需求文档与任务书;真到部署时那几张并没部署,一次部署把另外 23 笔不属于本单的提交一起带上了线,其中有一次首次触发的数据迁移,它们的责任方从没做过部署验收,于是立了本条。

### 7.20 部署前后按每条应上线的支跑特征探针;包的哈希只证明线上跑的是这个包

name: deploy-probes-per-branch
type: feedback
description: 项目有线上服务、部署前后要确认「该上线的都上了」时想起;有人说「今天部署过了」时也想起

项目有线上服务时,每次部署前后都按每条应当在线上的支跑一遍特征探针(搜该支独有的字符串、接口或行为),全部命中才算通过;包的哈希只能证明「线上跑的就是我打的这个包」,证明不了「包里没漏掉某条支」。

**Why:** 并线、部署、推送分属不同角色各管一段时,会出现两种相反的空档:支已并进主干却从没部署,被当成「线上已验证」;部署时从主干重新拉支打包,反把自己还没并进主干的修复覆盖掉。哈希比对对这两种都是盲的。一个角色一条龙做完并线与部署、且部署的提交必是主干头时,空档变小,但探针仍是最便宜的回读,不省。
**How to apply:** 每条支交付时附一条特征探针命令,部署脚本前后各跑一遍、打印命中数;部署前先比一次「线上版本 vs 远端主干」,不因「今天部署过」就默认已生效;判做对了的标志是部署回报里每条支一行「探针命中 N」。
源案例:2026-09-04 某大型多人在线项目同一天撞两起相反的部署事故:一条支已并进主干却从没部署,差点被当成已在线上验证过;另一次从主干重新拉支部署,覆盖掉了自己还没并进主干的一处修复,线上一度丢了刚做好的提示;两次都是靠逐支搜特征字符串的探针脚本才查出,哈希比对完全看不出,于是立了本条。

### 7.21 部署成功只认五样回读,日志里的「就绪」字样是纸闸

name: deploy-success-five-readbacks
type: feedback
description: 项目有线上服务、部署命令跑完、准备宣布「上线成功」时想起

项目有线上服务时,部署成功只认五样回读同时成立:指向当前版本的链接或配置已切到新版本、新版本的产物目录非空、服务状态是「已激活」而不是「启动中」、端口确实在监听、服务的启动时间晚于本次部署开始;搜日志里有没有「就绪」字样是纸闸,不算。

**Why:** 日志是追加写的,服务若陷在崩溃后自动重启的循环里,上一次成功启动留下的「就绪」一直都在、搜得到;部署失败的真实样子往往是产物目录建出来了但是空的、版本链接没切、服务状态照样「运行中」,看起来像成功。部署脚本在某个自检失败时提前退出,后面的检查项压根没打印,也容易被当成「输出被截断」。服务有自己的健康检查接口并报出版本号时,可以用它顶替其中两样,但仍要核那个版本号是本次的。
**How to apply:** 部署回报固定五行,每行贴命令与输出原文;部署脚本里前置命令的返回码逐个检查,输出提前结束本身就当失败;判做对了的标志是五行齐全、启动时间晚于部署开始时刻。
源案例:2026-09-05 某大型多人在线项目一次部署后靠搜日志「就绪」判上线,差点被崩溃重启循环里的旧日志骗过,真正戳穿的是「端口没在监听」和「服务状态是启动中」两条;另外还发现部署脚本在一处自检失败时提前中止,后面该打印的检查项全没出现,容易被误读成输出截断,于是立了本条。

### 7.22 部署用的构建配置和日常测试的不同时,本地全绿证明不了部署那一刻编得过

name: deploy-build-config-differs-from-test
type: feedback
description: 项目部署或发布用的构建配置(如 Release)与日常构建、测试用的(如 Debug)不同,准备并一批要上线的改动时想起

项目部署或发布用的构建配置与日常构建、测试用的不同,而代码里又有按配置切换的条件编译时,本地全绿加主干全绿证明不了部署那一刻编得过;凡要真部署的一批,并线前自己用部署配置完整构建一次,不拿测试配置顶替。
1. 探针、工具类的辅助工程,也显式用与被测代码相同的配置构建。
2. 认得部署失败的真实样子:产物目录建了但是空的、版本链接没切、服务照样在跑(见 7.21)。

**Why:** 常规闸(编译、全部测试)默认都用开发配置跑,没人想到去验部署配置;条件编译本是为区分环境而设,一旦有代码不小心跨过这条边界,就会「全绿而部署即坏」。仓里本来就有在部署配置下编不过的既有工程时,先在干净主干上用同一配置构建对照,别误以为是自己写坏的。部署与测试用同一个配置时,本条不适用。
**How to apply:** 并线清单加一步「用部署配置构建全部要上线的工程」,回报贴构建输出的最后两行;判做对了的标志是部署那一刻的构建零错误、产物非空。
源案例:2026-09-15 某大型多人在线项目一个源文件顶部的类型引用被包在只在调试配置下生效的条件编译块里,本地与主干全绿,一到线上用发布配置编译就报找不到类型,产物目录建了但是空的,服务没掉线、看着像部署成功,其实根本没切到新版本;09-20 又有人顺手用发布配置构建一个测试工程,撞上同一种仓库既有形态,于是立了本条。

### 7.23 持久化数据的格式版本号一升,没有存量数据的读法就不并、不部署

name: format-version-bump-needs-migration
type: feedback
description: 项目有线上服务和存量持久化数据、要并一笔改了持久化格式或协议版本号的改动时想起

项目有线上服务和存量持久化数据时,持久化格式(快照、数据文件、协议)的版本号一升,就先问清「线上已有的旧数据怎么被读」;没有迁移路径、也没有「有意丢弃旧数据、丢多少」的明确决定之前,不并、不进部署计划。

**Why:** 自动化测试证明的是代码自洽,测试环境通常从干净状态起步,不会去读线上磁盘上的旧格式数据;加载器若按设计「不跨版本猜着读」,新版一上线读到旧数据就抛异常,服务反复崩溃重启,测试却一条不红。没有存量数据(全新部署,或数据可以随时重建)时,这条不适用。
**How to apply:** 并线前对待并的每一笔搜格式版本常量的改动,命中就要迁移方案或丢弃决定,并把它当一个单独要拍板的项;判做对了的标志是每次版本号上升,都能指到一段读取旧版本数据的代码,或一句有记录的丢弃决定。
源案例:2026-09-05 某大型多人在线项目记下:把一个持久化快照的格式版本号往上抬,加载器按设计拒绝跨版本读取,合并树全部工程测试全绿,部署后服务因要加载线上磁盘上的旧格式数据每隔几秒崩一次,只能回滚,于是立了本条。

### 7.24 部署脚本整份重写配置文件时,没显式保留的运行时开关会被静默刷回默认值

name: deploy-script-rewrite-resets-switches
type: feedback
description: 项目有线上服务、部署脚本会生成或重写环境配置文件,而线上开着某个非默认的运行时开关时想起

项目有线上服务、部署脚本用固定模板整份重写环境配置文件时,凡是没被显式保留的运行时开关,每次部署都会被静默刷回模板里的默认值;脚本的自检若也拿同一套默认值当基准,退出码、日志、自检全都正常。
1. 部署命令显式带上保留该开关的参数,一次都不省。
2. 部署后从运行中进程的实际启动参数或配置文件里回读这个开关的当前值,不只看退出码。
3. 根治是把脚本改成「先读旧值再增量写」;根治之前,每次部署都显式声明。

**Why:** 脚本不读旧值,开关保不保得住全看这一次部署命令带没带参数,漏了也不报错;而能看到的信号全都正常:退出码为零、日志只是少打印一行、自检拿同一套默认值当基准永远判不出来,只有去看配置文件里那一行才发现。脚本改成增量写、或开关不再放在被重写的文件里之后,这条作废。
**How to apply:** 部署清单列出线上当前所有「非默认」的开关,每个开关对应部署命令里一个参数和一条回读命令;判做对了的标志是部署后回读的开关值与部署前一致。
源案例:2026-09-20 某大型多人在线项目已决定开启某个功能开关,一次部署命令漏了保留它的参数,部署脚本整份重写环境配置文件,把几分钟前刚打开的开关刷回关闭,自检拿同一个默认关闭的值做基准照常通过,于是立了本条。

### 7.25 目标机上跑的部署脚本是它本地的文件,不会随部署的提交自动更新

name: deploy-script-on-target-not-auto-updated
type: feedback
description: 项目有线上服务、本次改动碰了仓里的部署脚本或部署目录下任何文件时想起

项目有线上服务、目标机上实际执行的部署脚本是它本地磁盘上的一份文件时,改了仓里的部署脚本不会自动影响下一次部署;凡本次改动碰到部署目录,部署前先把新脚本同步到目标机:
1. 先在目标机上整体备份现有部署目录。
2. 从本次部署提交里取出改过的部署文件拷上去,保留可执行权限。
3. 核哈希与语法,回读关键配置行。
4. 再真正执行部署。
5. 几扇窗先后部署时,后部署那一方拷上去的脚本必须已含先部署那一方的脚本改动。

**Why:** 部署流程自己的检查(返回码、自检)只核「传入的提交号对应的产物切换成功没有」,不核「这次跑的部署脚本本身是不是最新的」,这是元层面的盲区;新配置被旧脚本静默写回旧值,一切都显示正常。部署脚本每次都从部署提交里现取时,这条作废。
**How to apply:** 部署步骤第一问固定是「本单改没改部署目录」,改了就先走上面前四步;回报写「目标机部署脚本哈希 = 部署提交里的哈希」;判做对了的标志是这两个哈希相等。
源案例:2026-09-25 某大型多人在线项目在仓里改了部署脚本里一个环境变量的默认值,没先把新脚本拷到服务器,实际跑的仍是服务器本地的旧脚本,新配置被静默写回旧值,部署返回码与自检全部正常,于是立了本条。

### 7.26 配置种子「键已存在就跳过」时,改默认值对线上已有的键无效,删键不清库会让服务起不来

name: upsert-skip-seed-ignores-new-defaults
type: feedback
description: 项目有线上服务、配置默认值由部署时的种子脚本写进库,要改某个默认值、或删除和改名配置键时想起

项目有线上服务、部署时用「键已存在就跳过」的种子脚本把配置默认值写进库时,改代码里的默认值对线上已有的键完全无效,只有全新的键会拿到默认值;反过来删掉或改名配置键,种子只插不删,库里的旧行还在,遇到「未知键拒绝启动」的严格校验,服务就起不来。
1. 验收「改了默认值」不看代码与测试,要真查一次线上表,确认新值生效。
2. 要让新默认值生效:部署前删掉要刷新的旧行,让本次种子重新插入;或走专门的管理接口改。
3. 删键或改名的改动,部署前查出「库里有、新代码里已没有」的键一并清理,并写进验收判据。

**Why:** 「已有值优先」的设计本意是保护运营手改过的值,副作用是让代码默认值的修改对存量数据全部失效;而库里的行多半根本不是运营改的,是历次部署留下的旧默认值,这层保护保护的是过期值。种子脚本改成「按版本覆盖默认值、只保留有手改记录的行」之后,第 1、2 点可以放宽。
**How to apply:** 改默认值的单,判据写「线上表该键 = 新值」并贴查询输出;删键的单,判据写「线上表孤儿键 0 个」;判做对了的标志是这两条查询输出都在部署回报里。
源案例:2026-09-18 某大型多人在线项目部署脚本每次导出的配置默认值语句在键已存在时是空操作,线上表几千行,记录运营手改的审计表却是零行,全是历次部署留下的旧默认值,改代码里的默认值对线上一条都没生效;09-23 又撞反方向:删了一批不再用的配置键,库里的旧行还在,新版启动校验遇到未知键直接拒绝启动,服务陷入崩溃重启循环,于是立了本条。

### 7.27 停服直接改线上库:库端函数的类型与匹配语义和应用不一样,改完先按应用自己的读法读一遍

name: live-db-edit-app-semantics
type: feedback
description: 项目有线上服务、要停服直接改线上库(补数据、修存量记录、批量改字段)时想起

项目有线上服务、要停服直接改线上库时,库端函数的类型与匹配语义和应用不一样,SQL 语法对、执行成功,不代表应用读得回来;改后的每一类数据,先在本机用应用自己的读取代码读一遍,再上线执行。
1. 库端对 JSON 里的数字做算术,结果可能被存成浮点型;应用按无符号整型读,反序列化抛异常,服务启动时全量读到它就起不来。
2. 有的库端搜索函数只匹配字符串值,拿它查「某个数值序号有没有被占用」永远搜不到,等于没查。
3. 库服务器的时区可能和应用写入时用的不同,库端取「现在」写进去的时间会差固定几个小时。
4. 流程:只读子代理备份取证、在本机用应用的读取代码模拟读一遍 → 人核 → 新起一个执行子代理严格按手册执行;SQL 终稿与执行手册单独留档。

**Why:** 这几类坑编译、单元测试、SQL 语法检查全抓不到,只有服务一启动或事后核数据才露出来,而停服窗口里每一次失败都是线上事故;草稿阶段排掉的坑越多,执行时剩下的越是这种「语义不一样」的。改数据走应用自己的管理接口、不直写 SQL 时,这条不适用。
**How to apply:** 停服改库的手册里每条改动后面跟一步「本机用应用读取代码读回」;用到数值运算、时间函数的地方,手册写明类型与时区;判做对了的标志是开服后第一次全量加载零异常。
源案例:2026-09-25 某大型多人在线项目一次停服改库,事前用只读子代理加本机反序列化排掉了草稿里三处必出问题的地方,执行时仍撞上两处:对 JSON 里的数字加一后被库存成浮点型,应用按无符号整型读,服务启动全量加载时抛异常、起不来;另一处拿只匹配字符串的库函数查数值序号的占用,等于没查,于是立了本条。
