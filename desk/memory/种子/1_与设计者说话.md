# 1 · 与设计者说话

本节收:AI 窗口怎么和设计者(项目唯一拍板、唯一开窗的人)打交道——他是谁,问他什么、怎么问,话怎么说、记在哪,他的话怎么落,他的授权怎么接,他定下的干活方式。读法:新项目开第一扇窗时通读一遍;之后每次要给设计者发话、请他拍板、把他说过的话落进文件、或接他当窗给的授权之前,翻对应那一组。

## 一 · 他是谁

### 1.1 设计者是唯一拍板人和唯一开窗人:记逻辑不记数值,审美与界面自认不懂,不替你跑命令

name: designer-profile
type: user
description: 第一次和设计者打交道,或拿不准该不该问他、要不要等他动手、该怎么跟他说时

1. 设计者是项目唯一拍板的人,也是唯一开窗、唤醒各扇窗的人;他日常只做三件事:开窗、贴一句激活句、拍板。
2. 逻辑是他亲手设计的,他记得;数值定得早,大多记不住。
3. 美术、界面、前端他自认不懂,审美交给专业的人定。
4. 他不替 AI 跑任何命令,也不帮你翻目录;脚本、查询、取证都由 AI 自己跑。
5. 模型按量付费;他认为模型想得越多有时越容易幻觉,挂着窗空等就是在烧他的钱。
6. 他本机时钟可能和服务器不在一个时区:一切时刻以服务器或工单台的时间戳为准,别拿他本机的时间当判据。

**Why:** 本节后面每一条都是这张画像的一次展开;不先认清他是谁,就会拿他记不住的数去问他、拿他看不懂的审美题去烦他、坐等他去跑一条命令。曾有负责人拿本机时钟当判据,把日期改错。画像只在换了人、或他亲口改了分工时才需要重写。
**How to apply:** 新项目开第一扇窗时,拿这六条问他一句「还是这样吗」,有变化就改这一条;之后每遇到「该不该问他」「要不要等他动手」,先回这里对一遍。判做对了:他从没被要求替你跑命令,也没被问过他记不住的数。
源案例:2026-09-04 某大型多人在线项目设计者自述逻辑很早就定下、很多数值已经不记得,但逻辑大概还记得;09-08、09-14 又先后自述不懂前端、美术和界面,审美上限很低,这张画像由这几次自述归纳而成。

### 1.2 设计者只拍自己懂的领域:逻辑与规则直接问他,审美、界面、前端的取向题不拿去问他

name: designer-decides-only-his-domains
type: user
description: 要请设计者拍板,或要在任务书里写「拿不准直接问设计者」时,先判这道题在不在他懂的领域

1. 他懂的领域(他亲手设计的逻辑、规则,他自己写的需求文档与文案):拿不准可以直接在窗里问他,他拍了就以他为准。
2. 他不懂的领域(好不好看、配色、界面怎么摆、分辨率这类取向,以及前端与美术):不给他出选择题,去问这块的专业负责人或专业外包方;需要他知情时,只给「推荐 + 选了会怎样」。
3. 谁能直接问他,看题目在不在他懂的领域,不看 0 号窗档次高低。
4. 给专业外包方只写规格与可读性要求,不写主观审美参照;内部评外包件只判规格,审美意见最多算建议,不作退回理由。

**Why:** 在他不懂的领域出选择题,等于把决定推给一个自认不懂的人,他只能随手选一个,或者回一句「你来定」,白占一轮;在他懂的领域,他当场判得又快又准,绕中间层反而慢。他把审美整块交给专业的人,是不想让自己的短板拉低专业方的上限。他哪天说「这块我也能拍」,就把那块挪进第 1 项。
**How to apply:** 出题前先问:这是逻辑、规则题,还是好不好看、怎么摆的取向题?前者按本节 1.5 的问法问他,后者找专业负责人;任务书里「拿不准直接问设计者」这句只写给他懂的领域的岗位。判做对了:他没有再回过「我不懂,你来定」。
源案例:2026-09-20 某项目一批界面类拍板题摆到设计者面前,他回复自己不懂、完全看不懂界面,让对方来定,整批白占他一轮;而早在 09-08 他授权拿不准可以直接问他的当天,就两次收窄成只限他亲手设计的逻辑和文案,于是立了本条。

## 二 · 问什么、怎么问

### 1.3 数值一律不问设计者:查真源直接用;他回答里的「我记得」「应该」「吧」是回忆,不是裁定

name: never-ask-designer-for-numbers
type: user
description: 手上缺一个数(倍率、上限、时长、百分比、数量),想去问设计者「这个该是多少」时

1. 数值不问。真源顺序:正式裁定原文 > 已交付的代码或配置里的现值 > 交接件;查到直接用,写明出处。
2. 需求文档缺值、而代码里已有同类常量的,沿用既有常量,新引用指向那个常量本身,不抄一份字面值。
3. 汇报写成「按某条裁定应为 A,现在是 B,改成 A」,不写「要不要改成 A」。
4. 真查不到才开口,且不问开放式的「多少」:把既有的几个值和各自后果摆出来,问「要 A、要 B,还是第三个」。
5. 他回答里带「我记得」「应该」「吧」「我忘记了」的数是回忆:不照抄进实现、不据此派单,去系统里读真值;读不到,就带着「查了哪几处、结果是什么」再问一次。他当面改了一个值,要同时让文档也改掉。
6. 例外只有两种:他自己先说「这不对」;或两条正式裁定互相矛盾。

**Why:** 他的每条机制早就拍过、落了码,他记住的是逻辑不是数;拿数去问,等于逼他重拍一次记不住的东西,答不准,还伤他对你的信任。随口的数落进代码,就凭空多出第三个和既有值打架的真源:曾有一个他随口给的时长,和系统里已有的两个同类时长都对不上。他也当窗抱怨过:一直拿数去问他,等于让他重新拍板一次,他根本记不清这么多数值。
**How to apply:** 想问数之前,先派子代理把三处真源查一遍;发出去的话里只要出现「这个数是多少」,就是做错了。判做对了:他收到的只有「应为 A、现为 B」这种陈述,或者摆着既有候选值的逻辑题。
源案例:2026-09-04 某项目一天三次向设计者要数:一次他记不清,而代码里早有裁定且各处一致;一次他给出一个「X 还是 Y」的含糊回忆;一次他不记得参数,却凭一句逻辑判断就点出了错——三次拿回来的都不能当真源用,于是立了本条。

### 1.4 已经有答案的不拿去问:文档写了照原话做,裁过的不问第二遍,标「要问」之前先查透

name: check-truth-before-asking-designer
type: feedback
description: 在任务书里写「此处要问设计者」,或准备在窗里向设计者提一个问题之前

1. 他的需求文档、正式裁定写了的,逐字照原话做,不自行解读,也不拿「取向」再去问他;任务书里不写「此处问设计者取向」这类闸。
2. 标「要问设计者」之前,把裁定记录、需求文档、已交付的代码和配置全查一遍;查到就写死并回指出处。真能留给执行方自定的,只有真源里明说「不代裁」的那部分。
3. 他答过的,直接引用上次的原话;他说过「这是最终裁定,以后不要再问」的,永远不再问——哪怕后来发现旧记录里的细节写错了,也只照裁定执行。
4. 交接件里「A 与 B 等价」「都行」这类模糊句,起草人要么追出一个确定答案,要么删掉,不留给下一个人猜。
5. 他说某块后端应该已经写了的,自己去核,常常实测并没有写。
6. 执行方真读不懂文档时,由负责这张单的窗本人去问一句,不让下属代问。

**Why:** 把自己该查的事标成「要问」,是把活推给执行方和他:执行方照着「要问」走偏,他被迫在窗里当场判一次本来查得到的事。曾有一个分类判断被标成「要问」,而代码里三类早已写死、注释还写明不许发明第四类,与他后来在窗里说的完全一致;另有一个他早已拍死的写法问题,因为旧记录里一句「两种写法其实一样」,前后被问了三次,他最后明确裁定没有例外、以后不要再问。
**How to apply:** 每个「要问」旁边写一句「查过哪几处、为什么都没有」,写不出来就是没查完;查的活派子代理,别自己读大文件。判做对了:他收到的问题都是真源里确实没有的,而且没有一道是他答过的。
源案例:2026-09-20 某项目有窗把文档里已写明的取向题问到设计者面前,他当窗定下:问了他也看不懂,照他的文档做就可以,只有看不懂文档的地方才来问他,从此任务书里不许再写「问设计者取向」的闸,于是立了本条。

### 1.5 逻辑题可以直接问设计者:先查透,再用人话四段、互斥选项、一条推荐,一次只问一件

name: ask-designer-logic-in-plain-words
type: feedback
description: 真源查不到,必须请设计者拍一道逻辑题(机制怎么走、先后顺序、谁能做什么、范围划到哪)时

1. 能问的是逻辑和范围题;给两三个候选让他拍,不替他定。
2. 问之前先派人取证,把代码和文档查透,并写上「查到了什么、哪一处填不出来」。
3. 一次只问一件,用四段人话:这是什么功能(用户眼里的样子)/ 线上现在怎么走 / 文档怎么说 / 几种做法做出来各是什么样。每个选项附一句改动量或风险,标出推荐。
4. 用带互斥选项的提问方式问,不抛开放式的抽象问题。
5. 他可能把备好的选项全推翻、给一套新逻辑:照新逻辑重做,不许硬套回原选项。拍完之后让施工方先出方案再动手。
6. 不涉及产品取向的纯技术细节自己定,写清假设,不必都问。

**Why:** 很多设计意图只在他脑子里,代码和文档都查不到,猜错会做出语义完全相反的功能;他自己说过,逻辑问题可以直接问他,但必须用通俗的人话问,最好详细解释。术语堆出来的问题他看不懂,选项不带代价他没法比,范围题替他定了他会当窗反过来,白改一轮。
**How to apply:** 发问前自查:四段齐不齐、有没有推荐、是不是一次一件;他的回答原话记进进度件,改动处引原话。判做对了:他一次就能答,答完不用再追问第二轮。
源案例:2026-09-24 某项目设计者定对接中撞到的逻辑缺口本单一起补齐,但要用人话告诉他具体逻辑是怎样的,同时给出选项和推荐;照这个问法,一张对接单把六件既定缺口和四件新发现逐件摆成几选一加推荐,他全选了推荐项,当次就把服务端那一半一起做完上线,于是立了本条。

### 1.6 拍板选项用设计者亲眼见过的具体数和画面举例,不用抽象词

name: designer-options-use-concrete-examples
type: user
description: 给设计者写拍板选项时,尤其是一个系统级毛病要他定修法时

1. 每个选项写成「改完以后你在屏幕上会看到什么」,用他亲眼见过的数和画面举例。
2. 不拿抽象词(「数据源合并」「口径统一」之类)当选项;他问「是不是 X」,直接答是或不是。
3. 他报的是系统级毛病时,要的是根治不是补丁:先派子代理摸清底层到底怎么接的,勘查结论写「底层一句话 + 缺陷清单(每条标真人会不会撞上)」,再出题。

**Why:** 抽象选项他看不懂,只能回一句没看懂,一来一回就是一整轮;换成他见过的数,他一眼就能判出哪个符合当初的设计。他的意思是不该为了修毛病而修毛病,要看底层到底是怎么接上去的——只补表面那一处,同一个根上还会再长出下一个。
**How to apply:** 选项写完读一遍:每个选项里有没有一个他在界面上能看到的数或画面?没有就改写。判做对了:他一次答完,不再回复没看懂。
源案例:2026-09-26 某项目一个系统级毛病的拍板题,两次写成抽象选项,设计者两次都回复没看懂;改成「面板上现在显示 N,加 1 点后你希望看到 N+1 还是仍是 N」这种他亲眼见过的样子后,一次就拍完四件,于是立了本条。

### 1.7 设计者报现象含糊时,先问一句能把方向一刀切开的互斥题;先信他看到的

name: designer-symptom-ask-one-split-question
type: user
description: 设计者只用三五个字报一个毛病或现象,你一时复现不出来时

1. 他报现象常常只有三五个字。别急着自己盲目复现,先给他两个互斥的可能让他挑(例:「是点了没反应,还是打开了但内容不对?」),他答一句就砍掉一半排查空间。
2. 他亲眼看到的往往比你复现的更可靠。你复现不出来,不等于他看错了;先信他,再自己量一遍,量完再回话。

**Why:** 含糊的描述会让排查方在错的方向上绕好几轮,而一句区分题一分钟就能定方向;这句区分题本来一开始就该主动问。
**How to apply:** 收到含糊的报告,先写出两三个互斥的可能,挑最能一刀切开的那一对问他,同时派子代理去取证。判做对了:第一轮回话里就有这道区分题,而不是「我这边复现不了」。
源案例:2026-09-04 某项目设计者报「某个东西打不开」,排查方核了文件和路径都没问题、自己复现不出,绕了三四轮;他补充说确实是点了没反应,一分钟就定位到是事件没绑定,于是立了本条。

### 1.9 和文档对不上,或和别的岗位一轮对不清,直接问设计者,不在中间层兜圈子

name: designer-escalate-after-one-round
type: feedback
description: 发现文档、代码、设计口径对不上,或同一件事已经和另一个岗位来回过一次还没说清时

1. 发现和文档对不上:直接在窗里问他拍板(问法见本节 1.5),不转给中间的岗位,不写「等某位改」。
2. 一件事和别的岗位最多核对一次;要第二轮,就改问他。
3. 他给了专门的拍板渠道时,严格照那个渠道要求的格式写(例如「这是什么 / 选了会怎样 / 推荐」按序三段、都不许空);格式不对,他可能根本看不到。

**Why:** 交接件多半只是代码盘点,设计逻辑在他脑子里;转一圈中间层多一跳,对方还常常只改文档不改画面。他在另一次也说过,岗位之间来回拉扯两轮以上,成本比直接问他还高;曾有一条给他的反馈因格式不对,连续两次没被他看到。
**How to apply:** 数一下同一件事已经在岗位之间往返了几次,到第二次就停下改问他。判做对了:没有一件事在两个岗位之间来回超过一轮。
源案例:2026-09-23 某项目对接阶段,设计者当窗定和文档不符的地方不再转给中间的岗位,让 0 号窗直接找他拍板,理由是只要具体说清是什么功能,他就能知道具体逻辑是什么,于是立了本条。

## 三 · 话怎么说、记在哪

### 1.10 给设计者看的字一律中文通俗话:短、三段、做完一段就回一句

name: talk-to-designer-plain-chinese
type: user
description: 给设计者写任何一句话之前——进度播报、子代理结果转述、结论、收尾、提问

1. 一律中文通俗话;进度、转述、收尾都不切英文,术语换成人话。代码标识符、路径、命令照原样保留,周围的说明文字用中文。
2. 一件事控制在 8 行以内,分三段:出了什么事 / 对他意味着什么 / 要他定什么(附一句推荐)。
3. 每做完一段就回一句进度;长时间不吭声,他就不知道你在做什么。
4. 技术细节、需要别的岗位裁定的事走内部渠道,不塞给他。

**Why:** 他靠窗里的中文播报跟进度,英文或术语他读着费劲,等于没报;他同时盯着好几扇窗,超过八行的话他没空细读。他也当窗叫停过一扇埋头干活的窗,要它停下来和他交流,而不是一个劲地做、让他完全不知道在做什么。
**How to apply:** 发出前自查三件:是不是中文、有没有术语和内部编号、是不是超过八行。判做对了:他看完能直接回「可以」或选一个,不用反问「这是什么意思」。
源案例:2026-09-23 某项目一扇窗把几条进度播报写成了英文,设计者当窗指出文字要用中文输出,这样他才知道进展,并定下进度、转述、收尾一律中文通俗话,于是立了本条。

### 1.11 回设计者报动作不报代号:请他开哪一位的窗、写全称;不报内部单号,不报具体模型名

name: designer-reply-actions-not-codes
type: user
description: 回设计者、要他去做点什么(开窗、看单、唤醒某个岗位)时,或要跟他提任务档次和模型时

1. 他要的是动作:「请开 <岗位全称> 的窗」「让 <岗位全称> 看一下工单」;不报内部单号,非指某张单不可时用标题人话。
2. 岗位名写全称,不省成编号尾数。
3. 给别的岗位发了单,回话里必须点名请他开哪一位的窗:各扇窗不会自己醒,他是唯一的唤醒人,不说就等于没人去开。
4. 他把「转达」下放给你时,可以直接给相关岗位发单,单里注明是他授权的;但唤醒仍要告诉他。
5. 对他只说任务档次(高、中、低这类标签),不报具体模型或资源名;挑哪个模型、怎么调度是他的事。
6. 单子内部、正式裁定、对话线里照旧写编号,只有给他的聊天不写。

**Why:** 他只在工单台上操作,内部编号对他是噪音,工单里本来都看得到;他同时看十几扇窗,一个尾号他对不上是谁家的。资源额度和可用性由他掌握,报具体模型名只会添乱,还可能被下游误读成指令。
**How to apply:** 发出前扫一遍:有没有单号、有没有尾号、有没有模型名;每派出一张给别人的单,回话末尾有没有一句「请开某某的窗」。判做对了:他看完就知道下一步去点哪里。
源案例:2026-09-03 某项目回设计者时直接报了工单编号,他定下不要直接回工单编号,只需告诉他让谁查看工单、开哪个窗;09-05 又因只报了一个尾号「-30」他对不上是谁,追加要求以后一律写岗位全称,于是立了本条。

### 1.12 让设计者看任何东西,都附一个能直接双击打开的本机绝对路径

name: give-designer-openable-path
type: user
description: 请设计者看图、听样、对比、点头确认任何文件时

1. 每件要他看的东西后面跟本机绝对路径,能直接双击打开;多件列成清单,一行一个。
2. 发之前确认文件真在那个路径上。
3. 实在给不出本机路径时,写「工单标题 + 附件序号」;不能只写「第 09 张图」「上面那个」。

**Why:** 他不在你的窗里,也不会去项目目录里翻;只有你自己懂的引用,对他是空话,他只能回头问你在哪,白跑一轮。
**How to apply:** 回话里一出现「看图」「听一下」「对比」「点头」这类字样,就逐条核后面有没有路径。判做对了:他从不需要问「在哪里看」。
源案例:2026-09-12 某项目请设计者看「第 09、10 张图」却没给路径,他不知道去哪看,当场定下每次请他查图都要附上地址,否则他不知道去哪里看,于是立了本条。

### 1.13 设计者在聊天里定的、你答应他的,当轮落成工单台上看得见的记录

name: designer-words-land-on-desk-same-turn
type: feedback
description: 设计者在聊天里拍了板、授权了什么,或你答应了他一件事之后;以及收尾前自查时

1. 聊天里说的不算数:你答应他的事,当轮落成工单台上看得见的状态(建单、改状态、写进任务书)。
2. 开窗一律经工单生成,不在聊天里手写「请开某窗」,否则他没有开窗记录。
3. 需要对方做事,才发占对方待答位的正式请求;单纯告知或更正,走不占待答位的通知,只给新旧对照、不给问句、不等回复。已发出的待答请求收不回,发之前先想清楚要不要对方做事。
4. 送达不等于被看到:追加的必做事项,要么改进任务书,要么要回执,要么另开单。
5. 对工单台的写操作,先看返回结果,再说「已完成」。

**Why:** 阻塞的单在工单台上安静地躺着,没有机制会提醒谁回头看;他说过的话只留在聊天记录里,执行方随时可能读不到。曾有一条必做的追加只走了聊天通知,执行方到交付都没读到。
**How to apply:** 收尾前逐条对:今天说过的每一个「已完成」「已安排」,工单台上有没有对应的记录。判做对了:只看工单台,就能还原今天和他定下的每一件事。
源案例:2026-09-04 某项目设计者定下所有开窗一律走工单,否则他没有开窗记录,从此开窗只经工单生成、不在聊天里手写;另有一次,一位负责人一天在同一个坏习惯上栽了三次(答了「已排期」却没建单、阻塞状态没回头核、把本单执行方要做的事写成了前置),三次都是别人来问才暴露,于是立了本条。

## 四 · 他的话怎么落

### 1.14 设计者的决定即最终决定:当轮改、当行引原话;对别的岗位是告知,不是请裁

name: designer-decision-is-final
type: feedback
description: 设计者当窗更正、拍板、推翻某件事之后,准备去改文件或通知别的岗位时

1. 他拍了,当轮直接改任务书或自己管的文件,改动处当行写明「据设计者某日当窗原话改,原值 X」,并逐字引原话。
2. 对其他相关岗位是「告知」,不是「请裁」:不问别人同不同意,不写「请某某追认」;告知标题写明「最终更正·告知·不需答复」,走不占对方待答位的通知(见本节 1.13)。
3. 改完自查:别处还有没有「等设计者定」的残留句子;他已经定完了,这类前置当场删掉。
4. 给别人的处置建议,先自己想一遍对方会不会撞上同样的墙。

**Why:** 协作链上没有哪一环是他的上级;把他的决定当成「要某人确认的提案」,等于替他把决定降了级,还会给排队中的单凭空加一条永远不会满足的前置。
**How to apply:** 每落一条他的决定,检查三样:原话在不在改动处、原值写没写、有没有残留的「等他定」。判做对了:下游读到的是他的原话,而不是某个岗位的转述或请示。
源案例:2026-09-17 某项目设计者当窗逐字给出更正,说明可以直接照他说的改,因为他的决定就是最终决定,负责的总监却把作废旧口径写成请另一个岗位去处理,对方撞上同样的墙,只好当轮再补一条自己收回,于是立了本条。

### 1.15 设计者后说的压过先说的:以最新一句为准,顺着找全抄了旧说法的地方

name: designer-latest-word-wins
type: user
description: 设计者当窗推翻了自己以前的决定、或一句话定了新标准时;或手上的旧文档与他最新的说法打架时

1. 他会当面推翻自己先前拍过的决定,也会直说自己以前的设计有问题。以他最新一句为准;仓里的旧文档、旧注释是「待更正」,不是依据。
2. 他一句话定了新标准,与之冲突的旧内容整体过期,不必逐条请示;但过期只覆盖新标准真正说到的那一面,没提到的旧约定照旧有效。
3. 推翻之后,把抄了旧说法的地方(文档、代码注释、任务书、交接件)一次找全:自己管的当场改;别人管的只读真源标「待更正」,转给它的负责人改。
4. 他给的草图、手绘、参考材料可能只有一部分还算数;问清哪部分要推翻、哪部分仍有效,不整张照抄。
5. 分工、谁能直接问他、谁去通知谁,也会被他改;跟最新一句走,别当永久定案。他说冲突由他开窗时自己去说、不用你通知时,只出一张冲突事实表给他,不越权去通知对方。

**Why:** 旧决定一旦被抄进好几处,只改一处,其余几处会在下一窗被当成现行依据再抄出去;照着旧文档做,交付的就是一个他已经改掉的东西。而每处冲突都去单独请示,又会把进度拖死。他要求一定传达清楚并刻进记忆时,就是不想再为同一件事讲第二遍。
**How to apply:** 收到他推翻旧决定的话,当轮派子代理全仓搜旧说法的关键词,列出所有命中处,每处写明被哪句新话取代。判做对了:仓里搜不到还当现行的旧说法。
源案例:2026-09-18 某项目设计者当窗推翻自己先前定的界面缩放「分两档」方案,改成按窗口宽度连续缩放,自承以前的设计有问题;旧方案已被抄进至少四处文档和代码注释,全部随之过期,于是立了本条。

### 1.16 转述不是原话:推翻已判的东西前回真源核;同一点第二次改口径,要拿出一条与说话人无关的证据

name: paraphrase-is-not-designer-words
type: feedback
description: 听到「设计者说 X,所以 Y」,或交接件里写着「现状是 X」,准备据此推翻已判的东西或往下传时

1. 转述里的「所以 Y」多半是转述者自己的推断;没标明是原话的,一律当推断。
2. 要用一句转述去推翻已经拍板或已经上线的东西,先回真源(他的原话、正式裁定、代码)核一次。
3. 同一个点第二次改口径,必须停下来找一条与「谁最后说了什么」无关的证据(代码、数据、比对结果),否则就是跟着最后一个说话的人来回摆。
4. 交接件里「实机现状是 X」这类断言,尤其是靠肉眼看屏幕得出的,先对最新代码核过再往下传;派单前先问一句「这东西是真不存在,还是只是没接通」。
5. 写「X 就是 Y」之前先做精确比对(例如哈希);比不上就只说「像」,不说「是」。
6. 口径翻转后做三件事:通知所有依赖这个判断的下游;更正错误转述的源头;逐条列出哪些结论作废,不能只写「以最新为准」。

**Why:** 曾有一个机制点在一天内被判了三次:第一次按真源判对了,第二次跟着一句转述改判,第三次设计者亲自当窗逐字澄清又改回来,而代码里三十秒就能查到的通则两次都没人去查。另有几件他已亲耳确认过的素材,被人拿统计指标判成「新版本」,工单台上记成全部否决,哈希一比才知道是逐字节相同的旧件,险些让他对着自己确认过的东西再做一遍。
**How to apply:** 每次要改一个已判的结论,先写下「这次的依据是谁说的,还是查到的」;是谁说的,就先去查。判做对了:每次改口径都附着一条可复查的证据路径。
源案例:2026-09-20 某项目交接件里一句靠肉眼看屏幕得出的现状描述(某界面「没有某几种状态的视觉」)被后续文件原样抄走,险些据此派出一张重做已有功能的任务书;派子代理核代码才发现那些早已做好,真缺的只是一个数据源没接通,于是立了本条。

### 1.17 设计者会对几扇窗重复同一件事:落正式记录前先拉最新、查重、问一句「这条还成立吗」

name: designer-repeats-to-many-windows
type: user
description: 准备把设计者说的一件事、或某位负责人的判语落成正式裁定或正式记录之前

1. 他当面对你说的事,很可能几乎同时也对另一扇窗说了一遍,对方也许已经落了记录。落之前先同步远端最新真源,按主题词查重。
2. 撞上了不另占一条:把双方各自漏掉的事实汇总,补进已有那条。
3. 两个转述版本对不上,不自己选边,当轮拿去问他。
4. 负责人写下的判语只是快照,他常在 0 号窗里当面把它推翻;落正式记录、引用某条判语前,先回那条线问一句「这条还成立吗」。
5. 自己的判语被他当面改掉了,当轮主动告诉依赖它的各方;作废时把现行口径和他的原话一起写进正文。

**Why:** 他同时开着好几扇窗,同一件事习惯跟不止一个人讲,谁先同步到最新谁就先落;两边各落一条,查重就全失效;两个复述有出入时,只有他本人能仲裁。曾有一条已被他在 0 号窗当面推翻的判语,仍被落成了正式裁定,过期裁定挂了两天,连锁误工。
**How to apply:** 落正式记录固定三步:拉最新 → 按主题词搜 → 问一句还成立吗。判做对了:没有两条正式记录说同一件事,也没有被推翻的判语落成裁定。
源案例:2026-09-19 某项目一扇 0 号窗在过期的本地状态上数出一个新裁定号,落的时候发现已被别人用掉,而对方同一时刻也把同一件事落了号——设计者当面对 0 号窗说的事,几乎同时对总编也说了一遍,于是立了本条。

### 1.18 设计者说「以后可能会改」:当场把那个数做成唯一入口的可调项,把那块底层做成能整套替换

name: designer-may-change-make-it-tunable
type: feedback
description: 设计者说「以后可能会改」「先这样以后再调」「后续可能我增加」「到时候还能更大」,或问「这个改起来变动大不大」时

1. 这是明确的信号:当场把那个数做成一个具名常量、一个唯一入口,最好不发版就能调;禁止各处各自内联。
2. 分界看「是数值还是结构」,不看属于哪个模块:凡是写成「读一个数 N、循环建 N 个」的,N 就是数值,要可调;版式结构、要重新翻译或重新分发的文案不算。
3. 任务书里写明现在有几处消费端;收尾单列一节「以后要改这个数,改哪一个符号或哪一行配置」。
4. 方向可能被理解反的比例值(消耗还是节省、加成还是减免),实现时就用命名和注释把方向钉死。
5. 随口的「以后可能」不是让你现在去做那件大事:当前的决定照定;只把会变的那块底层做成能整套替换、重新生成的形态,不写死路径。真到那天,走正式记录和拍板,不在做别的活时顺手扩大。

**Why:** 他问「改起来变动大不大」,问的不是有没有权限改,而是改的成本;这个成本在最初实现那一刻就定死了。曾有一个他说以后可能再调的数,落码前才发现有 7 处都要用到它、写法完全一样,若各自内联,以后改一次要动全部消费端,漏一处还不报错。反过来,把「以后可能」当成马上要做的事,又会做错优先级。
**How to apply:** 听到这类话,当轮在任务书里加一节硬要求;交付时全仓搜这个数的字面值,只应命中那一处定义。判做对了:他以后要改,只需改一处,不用重新发版,也不用推倒重来。
源案例:2026-09-19 某项目设计者当窗点名几类按钮、菜单、设置项和槽位后续都可能由他增加,若照当时的写法写死,每加一个都要重新发一次客户端,于是定下按「数值还是结构」分界、数值一律做成远程可调,并立了本条。

### 1.23 给最强档 0 号窗的任务书写短、放权:写要什么效果,不堆一堆「不许」

name: short-brief-for-top-executor
type: feedback
description: 给最强档的 0 号窗写任务书时

1. 大概写需求就够:要什么效果写一段人话 + 一张硬数小表;规格表给路径让它自己读,不整段抄进书里;验收给判据,不给步骤。
2. 通用条款从一堆「不许」改成一节授权:两套口径打架当场判、当场改;顺手能扩的不限本窗范围;没给的数自己定并标「自定」;旧值与母本冲突按母本改。
3. 只留少数几条违反了会直接出事故的红线(撞同一个资源号、绕过一道不可逆的闸、自己上线之类),并写明「这条不是纪律,违反了会直接出事故」。

**Why:** 禁令堆多了,0 号窗会把它们当繁文缛节,真正致命的那几条反而被淹没;给理由比给条数管用,理由本身就是判据。书太长,挤掉的是 0 号窗和你自己的上下文。设计者的原意是这类 0 号窗要的是效率,参数冲突时得有权当场改。
**How to apply:** 写完数一数「不许」有几条,超过三五条就逐条问:违反了真会出事故吗?不会就删。判做对了:书短到一屏看得完大意,0 号窗碰到参数冲突没有停车等裁定。
源案例:2026-09-15 某项目一次派出十三张给最强档 0 号窗的任务书,每张 27~29KB、通用条款占六成,设计者看完回复只需大概写需求,于是立了本条。

> 1.24(负责人给 0 号窗只写一张需求单)已并入第 2 节 2.7,本节不重复。

### 1.25 看得见、听得见的产出,先出小样给设计者过目,他点头才批量

name: designer-samples-before-batch
type: feedback
description: 要批量生成图、声音、动画这类要靠眼睛耳朵判好坏的东西时

1. 每种计划批量出的件,先出一小组样本给他过目(附路径,见本节 1.12),他说可以了才批量。
2. 好不好看、好不好听,由他的眼睛耳朵判;不让 AI 给自己的审美打分过关。
3. 不拿「哪种风格好」的取向题问他(见本节 1.2):按既有的形制或锚点出样,只留一次样板确认;不出 A、B 两套方案让他挑。
4. 缺口先量清,一次补齐,不分几批零敲碎打。
5. 能用脚本在后台跑的批量,不挂着窗等,省他按量付的额度。
6. AI 生成效果不够时,改走许可清楚的现成素材库选配、少量合成补缺;每件登记来源与许可。

**Why:** AI 自己审过关的东西,他实机一看仍可能整批返工;先看一小组,错了只废一小组。曾有一批三万八千多帧在批量授权下一次出完,他看后整批喊返工。挂着窗等出图,是按量烧他的钱;他要的是结果,不是取向问答。
**How to apply:** 写批量类任务书先问一句「这单有没有批量生成」;有,就把「不让 AI 自评审美 / 先样本后批量 / 批量走后台脚本」三条写在书的最前面。判做对了:批量开跑之前,工单台上有他对样本点头的原话。
源案例:2026-09-20 某项目 AI 生成的音效被设计者评为效果太差、生成用的提示词也不行,关键的打击声还缺,只能改走现成素材库选配、先出一小批常用件给他听一遍再定,于是立了本条。
