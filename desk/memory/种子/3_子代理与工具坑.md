# 3 · 子代理与工具坑

本节收:子代理会怎样读错、越权被拦、把不该写的写进去,以及 shell、编码、换行、路径、网络、权限、测试链这些工具与环境怎样「报成功却没做成」的经验。读法:派子代理读码或施工前、写 shell 命令与脚本前、拿测试结果或测量数字下结论前读本节。

### 3.1 子代理读的是本地检出,它报的行号和结论只对它读到的那个提交成立

name: subagent-reads-stale-local-checkout
type: feedback
description: 派子代理读码、查某分支是否并入、报行号或数值前想起;子代理默认读本地检出,它可能落后远端主干、不在你以为的提交上,甚至是另一个仓

子代理(以及任何脚本)报出的行号、数值和「并没并入」之类结论,只对它实际读到的那个仓、那个提交成立;它默认读的是本地检出,而本地检出可能落后远端主干几十到几百笔,也可能根本不是你以为的那个提交或那个仓。

**Why:** 子代理报出的「文件:行号」自信又具体,但只对它碰巧读到的那个提交成立;本地检出落后几笔、在哪个提交、属于哪个仓都不会出现在回报里,核的人若也读本地就错上加错;只有所有人都只读远端引用时这条才可省。
**How to apply:** 派子代理的提示词里写死取数命令:先 `git fetch`,再用 `git show <远端>/<主干>:<路径>`、`git grep <模式> <远端>/<主干>` 读远端引用,不读工作区;下结论前先跑 `git rev-parse --show-toplevel`、`git remote get-url <远端名>`(几个仓的远端可能同名,在错的仓里取值照样成功)和 `git rev-parse HEAD`(HEAD 可能游离在无名提交上),核清站在哪个仓、哪个提交;要取某个提交的文件,用 `GIT_INDEX_FILE=<临时索引> git read-tree <提交>` 再带同一变量跑 `git checkout-index -a --prefix=<目标目录>/`,不碰共享工作树;子代理回报推翻先前结论或与别人的数不同时,先问它在哪个仓、哪个提交上看的,对不上就另起子代理按远端引用核对一次;判做对了的标志是每个结论都带仓路径与提交短号。
源案例:2026-09-11 某大型多人在线项目一位执行方在主仓里查本应在另一个仓核的分支头,两仓远端同名、取值成功却取错对象,核对时又在同一个错仓里核,误判「未合并」而二次停工,造成两头互相等待;更早的 2026-09-05 在共用主检出上合并两笔输出正常,`git merge-base --is-ancestor` 却全部失败,原来 HEAD 是游离的、合并落在无名提交上,直到准备推送才发现;2026-09-21 又有一个子代理据落后远端的工作树翻案三条、错了两条,错的两条已写进章程并推上远端,同日出包脚本从共用检出拷资源,一个目录少了几百件,七道闸一条没红,于是立了本条。

### 3.2 几项任务共用一份检出,验证跑到一半代码会被别人悄悄换掉而指标全正常

name: shared-checkout-swaps-code-under-you
type: feedback
description: 几个子代理或窗口可能在同一目录干活、要跑一段耗时的实机验证或取证、要清理一份共享检出时想起

几项独立任务放进同一份物理检出并行,即使约定分时也会互相静默干扰;最隐蔽的一种是验证跑到一半,对方切分支重编了同一份产物,你拿到的结果其实是对方的代码,而所有外部指标都正常。
1. 一单一棵工作树、一条从具体提交号拉出的分支,任务书写死路径与分支名,禁止在共享主检出上干活;任务书只写「cd 到某仓」,会把并行任务全部赶进同一份检出。
2. 耗时的实机验证前后各记一次能唯一标识当前运行代码的指纹(提交号、产物哈希),两次不一致就判本次验证作废重跑。
3. 清理共享检出前先 `git status` 看状态,不是自己留下的改动一律不动。

**Why:** 不是谁的代码写错,是编排把本该独立的产线放进了同一份目录;版本控制察觉不到语义层的互踩,提交会把对方的半成品一起打包,对方编译不过会连带挡住你,共享的追加式记账文件会产生合并解决不了的冲突。
**How to apply:** 派并行子代理时各给一棵独立工作树,提示词开头要它先跑 `git rev-parse --show-toplevel` 核对路径;验证回报里带前后两次指纹;判做对了的标志是任意两个并行任务的 `--show-toplevel` 输出都不同。
源案例:2026-09-05 某大型多人在线项目两张互不相干的单在同一目录同一分支开工,一方刚构建完准备取证,另一方几乎同时切分支重编了同一份产物,取证读到的已是对方改后的代码,而单次看的编译指纹、日志、图像全部正常,险些当作「改动前」的证据交出去;前一天 2026-09-04 有人准备清理这份共享检出,先看了一次状态才发现另一项任务正在上面,险些清掉,于是立了本条。

### 3.4 子代理起草的提交信息会夹带聊天过程与自我纠正,提交前逐句删

name: commit-message-no-chat-residue
type: feedback
description: 子代理或本窗写提交信息、PR 描述时想起;要公开的仓尤其要紧

提交信息只写「改了什么 + 技术原因」;与设计者的对话过程、定位与推广考量、AI 的自我纠正痕迹(「这是我的失误」「上一轮漏了」「用的是哪个模型」)一概不写。子代理起草的提交信息最容易夹带这些,本窗提交前逐句过一遍。

**Why:** git 历史是永久的公开面,读历史的人要知道的是代码为什么这样,聊天过程和自我检讨只会稀释信号,公开仓里还会把内部沟通与策略直接暴露出去;推上公开远端后几乎删不掉。
**How to apply:** 用 `git commit -F <消息文件>` 提交,消息文件先读一遍再提交;首行写模块和做了什么,正文写改动面与原因;看到「上一轮」「我漏了」「按你说的」这类词就删;判做对了的标志是陌生人只读提交信息就知道改了什么、为什么改。
源案例:2026-09-11 某项目一个准备公开的开源仓,连续 18 笔提交信息里对话对象的称呼出现了 10 次,内部渠道推广策略的原话也被原样写进了提交信息,这些内部沟通与策略险些随公开历史永久外露,于是立了本条。

### 3.5 注释、测试名、文档描述都不是实现,陈述「代码怎么做的」只读实现本体

name: comments-and-test-names-are-not-behaviour
type: feedback
description: 子代理或自己要写「代码是这样实现的」「某测试已经验证了某事」之前想起

陈述代码行为只读实际执行的实现本体,不引用注释、文档字符串或测试名;拿某个测试当「已被机器验证」的凭据前,先打开它的实现,看它实际读取、断言的是哪个文件、哪个版本、什么粒度。
1. 注释会随代码演进与实现漂开,长期没人改。
2. 注释里指明的「真源文件」可能早被弃用、换成了新文件;打开它核数值还不够,要顺着调用链确认现在是谁在读它。
3. 测试名承诺「核对 A 与 B 一致」,实现里可能只读了 A 的旧版本、对 B 零覆盖;这种误引一旦出现,还会在后续任务书里被再抄一次。
4. 与 3.6 的边界:本条管「非得陈述实现时读什么」;只想知道某个层叠多年的内部工具会怎么表现时,按 3.6 直接跑它看输出,根本不读码。

**Why:** 取数这一步带着缺陷,结论却被当既定事实写进后续文档,下游按错误前提开工、返工;描述性文字与实际行为之间没有任何机器保证它们同步。
**How to apply:** 子代理回报里凡是「代码是这样做的」,要求附实现本体的文件与行号(按远端主干读),不接受注释原文当证据;任务书写「某测试会核对你的改动」之前,先搜一遍那个测试实际读取的路径;判做对了的标志是每条行为陈述都能指到一段会执行的代码。
源案例:2026-09-04 某大型多人在线项目一张任务书把「某测试会自动核对你的新增条目」写成验收凭据,执行方打开才发现它只读旧版规范、对新增条目零覆盖,2026-09-05 同样的误引又被写进另一张任务书;2026-09-09 又有人引一处注释推断两层渲染逻辑不同源,据此改排序写进任务书,被执行方顶回,同文件紧邻的另一句注释和真实实现都否定了这个推断,于是立了本条。

### 3.6 历史层叠出来的大工具代码派谁读谁出幻觉,问行为就跑它,不读实现

name: layered-tool-code-hallucination-trap
type: feedback
description: 想弄清某个层叠多年的内部核心工具某条命令怎么拦、怎么判,或要给它派修改时想起;总编、总监、0 号窗尤其要想起

一套在很长时间里一条检查接一条检查叠出来、特例互相引用嵌套的内部核心工具,谁去读它的实现都容易觉得「整体懂了、只差这一处」,于是改一处漏三处;只想知道它会怎么表现时,不读实现。
1. 摸行为:看它自带的 `-h` 帮助,或故意真跑一次,看拦截原话与报错原文。
2. 动作之后回读真实状态;它打印的提示可能与实际状态不一致,提示说拦下了,状态其实已经变了。
3. 真要摸底,只派一个只读、限定回答一个具体问题的子代理,拿回一句结论,不派它去「理解整体」,更不让它顺手改。
4. 要改,交给专门维护它的角色,一次只给一件很小的事,验收判据写死成「跑这条命令得到这一行输出」,不写「顺手把相关检查理一遍」;写状态值只走现成的专用写入口,不进内部改。
5. 与 3.5 的边界:3.5 管「非得陈述实现时读什么」(读实现本体,不信注释);本条管「只问行为时根本别读码」,用运行输出代替阅读。

**Why:** 这是与读者能力无关的系统性认知风险:检查层层叠加、例外互相引用,读进去的每一段都像最后一块拼图,复杂度越高越容易自信地错;总编、总监与 0 号窗本该保持上下文干净,不该被这种代码装满;命令的行为有帮助文本和实跑结果可查时,读实现既贵又不准。
**How to apply:** 总编、总监、0 号窗对这类代码不读、不扫、不改;任务书里问行为的地方写成「跑 `<命令> -h` 或跑一次 `<命令>`,贴拦截原话」;派给维护者的单一次一件,判据是一条命令加一行预期输出;判做对了的标志是结论里引的是运行输出,而不是源码片段。
源案例:2026-09-22 某大型多人在线项目负责维护内部核心流程工具的一方反馈「修一次就出一次幻觉,自己动手还是派子代理都一样,可能是一步步加的检查点太多了」,并建议最多让能力较低的模型扫一眼、谁扫谁出幻觉,反复的误判拖慢了对这套工具的维护;此前 2026-09-15 这套工具的一条提交类命令打印了一大段「拦下」提示,实际状态却已跳到下一环节,照提示重试就会走错路,于是立了本条。

### 3.7 搜索得出的「没有」「没人用」「不受影响」有四个系统性盲区

name: negative-search-has-blind-spots
type: feedback
description: 用 grep 之类搜索下「某东西不存在」「这个成员没有消费方」「改这张表不影响别处」的结论前想起

用文本搜索得出否定式结论之前,先证明搜索面够全;下面四类情况搜不到或搜错:
1. 按规则现场计算的审计或逻辑不含任何可命中的字面值,改一张规则表时字面搜索只能找到一半连带面。
2. 带限定符的模式(`对象.成员`)漏掉同一类型在其他文件里的裸引用;语言允许一个类型拆到多个文件(如 C# 的 partial class)时,必须再搜一遍不带限定符的。
3. 用 `head` 限行数时,相关结果可能被截在后面,或被字母序靠前的另一个目录占满;存在性判断先数总数或分目录查,不加 `head`。
4. 命中一个「看着对得上」的结果,可能是废弃但为兼容保留的旧别名;命中要打开看上下文与实际调用链。

**Why:** 否定式结论一旦写进任务书(「预期全绿」「零外部消费者」)就会被下游当事实照搬;搜不到只说明「用这个模式在这个范围里没搜到」,不说明不存在。
**How to apply:** 改规则表前多问一句「有没有按规则现算这张表的审计」;任务书不写「预期全绿」,除非真跑过,改写「预期 N 条红,逐条列出」;回报否定式结论时附上用了哪几个模式、搜了哪些目录、命中总数。
源案例:2026-09-08 某大型多人在线项目改一处规则判定边界,任务书断言「预期全绿」,实际红了三条靠规则现算的审计,字面搜索命中的常量还是已废弃的旧别名;2026-09-11 又有人用截到八行的搜索查某类消息「服务端有没有发送」,八行恰好被另一个目录按字母序占满,得出「完全没有发送逻辑」并报了出去,真正的发送点就在被截掉的部分,于是立了本条。

### 3.8 任何「往某处写」的步骤做完都要换一条路读回核对

name: tool-writes-need-readback
type: feedback
description: 用编辑工具改文件、用 shell 传长文本、用 heredoc 生成源码、提交前后想起;写入报成功不等于写对了

任何往文件、仓、外部系统写东西的步骤,做完都要换一条不经同一管道的路读回核对,对不上就报错并删掉半成品。下面几种都是「报成功而内容已变」:
1. 编辑工具或子代理会悄悄给文件加 UTF-8 BOM:编译、测试全绿,差异里只多一处 `@@ -1 +1 @@`、两行肉眼一样;核法是提交后跑 `git show HEAD:<路径> | head -c 3 | od -An -tx1`,输出不许是 `ef bb bf`,核 blob 不核工作区。
2. 双引号包住的长文本里,反引号被 shell 当命令替换真的执行了(或整段被吃掉),外层命令仍返回 0;长文本先落成文件再按文件传,必须直传就用单引号且正文不含单引号。
3. heredoc 即使用了带引号的定界符,写出的源码里反斜杠转义仍可能被折掉一层;含反斜杠的内容用目标语言的原始字符串或改正斜杠,写完直接读文件核对,不走标准输入管道。
4. `git add` 对带冲突标记的文件照样成功,`add && commit` 就把冲突标记提交进去;提交前先跑 `git diff --cached --check`。

**Why:** 这些变形都不影响编译、测试和退出码,常规差异高亮也不标,唯一征兆在内容本身;BOM 还会在并线时变成莫名冲突、让依赖行首匹配的搜索落空,把「零命中」的判据污染成假的;只有写入链路自带回读校验时这条才可省。
**How to apply:** 每个写入步骤后面紧跟一个读回步骤(读文件、`git show`、查看已发出的正文),回报写「已核 N 个文件均无新增 BOM」这类带数字的句子,不写「已核」两个字了事;发现 BOM 另起一笔提交剥掉,不用 `--amend`;本来就要求带 BOM 的脚本例外,只核改前改后首字节一致;反引号已被误执行时,先看工作目录多了什么,只回退点名的路径,不整体强制重置。
源案例:2026-09-21 某大型多人在线项目一波并行施工里,一个支的两个文件被子代理各加了一个 UTF-8 BOM,同批另一个支九个文件一个没加,编译测试全绿,只在逐文件核 blob 首字节时才露出来;另有两次用双引号传长正文,一次反引号里的构建命令被真的执行、在共用目录里重新生成了产物,一次交给他人的参数名和路径整段被吃掉致对方无法执行,于是立了本条。

### 3.9 仓开了换行符自动转换,工作区的字节和提交里的字节不是一回事

name: autocrlf-worktree-differs-from-blob
type: feedback
description: 用脚本做多行文本替换、判断文件是不是整份被改了、查文件是 LF 还是 CRLF 时想起

开了 `core.autocrlf` 或 `.gitattributes` 换行规则的仓,工作区文件与提交里的 blob 可以是两种换行符;按 blob 的 LF 写的多行匹配锚点,在 CRLF 工作区上会静默落空、不报错,看起来像「这处本来不用改」。
1. 脚本做多行替换,先把锚点换成工作区实际的换行符(或读入后统一转 LF、改完再转回),每处替换后回读确认真的生效、次数对得上。
2. 混合换行(如 `\r\r\n`)会让按行切分的函数多切出行,按行号定位的替换全部错位;替换前后各数一次「非 CRLF 结尾的行数」这类不变量。
3. 判断有没有被整份改坏,看 `git diff --cached --stat` 或 blob,不看工作区显示;编辑工具让工作区整份「换行变了」,提交时多半被归一化掉,是虚惊,改动行数接近全文件行数才可能是真事故。
4. 查一个文件的换行符用 `git ls-files --eol <路径>`(同时显示索引 `i/` 与工作区 `w/` 两侧)或 `od -c`,不凭编辑器显示猜。

**Why:** 换行转换只发生在提交与检出这两个边界,脚本按一边写、在另一边跑,匹配失败不会有任何报错;反过来有人把工作区的换行显示变化当事故去逐字节修,是白费工;仓里所有文件都是 LF 且不做转换时这条才不需要。
**How to apply:** 能用交互式编辑工具就不用脚本批量替换;非用脚本不可,就让替换函数返回替换次数,次数与预期不等就报错退出;改完用该语言的解析器过一遍语法;回报写「替换 N 处,回读 N 处」。

### 3.13 绿数和常量值离开提交号就没法比

### 3.14 整包测试一次跑出的红绿不能直接采信,先分清是不是非确定性

**How to apply:** 在干净检出上连续跑两次,失败数与失败名都复现才下结论,报绿要注明是不是干净树上第一次跑出来的;把资源敏感的子集拆出来单独跑,与其余部分相加才是真实绿数;验收判据写「本单相关的那一组测试」而不写「整包全绿」,也不列固定的「已知会抖」豁免名单;真怀疑自己改坏,开一棵不含改动的对照树在同条件下跑基线。

### 3.15 只钉文本或纯函数的测试,挡不住行为被改坏

name: shape-only-tests-miss-behaviour
type: feedback
description: 写或评估测试断言时想起;尤其是界面控件、事件后应重算的逻辑、「代码里有这一行」式的断言

2. 显示的字对,背后驱动行为的属性值错。

**Why:** 形状对而行为错的组合,改动一多必然出现,这类断言对它完全免疫,会全绿着把生产改坏;测试直接走用户可见的那条路时这条才不需要额外操心。

源案例:2026-09-08 某大型多人在线项目一小时内两次全绿着把生产改坏(下拉列表塌陷、增量更新漏了派生字段);2026-09-11 一次界面移植里显示文字的断言全绿,背后驱动行为的属性值却已被改坏;2026-09-19 又查出一处布局在窗口尺寸变化后不再重算,测它的纯函数测试一直全绿,因为它只在启动时被调用过一次,于是立了本条。

type: feedback
description: 要把某个账户限制成只读、或宣布「权限已收紧」之前想起;Windows NTFS 这类继承叠加的权限模型

在 NTFS 这类权限从父级继承并叠加的模型里,给某账户追加一条只读授权,收不回它从上层继承来的修改权限;要真正限制必须用显式拒绝规则,核实时看目标路径含全部继承来源的完整权限表,不只看自己刚加的那一行。

**Why:** 授权规则只会叠加,不会互相抵消或收窄,只有拒绝规则能盖过授权;只看新加的那一行,等于只看到局部。
**How to apply:** 用 `icacls <路径>` 看完整权限表(带 `(I)` 的是继承来的);要限制就加拒绝规则,或断开继承后重设;宣布「已限制」之前让被限账户实际做一次写操作,被拒才算数。
源案例:2026-09-05 某大型多人在线项目给一个共享账户的目录加了只读规则,在权限列表里看到这一条就宣布「只能读」,结果该账户照样改了文件,因为上层继承来的修改权限一直都在,于是立了本条。
