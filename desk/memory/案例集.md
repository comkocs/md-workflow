# 案例集 · 通用经验种子的来由

本件是 `desk/memory/种子/` 七个分节的附录:把每一条种子末尾那一行来由(哪天、某类项目撞了什么、代价多大、于是立了哪条)按节汇成一份,给读产品文档的人看「这条规矩是怎么来的」。另含五条不对应种子的独立流程案例。规则本体、Why、How to apply 仍以各分节文件为准,本件不重述。

写法:每条一行,`- **<节.序>** <故事> → 立:「<那条的标题>」`;项目一律写「某项目」或「某大型多人在线项目」,角色只写设计者、总编、总监、0 号窗、子代理,日期与数字保留。分节里已并入别条、只留指向的序号,本件不再单列(它们的来由已并进被指向那条)。

核对:种子映射案例条数 = 七个分节里 `源案例:` 行的总数;独立流程案例不对应种子。案例集总条数 = 种子映射案例条数 + 独立流程案例条数。`grep -c '^- \*\*' desk/memory/案例集.md` 得总数;`cat desk/memory/种子/*.md | grep -c '^源案例:'` 得种子数;`grep -c '^- \*\*流程案例-' desk/memory/案例集.md` 得独立案例数,总数减独立案例数必须等于种子数。作废清单的来由行仍由各条自带,不重复收进本件。

- **7.26** 2026-09-18 某大型多人在线项目部署脚本每次导出的配置默认值语句在键已存在时是空操作,线上表几千行,记录运营手改的审计表却是零行,全是历次部署留下的旧默认值,改代码里的默认值对线上一条都没生效;09-23 又撞反方向:删了一批不再用的配置键,库里的旧行还在,新版启动校验遇到未知键直接拒绝启动,服务陷入崩溃重启循环。 → 立:「配置种子「键已存在就跳过」时,改默认值对线上已有的键无效,删键不清库会让服务起不来」
- **7.27** 2026-09-25 某大型多人在线项目一次停服改库,事前用只读子代理加本机反序列化排掉了草稿里三处必出问题的地方,执行时仍撞上两处:对 JSON 里的数字加一后被库存成浮点型,应用按无符号整型读,服务启动全量加载时抛异常、起不来;另一处拿只匹配字符串的库函数查数值序号的占用,等于没查。 → 立:「停服直接改线上库:库端函数的类型与匹配语义和应用不一样,改完先按应用自己的读法读一遍」

## 八 · 独立流程案例(5 条,不对应种子)

- **流程案例-6** 某项目多窗共用同一数据库实例,DDL 排队互卡,单换端口也无用。为什么有这条规矩:每窗独立数据库实例和专用数据目录,并约定排队,才能避免共享实例互卡。 → 立:「每窗独立数据库实例」
- **流程案例-8** 某项目的 AI 测试通道按固定清单复测,执行席只报通过或不通过,复检席审计判红绿后把红项转问题单,工具焦点与超时单列环境限制。为什么有这条规矩:AI 测试通道归复检席,执行结果有明确判定者,环境红不冒充功能红。 → 立:「AI 测试通道归复检席」
- **流程案例-10** 某项目打包员与测试调度反复接受轮次调用,各用一张常驻单,喊一轮跑一轮。为什么有这条规矩:相同职责的复跑不用每轮新建再结单,轮次结果仍能回到同一单核查。 → 立:「反复调用的职责使用常驻单」
- **流程案例-14** 某项目交付含仓外文件,仓提交本身不能证明打包收到的是哪份文件,于是 settle 前把 SHA256 写进打包清单,打包员出包前逐条核。为什么有这条规矩:仓外文件也要有可比对的交付锚,才能确认收到与打包的是同一份。 → 立:「仓外件加 SHA256 打包锚」
- **流程案例-16** 某项目由设计者在电脑前手动让项目目录外、无项目记忆索引的激活员专窗发送缓存保活,不用定时心跳,没有「续全部」,断线超过一小时不激活。为什么有这条规矩:该保活仅在设计者手动操作时发生,不把专窗变成自动唤醒所有工作窗的入口。 → 立:「激活员窗手动保活」
