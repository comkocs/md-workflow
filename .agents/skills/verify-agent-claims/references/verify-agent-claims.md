# 核子代理与他人报告 · 精简步骤

本文件就是完整做法,照着做即可,不用另找原文;和别处说法对不上时,以本 skill 为准。来由:多窗口、多子代理一起干活时,反复出现几种误判——读了落后的版本、搜索范围不全、把注释当成实现、写完没读回、肯定答复没问基准。下面每一步对着其中一种。

## 先做的两件

1. 给收到的结论归类:否定式(没有、没人用、不受影响、没并入),肯定式(已做、已写入、已验证、是最新),预言式(会崩、会红、预期全绿),行为陈述(代码是这样做的)。后面按类走对应一步。
2. 问它对着哪个仓、哪个提交量的:回报没带仓路径与提交短号的先补问,说不清的结论不采信。

## 对远端主干量

3. 自己复核时先从 {{代码托管远端}} 取最新,用 `git show {{远端主支}}:<路径>`、`git grep <模式> {{远端主支}}` 读远端引用,不读工作区。
4. 下结论前核清自己站在哪:哪个仓(看远端地址,几个仓的远端可能同名)、HEAD 在哪个提交(可能游离)。做法是各跑一次:`git rev-parse --show-toplevel` 打出仓根路径,`git remote get-url {{代码托管远端}}` 打出远端地址,`git rev-parse HEAD` 打出当前提交号;哪一条和你预期的不一样,先停下查清再往下。
5. 要派人复核时,把第 3 步的取数命令写死进提示词,不让它默认读本地检出;交子代理做,平台没有子代理就自己做。

## 翻案举证加倍

6. 回报推翻先前结论、或与别人的数对不上:先问它在哪个仓、哪个提交看的;对不上就另起一个按远端引用再核一次,不凭单份回报改口。

## 按类核

7. 否定式:要它附用了哪几个模式、搜了哪些目录、命中总数;逐个过四个盲区——按规则现算的逻辑没有字面值、带限定符漏了裸引用、限行数截掉了结果、命中的是旧别名。四个盲区各自的过法:改的是一张规则表,先问有没有检查或审计按这张表现场推算,有就把它们算进受影响的范围;搜过 `对象.成员` 这类带前缀的写法后,再只搜成员名一遍,同一个类型可能分散写在好几个文件里;判断「有没有」时先看总命中数或按目录分开搜,不截行;命中了也要打开看上下文和实际调用方,排除早已停用、只为兼容才留着的旧名字。
8. 行为陈述(代码是这样做的、某测试已核过):只认按远端主干读到的实现本体文件与行号,注释、测试名、文档描述不算证据;拿测试当凭据前先打开看它实际读哪个文件、断言什么。
9. 肯定式里的「已写入、已提交、已改好」:换一条不经同一管道的路读回(读文件、看提交里的内容),核新增 BOM、反引号被吞或被执行、反斜杠被折、冲突标记被提交;回报要带数字,如「已核 N 个文件」。具体核法:BOM 对着提交里的文件查,`git show <提交>:<路径> | head -c 3 | od -An -tx1` 打出 `ef bb bf` 就是多了 BOM;冲突标记在提交前用 `git diff --cached --check` 查;反引号和反斜杠打开写出来的文件逐处对原文,命令返回 0 不算数。
10. 肯定式里的「是、已处理、是最新、已包含」:追问拿什么算的——日期、路径、单位、时区、编码、对着哪个提交,逐一与本次对象对,一样对不上就不作数。
11. 预言式:没真跑过的不采信;要么在 {{远端主支}} 的提交上真跑一次附原样输出,要么改写成「预期 N 条红,逐条列出」。引用的行为依据仍按第 8 步只认实现本体。

## 落结论

12. 采信或推翻后写进文档时,每个结论带仓路径、提交短号与取证命令;推翻的写明原结论错在哪一步(读错提交、搜索盲区、读了注释、没读回)。
