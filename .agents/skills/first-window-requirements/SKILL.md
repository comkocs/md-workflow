## 这个 skill 是干什么的(人话)

这个 skill 帮你在新项目开工前归纳十题填需求卡、按尺子判档、裁出作业规矩、选预设、确认三件方案、拆好单并填好规范,准备齐了先问用户,用户说建才建仓。骨架都在本目录,不需要另外安装框架;需同时拷 `desk/真源/`(通用包)。

## 分类

分类:单独装即可用

## 用前填这几个名字

- {{开窗目录}}:首次需求对接窗所在目录;建仓前的产出只放它下面的 `需求/`。
- {{办公目录}}:后续建好的办公仓目录;本 skill 不提前创建它。
- {{拍板人}}:最终确认需求与方案的人。
- {{参数表位置}}:本项目存放路径等参数的参数表位置,填代码规范时用。

## 什么时候用

不管用户提示词怎么写,新项目先走「首次需求对接」;点头前除 `需求/` 外不建文件,十题、档、裁剪、预设与岗位合成一次判定报告请用户确认。

窗由总编兼策划,第一句自报「本窗是首次需求对接窗」;每步完成回拍板人一句,用人话三段 ≤ 8 行。只从需求原话取需求,落件时逐字保留,不编功能。派遣档位只用顶级 / 困难 / 日常 / 轻量,不写具体模型名。

只聊天的窗用 `desk/先核对产品需求.md`; `需求/` 已有它出的需求包时,第 1~4 步只补缺。

## 五步

### 对接第 1 步 · 收需求

先用用户给的或 `需求/` 下的产品文档 / 需求包;没有则扫描工作目录含子目录,找到像产品、需求、研发、PRD、SRS、原型的文档或图片,问「按它来?」。仍没有才问做什么、给谁用、第一版要有什么,并提一句可选 `desk/先核对产品需求.md`(任意窗可跑);不在本窗走整套核对。回答逐字落 `{{开窗目录}}/需求/需求原话_<日期>.md`。

### 对接第 2 步 · 归纳十题、需求卡、裁剪、定预设

`desk/真源/` 是通用包,只读、只调用;下面命令都在它下面跑。有 `python` 用 `python`;没有时将 `python -X utf8` 换成 `py -X utf8`,其余参数(含 `-I`)不变。

- 十题:用 `desk/真源/开局向导.md` ② 原表,AI 从产品文档归纳,不逐题问;缺项标明假设,合入一次判定报告请用户确认。
- 需求卡:跑 `python -X utf8 -I 工具/裁剪.py 档案` 看预设,从 `desk/真源/档案/` 拷最近的一份到 `{{开窗目录}}/需求/需求卡.toml` 改值,保留 TOML 引号写法。
- 档:预计代码 ≤ 20 万行定中档、选中型预设;> 20 万行定大档、建议满血预设与按模块加总监;小型一窗到底只在用户点名时用。明写 `[规模] 档`,用户可当场改档。
- 裁剪:先跑 `校验`,再跑 `python -X utf8 -I 工具/裁剪.py 出 --卡 <需求卡> --出 {{开窗目录}}/需求/待确认`,连同十题、需求卡、档与依据、减哪些闸、预设、岗位及 AI 工时合成一次判定报告,用户点头后继续。
- 定预设:判档依据与需求卡路径附在需求原话件末尾,需求卡每挪一处同步改路径;用户点名小型一窗到底时不建办公仓、不装 `core/`,点头后按通用包 ⑥ 将裁出件、需求卡、`本项目自定.md`(如有)与三行 `CLAUDE.md` / `AGENTS.md` 落项目根,收尾提示可走丙岔只装流程。
- 大 / 中:建办公仓搬入 `需求/` 后,把 `作业规矩.md`、`做法建议.md`、`拆掉清单.md`、`裁剪记录.json`、`开窗必读.md`(有才有 `当日口径.md`)、需求卡、`本项目自定.md` 同法挪到 `{{办公目录}}/` 根(需求卡即 `{{办公目录}}/需求卡.toml`,原话件里记的路径随之改);裁出的 `宪法.md` 不落(唯一宪法是 `{{办公目录}}/desk/宪法.md`),落下的 `开窗必读.md` 里「宪法.md」改指 `desk/宪法.md`。

### 对接第 3 步 · 出三件

已有完整产品文档直接用,不重复出三件;需补充时派子代理,思维导图与产品文档用「日常」档,原型图或架构图用「困难」档。下面的产出均在 `{{开窗目录}}/需求/`:

1. `思维导图.md`:用 `references/思维导图骨架.md`,mermaid `mindmap` 的根为产品名,二级为模块,三级为功能点。
2. `产品文档.md`:用 `references/产品文档骨架.md`,六节为目标与用户 / 功能清单按模块 / 非功能要求 / 数据与接口概要 / 第一版范围与不做 / 待拍板题。
3. 有界面出 `原型图.html`:用 `references/原型图骨架.html`,单文件静态线框,不接后端,每页一节标题对应功能清单。无界面(后端、脚本、库)改出 `架构图.md`:用 `references/架构图骨架.md`,mermaid `flowchart` 加接口草图表(名 / 入参 / 出参 / 错误码)。

三件各带「依据:需求原话件第 N 行」引用,把 N 换成真实行号。未明确的信息列为待拍板,不编需求。

### 对接第 4 步 · 对接确认

已有产品文档直接用,不要求重做三件;把需确认的补充内容合入一次判定报告,改动与确认句逐字记入需求原话件。默认按当前最先进、最通行的做法出方案;用户点名老做法或接管老项目时按用户的。与用户要求冲突先提 A / B。

「问岗位」合入一次判定报告:默认总编 + 技术总监,总编规划、技术总监包全部技术,主窗直派子代理、自并、自派独立审计。预计 ≤ 20 万行一律此模式、只激活技术总监一位;> 20 万行才建议按模块加总监。用户可改,勾选逐字落需求原话件。

### 对接第 5 步 · 拆解与规范

按产品文档把功能清单按垂直功能切片拆成模块与单,每单从数据到逻辑到界面到测试一条线能独立交付,不按前端 / 后端 / 数据库平行拆。用 `references/拆解清单骨架.md` 落 `{{开窗目录}}/需求/拆解清单.md`。每单写类型档(甲类大型 / 甲类中小 / 乙 / 丙,按 1,500 行 / 10 文件判),表头为单名 / 模块 / 档 / 依赖 / 验收一句;类型档与派遣的四档不是一回事。

同窗把 `references/代码规范骨架.md` 填成 `{{开窗目录}}/需求/代码规范.md`,填清语言、格式化工具与命令、测试命令。有美术 / 二进制素材才把 `references/素材管理骨架.md` 填成 `{{开窗目录}}/需求/素材管理.md`,没有则不建。填完回一句。

对接确认且成立证据齐后,问用户「现在建仓还是先停」,用户说建才进建仓与起台,不自动建仓。本窗不自己开别的窗,Codex 能开窗也不开;收窗只写三样:可收 / 在等谁 / 下一扇窗开什么。

## 成立证据

产品文档或简答、判定报告、拆解清单、代码规范(素材管理可选)、需求卡在 `{{开窗目录}}/需求/`。后续建办公仓时用 `mv` 搬入 `{{办公目录}}/需求/` 后 `git add`,代码规范、素材管理移到办公目录根;开窗目录不是 git 仓,不在建仓前执行搬入。
