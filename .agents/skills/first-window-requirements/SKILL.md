## 这个 skill 是干什么的(人话)

这个 skill 帮你在新项目开工前问清需求、判规模、确认三件方案、拆好单并填好规范,准备齐了再建仓。骨架都在本目录,不需要另外安装框架。

## 分类

分类:单独装即可用

## 用前填这几个名字

- {{开窗目录}}:首次需求对接窗所在目录;建仓前的产出只放它下面的 `需求/`。
- {{办公目录}}:后续建好的办公仓目录;本 skill 不提前创建它。
- {{拍板人}}:最终确认需求与方案的人。
- {{参数表位置}}:本项目存放路径等参数的参数表位置,填代码规范时用。

## 什么时候用

新项目尚未建仓、要先把需求与第一版范围对清时使用。窗由总编兼策划,第一句自报「本窗是首次需求对接窗」;每步完成回拍板人一句,用人话三段 ≤ 8 行。只从需求原话件取需求,不编功能。派遣档位只用顶级 / 困难 / 日常 / 轻量,不写具体模型名。

## 五步

### 对接第 1 步 · 收需求

用户给了需求文本,逐字落 `{{开窗目录}}/需求/需求原话_<日期>.md`,不改一字。没给则问三题:做什么给谁用 / 哪些功能是第一版必有 / 有没有点名要用的老做法或要接的现有系统。答复逐字落同一件。

### 对接第 2 步 · 判规模

大型 = 代码仓预计 ≥ 50,000 行、在岗位 ≥ 4、用户点名 MMORPG / SaaS / 多端平台,满足任一即选满血预设。其余为中小:预计 ≥ 10,000 行或 ≥ 2 位选中型,否则选小型。结果与依据附在需求原话件末尾,不改原话;另落 `{{开窗目录}}/需求/预设选择.md`,回一句,用户可当场改判。

### 对接第 3 步 · 出三件

派子代理,思维导图与产品文档用「日常」档,原型图或架构图用「困难」档。下面的产出均在 `{{开窗目录}}/需求/`:

1. `思维导图.md`:用 `references/思维导图骨架.md`,mermaid `mindmap` 的根为产品名,二级为模块,三级为功能点。
2. `产品文档.md`:用 `references/产品文档骨架.md`,六节为目标与用户 / 功能清单按模块 / 非功能要求 / 数据与接口概要 / 第一版范围与不做 / 待拍板题。
3. 有界面出 `原型图.html`:用 `references/原型图骨架.html`,单文件静态线框,不接后端,每页一节标题对应功能清单。无界面(后端、脚本、库)改出 `架构图.md`:用 `references/架构图骨架.md`,mermaid `flowchart` 加接口草图表(名 / 入参 / 出参 / 错误码)。

三件各带「依据:需求原话件第 N 行」引用,把 N 换成真实行号。未明确的信息列为待拍板,不编需求。

### 对接第 4 步 · 对接确认

把三件给用户逐项确认,改动逐字记进需求原话件「修订」节,带时刻;确认句也逐字落件。默认一切按当前最先进、最通行的做法出方案(语言、框架、架构、工具链);用户点名老做法或是接管老项目时按用户的。与用户要求冲突先提 A / B 再做,不擅自改。

### 对接第 5 步 · 拆解与规范

按产品文档把功能清单拆成模块与单,用 `references/拆解清单骨架.md` 落 `{{开窗目录}}/需求/拆解清单.md`。每单写类型档(甲类大型 / 甲类中小 / 乙 / 丙,按 1,500 行 / 10 文件判),表头为单名 / 模块 / 档 / 依赖 / 验收一句;类型档与派遣的四档不是一回事。

同窗把 `references/代码规范骨架.md` 填成 `{{开窗目录}}/需求/代码规范.md`,填清语言、格式化工具与命令、测试命令。有美术 / 二进制素材才把 `references/素材管理骨架.md` 填成 `{{开窗目录}}/需求/素材管理.md`,没有则不建。填完回一句,之后才进建仓与起台。

## 成立证据

需求原话件、三件、拆解清单、代码规范(素材管理可选)、预设选择共 ≥ 6 件在 `{{开窗目录}}/需求/`,缺一件不进建仓。后续建办公仓时用 `mv` 搬入 `{{办公目录}}/需求/` 后 `git add`,代码规范、素材管理移到办公目录根;开窗目录不是 git 仓,不在建仓前执行搬入。
