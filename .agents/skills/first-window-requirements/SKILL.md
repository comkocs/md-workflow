## 这个 skill 是干什么的(人话)

这个 skill 帮你在新项目开工前归纳十题填需求卡、按尺子判档、裁出作业规矩、选预设、确认三件方案、拆好单并填好规范,准备齐了再建仓。骨架都在本目录,不需要另外安装框架;需同时拷 `desk/真源/`(通用包)。

## 分类

分类:单独装即可用

## 用前填这几个名字

- {{开窗目录}}:首次需求对接窗所在目录;建仓前的产出只放它下面的 `需求/`。
- {{办公目录}}:后续建好的办公仓目录;本 skill 不提前创建它。
- {{拍板人}}:最终确认需求与方案的人。
- {{参数表位置}}:本项目存放路径等参数的参数表位置,填代码规范时用。

## 什么时候用

新项目尚未建仓、要先把需求与第一版范围对清时使用。窗由总编兼策划,第一句自报「本窗是首次需求对接窗」;每步完成回拍板人一句,用人话三段 ≤ 8 行。只从需求原话件取需求,不编功能。派遣档位只用顶级 / 困难 / 日常 / 轻量,不写具体模型名。

## 五步

### 对接第 1 步 · 收需求

用户给了需求文本,逐字落 `{{开窗目录}}/需求/需求原话_<日期>.md`,不改一字。没给则问三题:做什么给谁用 / 哪些功能是第一版必有 / 有没有点名要用的老做法或要接的现有系统。答复逐字落同一件。

### 对接第 2 步 · 归纳十题、需求卡、裁剪、定预设

`desk/真源/` 是通用包,只读、只调用;下面命令都在它下面跑。

- 十题:用 `desk/真源/开局向导.md` ② 原表,不另写。首窗把已说清的归纳成答案,逐条列「已定」;没说的列「推荐缺省」;只把「要您答」的一次问完。用户说「按推荐」或当场改。
- 需求卡:跑 `python -X utf8 -I 工具/裁剪.py 档案` 看预设,从 `desk/真源/档案/` 拷最近的一份到 `{{开窗目录}}/需求/需求卡.toml` 改值,保留 TOML 引号写法。
- 档:本仓尺子定,明写 `[规模] 档`(通用包 ③「明确填写档时,以档为准」)。大 = 分工位 ≥ 4 **且**(预计代码 ≥ 50,000 行 或 点名 SaaS / 网络游戏 / 大型单机游戏 / 多端平台);中 = 分工位 ≥ 2 **或** 预计代码 ≥ 10,000 行 **或** 要上线持续运营;小 = 其余。道理:协调尺 = 分工位,留痕尺 = 代码量 / 上线。
- 裁剪:先跑 `校验`,再跑 `python -X utf8 -I 工具/裁剪.py 出 --卡 <需求卡> --出 {{开窗目录}}/需求/待确认`,按 ⑤「给决策者的话」报一次,点头后继续。
- 定预设:判档依据与需求卡路径附在需求原话件末尾,需求卡每挪一处,原话件里的路径同步改成新位置;用户可当场改档。大 → 满血预设,中 → 中型预设。小 → 不建办公仓、不装 `core/`,通用包一窗到底:`需求/待确认/` 生成件、需求卡(落 `{{开窗目录}}/需求卡.toml`)、`本项目自定.md`(如有)与三行 `CLAUDE.md` / `AGENTS.md` 照 ⑥ 落项目根后收尾;收尾话告诉用户「以后要工单台 / 总监位,装 md-workflow 全套,走其开局向导丙岔『只装流程』」。
- 大 / 中:建办公仓搬入 `需求/` 后,把 `作业规矩.md`、`做法建议.md`、`拆掉清单.md`、`裁剪记录.json`、`开窗必读.md`(有才有 `当日口径.md`)、需求卡、`本项目自定.md` 同法挪到 `{{办公目录}}/` 根(需求卡即 `{{办公目录}}/需求卡.toml`,原话件里记的路径随之改);裁出的 `宪法.md` 不落(唯一宪法是 `{{办公目录}}/desk/宪法.md`),落下的 `开窗必读.md` 里「宪法.md」改指 `desk/宪法.md`。

### 对接第 3 步 · 出三件

派子代理,思维导图与产品文档用「日常」档,原型图或架构图用「困难」档。下面的产出均在 `{{开窗目录}}/需求/`:

1. `思维导图.md`:用 `references/思维导图骨架.md`,mermaid `mindmap` 的根为产品名,二级为模块,三级为功能点。
2. `产品文档.md`:用 `references/产品文档骨架.md`,六节为目标与用户 / 功能清单按模块 / 非功能要求 / 数据与接口概要 / 第一版范围与不做 / 待拍板题。
3. 有界面出 `原型图.html`:用 `references/原型图骨架.html`,单文件静态线框,不接后端,每页一节标题对应功能清单。无界面(后端、脚本、库)改出 `架构图.md`:用 `references/架构图骨架.md`,mermaid `flowchart` 加接口草图表(名 / 入参 / 出参 / 错误码)。

三件各带「依据:需求原话件第 N 行」引用,把 N 换成真实行号。未明确的信息列为待拍板,不编需求。

### 对接第 4 步 · 对接确认

把三件给用户逐项确认,改动逐字记进需求原话件「修订」节,带时刻;确认句也逐字落件。默认一切按当前最先进、最通行的做法出方案(语言、框架、架构、工具链);用户点名老做法或是接管老项目时按用户的。与用户要求冲突先提 A / B 再做,不擅自改。

### 对接第 5 步 · 拆解与规范

按产品文档把功能清单拆成模块与单,用 `references/拆解清单骨架.md` 落 `{{开窗目录}}/需求/拆解清单.md`。每单写类型档(甲类大型 / 甲类中小 / 乙 / 丙,按 1,500 行 / 10 文件判),表头为单名 / 模块 / 档 / 依赖 / 验收一句;类型档与派遣的四档不是一回事。

同窗把 `references/代码规范骨架.md` 填成 `{{开窗目录}}/需求/代码规范.md`,填清语言、格式化工具与命令、测试命令。有美术 / 二进制素材才把 `references/素材管理骨架.md` 填成 `{{开窗目录}}/需求/素材管理.md`,没有则不建。填完回一句,之后才进建仓与起台。

## 成立证据

需求原话件、三件、拆解清单、代码规范(素材管理可选)、需求卡共 ≥ 6 件在 `{{开窗目录}}/需求/`,缺一件不进建仓。后续建办公仓时用 `mv` 搬入 `{{办公目录}}/需求/` 后 `git add`,代码规范、素材管理移到办公目录根;开窗目录不是 git 仓,不在建仓前执行搬入。
