# 怎么开始

`python tools/tickets/ticket.py serve --open` 起本地服务并在浏览器里打开可编辑工单台（默认 `127.0.0.1:8787`）。
命令行工位用 `python tools/tickets/ticket.py <子命令>`（本文命令都在 `<仓根>/core/` 下执行，即 `<仓根>/core/tools/tickets/ticket.py`）。
远程部署用 `python tools/tickets/ticket.py serve --host 0.0.0.0 --token <本次令牌>`。

# 工单数据层

工单真数据默认位于仓内 `core/data/`（已被 `core/.gitignore` 排除，不进入任何 Git 仓库）；设置环境变量 `TICKET_DESK_ROOT` 可改到别处。仓里提交的只有模型、命令行工具、网页和测试。

目录固定为：

```text
slots.json                 总监位、主力模型集合、模型名册（新库初值取自 core/desk_config.json）
items/T-000001.json        一单一文件
img/T-000001-01.jpg        压缩后的证据图片
log.jsonl                  只追加的状态审计日志
counter.json               六位工单号计数
state.json                 当前值面：全项目当天在变的那几个数
threads/<总监位>.jsonl     设计者、该总监、总编排三方对话
staff.json                 各位员工编号、在岗状态和经手工单
```

位表（总监位名、复检/平台/总编排三个特殊位、只发需求的位、任务档、模型名册、停用阈值、启用的扩展）来自配置文件 `core/desk_config.json`，代码里不写死；环境变量 `TICKET_DESK_CONFIG` 可指向另一份**完整**配置（整份替换，不是叠加）。默认配置的位是 前端、后端、内容、复检、平台、需求分发（只发需求）、总编；模型名册是本项目在用的 `opus`、`fable`、`codex`（主力，可接全部档）与 `sonnet`（上限乙档）、`haiku`（上限丙档）。

## 当前值面

**规矩落宪法，当前值落这里一处，两处不重复存。**

这几个数每天都在变。谁把它转抄进自己的接管件，抄件就再也不会自己更新——
曾有一张单正是照着抄错的判据图尺寸做的，整张作废。所以：**读它，不要抄它。**

四项是什么（键即真源名）：

| 顶栏那一项 | 键 | 是什么 | 怎么写 |
| --- | --- | --- | --- |
| 判据图 | `judging_resolution` | 判据图尺寸 | `1280x720` |
| 部署头 | `deploy_head_engine` / `deploy_head_server` | 两仓当前部署头 | 7～40 位十六进制短提交号 |
| 走/跑 | `walk_run_speed` | 走档与跑档速度 | `走=1.6,跑=3.2`，或 JSON `{"走":1.6,"跑":3.2}` |
| 已改未并公共工具 | `pending_shared_tools` | 已改未并的公共工具，一条一句状态 | `打包脚本=已改未并,在 feat/pack 上；ticket.py=T-000001 待复检`，或 JSON 列表；一个都没有写 `无` |

谁能改：**只有复检位与总编排位**（默认配置里叫 `复检` 与 `总编`）。别位总监与员工一律拒，
报错里会把这两个位名列出来。键不认识也拒，并把合法键全部列出来。
每改一次都往 `log.jsonl` 追一条 `state-set`：谁、何时、哪个键、旧值 → 新值。

各位怎么读（三条路，都是同一份值，任选一条）：

```bash
python tools/tickets/ticket.py state get                 # 一份 JSON，给脚本读
python tools/tickets/ticket.py receipt <一个单号>          # 最后一行就是四项摘要
```

- 网页顶栏常显这四项，鼠标悬停看这一项最近一次是谁、何时、旧值→新值改的。
- 没人填过的项，三处都显示「未填」，绝不预置假值——**工单台不替复检位填任何一个数**。
- 员工窗第 0 步跑 `receipt` 就已经看见这四项了，不必再去翻接管件。

改（只有那两位跑得动）：

```bash
python tools/tickets/ticket.py state set judging_resolution 1280x720 --by 复检
```

服务端旧版还没上这一版时，`receipt` 不会打出摘要行（服务端不回这一格，客户端就不硬编一行空的）；
`state get` 会被服务端当成不认识的命令拒掉。两种都不是本机坏了，是那台还没上服。

## 图片压缩与落盘

工单图片长边上限为 1280 像素，单张上限为 200KB。透明图输出 WEBP，质量依次尝试
85、79、73、67、61、55、50；不透明图输出 JPEG，质量依次尝试
88、82、76、70、64、58、52、50。第一轮到质量 50 仍超限时，长边缩至当前的
85% 后再跑同一轮质量档位；第二轮仍超限才拒收，并在错误里报告最终质量、长边和大小。

所有 `img/` 写入（附件、迁移和导出）都先写到同目录的 `<文件名>.tmp`，完成 flush/fsync
后再用 `os.replace` 原子替换最终文件。同名图片仍按原规则覆盖，但进程在写入中途退出时，
读者只会看到完整旧文件或看不到最终文件，不会读到半张图片。

设置环境变量 `TICKET_DESK_ROOT` 可把根目录改到测试临时目录；不设置就落在仓内默认数据根 `core/data/`。

## 状态进入时间与停滞告警

每张工单的 `状态进入时间` 只在状态真正变化时更新。`set --deliverable`、改任务书路径、附图等同状态操作仍会更新 `最后更新时间`，但不会把停滞计时清零。存量数据缺字段时，读取告警会回落到 `最后更新时间`，不会报错。

停滞阈值的服务端常量在 `tools/tickets/service.py` 的 `STALE_STATE_HOURS`，浏览器同名常量在 `tools/browser/tickets.js`；调整时必须同步修改两处：

| 状态 | 阈值（小时） | 说明 |
| --- | ---: | --- |
| 新建·已开窗 | 4 | 浏览器按服务端「已开窗」字段判断；旧包没带字段时才回落到 `deskOpened:<单号>` |
| 新建·未开窗 | 24 | 尚未派出或尚未传达 |
| 已认领 | 8 | 防止员工漏跑 `submit` |
| 返工 | 8 | 等设计者重新传达 |
| 待判 | 4 | 等所属总监判卷 |
| 待复检 | 8 | 等复检位跟进 |
| 已合并 | 24 | 等上服或实机验证 |
| 待答 | 24 | 需求、疑问等人答复 |

关闭、作废、实机复验过、阻塞不算停滞；阻塞继续在日览的阻塞段单列。

## 「已开窗」字段

「已开窗」现在保存在服务端工单上，而不是只记在某一台浏览器。设计者点【已开窗】成功后，服务端写入 `{"轮次": <当前返工次数>, "时间": <登记时间>, "实际模型": <本次模型>, "实际平台": <本次平台或空串>}`；「实际平台」可选（取值同建议窗口的四个平台名 claude/codex/vscode/zcode），不填就是空串、不影响任何现有行为，留着以后按平台看合格率。判卷判退时把字段清成 `null`，让该单立即回到设计者的「要你传达的」并提示重新开窗。判过、关闭等终态不清这个字段，保留它作为历史记录。

前端先比较服务端字段的「轮次」与当前「返工次数」：相同才认作本轮已开窗；服务端明确返回 `null` 时直接认作未开窗，不再让浏览器里残留的 `deskOpened:<单号>` 把返工单藏起来。只有旧服务端或旧回落快照完全没有「已开窗」这个键时，新前端才沿用原来的 localStorage 规则。旧单读取时会在内存中补成 `null`，无需跑迁移。

存量文件库可从 `log.jsonl` 倒推补齐。命令逐单顺序读取日志，取状态相对该单上一条日志发生变化的最后时间；没有有效日志则用发起时间。已有值默认不覆盖，所以可重复执行：

```powershell
python tools/tickets/ticket.py migrate --backfill-state-time
```

服务器 SQLite 库维护时显式指定数据库；确需重算已有值才加 `--force`：

```powershell
python tools/tickets/ticket.py migrate --backfill-state-time --db D:/path/to/tickets.sqlite
python tools/tickets/ticket.py migrate --backfill-state-time --db D:/path/to/tickets.sqlite --force
```

## 两个入口

- AI 工位窗主要使用 `python tools/tickets/ticket.py <子命令>` 写单、推进状态、发言和查看未读。
- 设计者与总编排用 `python tools/tickets/ticket.py serve --open` 起本地服务，在浏览器里阅读、答复和拍板；页面不再要求选择目录。直接打开 `file://` 时只读 `tools/browser/data/tickets-bundle.js`。

常用例子：

```powershell
python tools/tickets/ticket.py staff new --slot 前端 --tool opus
python tools/tickets/ticket.py new --type 派单 --slot 前端 --title "接入设置面板" --source "需求.md:设置面板" --consumer "设置页" --deliverable "web/ui/settings_panel.html" --assign "前端-01" --tier 乙 --player-facing --window codex
python tools/tickets/ticket.py claim T-000001 --by "前端-01"
python tools/tickets/ticket.py transfer T-000001 --to 总编 --reason "需要统一跨位验收口径" --by 前端
python tools/tickets/ticket.py receipt T-000001
python tools/tickets/ticket.py build
```

所有子命令都可在任意位置加 `--json`，供 AI 窗稳定解析。拦截失败退出码为 2，错误正文使用人话。

## 建议窗口（开窗工具建议）

派单要指定开窗工具时，**标题第一个字起**写 `【claude】`、`【codex】`、`【vscode】`、`【zcode】` 之一（全角方括号），例如 `【codex】生图:首页横幅`。服务端把标题开头的这个标签解析成「建议窗口」，显示在卡片的任务档旁边，设计者队列可以按工具筛。标题开头不写标签的，由设计者随机指派工具开窗。

**这是建议不是硬闸**：留空放行，标题开头写了个不认识的标签（比如已经作废的 `【cursor】`）也照样建得出来，只是解析不出标签、当成留空。

怎么选（两轮实测经验）：

- 要从文字生成图片的活**一律 `codex`**——它是唯一实测带 imagegen 的窗，`zcode` 与 `claude` 窗都没有。生图任务书第一步仍要写死「先试生一张，生不出立刻建阻塞单收窗」。
- `zcode` 留给切图 / 套卡面 / 排板 / 缩放 / 色相迁移 / 按规格核验 / 看图判卷。★`zcode` 窗默认跑的是**中低端模型档**，别把甲档代码活派给它。
- 代码、判卷、量测类不限，留空即可（`claude` 与 `vscode` 写代码优质，`vscode` 与 `codex` 插件多）。

**真源只有标题这一处。** 单上的「建议窗口」是从标题解析出来的派生值，每次读单都按当时的标题重算一遍并覆盖，所以它不会和标题各说一套。开窗指令那三行**一个平台名都不出现**——工具名只写在标题开头，设计者从标题就看得见，不必再往贴进员工窗的那两行里塞。

`new --window` 与 `set --window` 是**替你把前缀写进标题**的快捷方式：`claude` / `codex` / `vscode` / `zcode` 四选一，标题已经有前缀时是**替换不是叠加**；给空串（`set --window ""`）就是撤回建议，把前缀连标签一起去掉。填了不认识的值才拒，拒的时候把四个合法值原样列出来。自己在标题里直接敲 `【codex】` 效果完全一样——服务端旧版本还没上到能认 `--window` 时，这就是可用的写法。

每张派单必须显式填 `--tier 甲|乙|丙`，并用一个或多个 `--deliverable` 逐项写出必须产出的文件；只要其中一项在路径或工单 `img/` 中找不到，整单不能交板。丙档还必须填 `--context-lines`，且不超过 2000 行；丙档导出时使用随工具包提供的 `tools/tickets/templates/丙档任务书模板.md` 受限骨架。

`new` 建派单和 `set --deliverable` 改单时，命令行会先在操作人当前检出中逐项看一眼交付路径，再把请求发给服务端。**建单只核形态，不核存在**：形态不像路径的（既没有路径分隔符也没有扩展名，或者没有分隔符但含“。，,的”这类叙述标记）会拦下并报 `交付项要写成仓内相对路径或真实文件路径,叙述句永远交不了板。这一条:<原文>`；带路径分隔符的一律当成路径，不再拿“的”去判它。形态是路径但当前检出里还没有这个文件时，**只打一行提醒、退出码仍为 0，单照常建得出来**：`提醒:以下交付项现在还不存在,单照常建/改,但交板时会被逐条核`，并顺带说明只会存在于其他分支上的产物（比如只推到部署分支上的部署件）到交板时仍会被同一条闸拦下——那一类请建单时就改成提交端真的会有的路径。被提醒了通常什么都不用做：派单的交付项本来就是“还不存在、要执行方做出来”的东西，做出来再交板即可。冒烟测试确需整条跳过时加 `--deliverable-unchecked`；时间、工单号、操作者、命令、跳过的每条原文及其核验绝对路径都会写进 `log.jsonl`。

（这里为什么不拦：建单时硬拦存在性，等于把所有产出新文件的派单一律拦死，各位只能造空占位文件绕过；而占位件一旦存在，`submit` 那条真闸就永远核得过，闸反而被绕成了摆设。同时“文件存在就跳过叙述词启发式”的保护对派单永远不成立，导致带“的”的合法中文路径 100% 被误判成叙述句、报错还指错方向。）

存在性一律留给交板核：`submit` 的逐项核验原样不动，没有放宽。员工交板时若仍遇到缺文件，错误会列出全部现有交付项组成的完整 `set` 命令，并在命令下方另列“核不到的交付项”，使命令本身可直接复制到 PowerShell 或 Bash。员工没有改单权限是故意的：把该命令原样发给错误中点名的所属总监位，由本位总监或总编排修正；不要删掉看似无关的参数，因为 `--deliverable` 是整条替换，少写一项就会把原来的那一项删除。

建单前先把任务书 md 落盘；`new --taskbook` 与 `set --taskbook` 会在提交端核对文件确实存在。

内部工具单建单：CLI 加 `--internal`，或在总监派单页面勾选“非玩家可感知”。
**建派单必须二选一明写可感知标记**：`--internal`（内部工具单，交板给验证命令与原样输出，不要求实机图）与 `--player-facing`（玩家可感知单，交板时可附一张来源为「真登录」的图，选填）必须给且只能给一个——两个都不给或两个都给都会被拒，服务端是唯一真闸（网页端同样受这道闸：不带 internal 值就被服务端拒）。以前漏标默认“玩家可感知”，内部单要到交板那一刻才发现走错了那一支。非派单类型（疑问/阻塞/需求/拍板）不受这道闸影响。
**建单时标错了也能改回来**：`set <单号> --internal` 改成内部工具单，`set <单号> --player-facing` 改回玩家可感知，两个开关互斥，本位总监、总编排与设计者都能单独翻这一个开关（设计者解卡用），改动连同新旧值写进事件线；`set` 的其他可改项（任务书路径、指派给等）仍然只有本位总监与总编排能改。工单若已经是「阻塞」态，要先 `unblock`——它一律落到「返工」，正好是可改态（可改口径的只有新建/已认领/返工三态）。（曾有一张只改测试断言的内部单漏了 `--internal`，活全干完却在交板时被当时的真登录图片闸拦死；以前只能作废重建或拿无关截图糊弄闸，两条都不该走。现在可感知单附图已改为选填，但标错了照样该改回来：两支交板要的东西不同。）
玩家可感知单交板时附真登录图是**选填**：不附也能交板；附了就照旧挂在单上，来源照记（`attach --origin world` 记成「真登录」，隔离场景图仍记「隔离场景」，不会被算成真登录图）。想附却取不了图时可带 `--shot-blocked "<机器实况/试过什么/卡在哪步>"`（须同时带 `--verify-command` 与 `--raw-output`）如实记账，单上打「欠真登录图」标记，补一张真登录图即清；单上已有真登录图时带它会被拦。标记翻开关仍由该单所属总监位、总编排或设计者跑 `set <单号> --internal --by <位名>`；员工不要自己署总监名去翻开关，那是冒名。
内部工具单交板：不用附真登录图，但 `submit` 必须同时给 `--verify-command` 与 `--raw-output`。
内部工具单复验：复检人重跑交板验证即可通过 `live`；玩家可感知派单 `live` 时附图可选，给了图就挂成一张「真登录」图。
设计者队列里，状态为「已认领」的内部工具单点击【复制催办句】，会复制 `receipt` 与带 `--verify-command`、`--raw-output` 的 `submit` 原话。
玩家可感知单的同一按钮会复制 `receipt`、`attach --origin world`、`submit --evidence` 原话，并在末行提醒先核齐交付项、交板后只回一行回执。

## live 的同图、独图与一图批量

`live` 每次都必须写 `--shot 同图` 或 `--shot 独图`。`同图` 表示整批工单共用一张部署后真登录图；`独图` 表示这张图专为这一张工单拍摄。不写会直接拦下，并提示两个合法取值。

`live` 的附图本身是可选的：玩家可感知单不给图也能复验通过；给了图就挂成一张来源为「真登录」的图。

工单字段“实机图标记”按下面四条记录：

- `--shot 独图`：记“独图”。
- `--shot 同图` 且是非玩家可感知的内部单：记“同图”，不要求图片，事件线写“同图·内部单免图”。
- `--shot 同图` 且是玩家可感知单：记“待独图”。
- `--shot 免独图`：记“免独图”，另把 `--reason` 落进 `免独图原因` 字段（判据见下）。

“待独图”单之后可以再执行一次 `live --shot 独图`：系统把标记改成“独图”（给了图就再挂一张真登录图）、事件线记“补独图”，工单状态仍保持“实机复验过”。其他已经“实机复验过”的单不能重复 live。

`--shot` 的第三种用法是 `免独图`：判语已写明“无玩家可见产出”的诊断类单，以及验证对象已退役、原命题不再成立的单，可以免掉那张独图。四条判据要同时成立才放行——状态是“实机复验过”、实机图标记是“待独图”、`--by` 署名是复检位或总编排位（默认配置里是 `复检` 或 `总编`；带两位编号的员工名也算）、`--reason` 非空。打上后实机图标记记“免独图”，原因落在字段 `免独图原因`，事件线记“免独图 · <原因>”。这条通道不要图、也不能配 `--batch`（批量是给一张图配多张单用的，豁免必须一单一原因）；“已合并”态的首次 `live` 也打不了免独图，欠图这件事得先成立。免独图的单不再计入 `list --shot-pending` 与日览的“待独图 N 张”。

```powershell
python tools/tickets/ticket.py live T-000001 --shot 免独图 --reason "判语已写明无玩家可见产出，属诊断类单" --by "复检-01"
```

一张图批量复验时，首张单号放在 `live` 后面，其余单号重复写 `--batch`；`--shot` 对整批生效。远程模式只上传一次图片，某张单状态不对只跳过该张，不影响其余单。

复检位可直接照抄这一条，再替换单号、图片路径和员工编号：

```powershell
python tools/tickets/ticket.py live T-000001 "<真登录图路径>" --batch T-000002 --batch T-000003 --shot 同图 --by "复检-01"
```

只看仍待补专属图片的工单：

```powershell
python tools/tickets/ticket.py list --shot-pending
```

转交沿用原工单号，派单状态不变，其他工单回到“待答”；原因不能为空，转交历史、双方未读与“今日转交”日览同步记录。拍板单新建或转给设计者时，正文必须依次写满“一、这是什么”“二、选了会怎样”“三、推荐”。总监向别位提事使用 `new --type 疑问|派单 --slot <对方位>` 或 `transfer`，不另开总监间聊天线。

员工登记时 `--tool` 可先填 `待定`；设计者点“已开窗”后选择实际模型与档位，系统再同时写回员工名册与本单“实际模型”。
主力模型集合来自配置文件 `core/desk_config.json` 的「主力模型集合」（新库初值写进 `slots.json`），默认配置是 `opus`、`fable`、`codex`；登记非主力模型不拦，只提醒它一般只吃丙档（步骤逐条写死、上下文预算不超过 2000 行的模板任务书）。

## 模型停用：到线只通知，停不停是人的动作

停用线的数不是读「模型记分」账本，是每次判退时**从工单现算**的：只数「返工原因列表」里判退责任=模型的条目，出题责任、空值一律不计，按**模型基名+任务档**两维归并——`opus`、`opus5`、`opus-high` 归并成 `opus`（照名册前缀匹配）；`<工具>-未标` 归到工具名下并在通知里标「未标」；甲档与乙档各算各的，不互相推。同位 3 次、跨位合计 5 次（配置里的「停用阈值」）仍是停用线，但**到线不再自动停用**。工具只往总编排线和该单所属位线各写一行通知，列出计入的每一笔（单号 · 所属位 · 任务档 · 责任字段），模型仍算可用；停不停由总编排核过责任归属后**手工**落笔。曾有自动停用两次误伤一个主力模型：8 次判退里 2 次判语明写出题责任、3 次是 `-high`/`-ultra` 变体被归并——停用是误判，而一停就是所有该模型的窗全停摆。

手工停用与解禁是对称的一对，都只认设计者/总编排：

```powershell
python tools/tickets/ticket.py staff ban --tool <模型名> --by 总编 --reason "核过责任归属,三次判退确属模型责任"
python tools/tickets/ticket.py staff ban --tool <模型名> --slot "<总监位>" --by 总编 --reason "<一句话>"
python tools/tickets/ticket.py staff unban --tool <模型名> --slot "<总监位>" --by 总编
python tools/tickets/ticket.py staff unban --tool <模型名> --by 设计者
```

- 不带 `--slot` 写全项目，带 `--slot` 只停那一位；`--reason` 必填——误停一次就是那些位全部停摆，理由要留在事件线上备查。
- 主力模型（配置里「主力模型集合」列的那几个，及其变体）只有 `--by 设计者` 能 ban，总编排署名会被连设计者原话一起拒回；非主力模型权限不变。
- 模型名先规范化后再写，所以 `Opus  XHigh` 记成 `opus-xhigh`；`opus` 与 `opus-xhigh` 是两个互不相干的键，通知里报的是哪一个就停哪一个。
- 已在停用中再 `ban` 会被拒；全项目已停时再按位停也拒（范围更大的那条已经生效）。
- 停用后 `staff new`（开新窗）和 `open_window`（登记实际模型）**两条路都被拦**——只拦前者的话，把窗先开成 `待定` 再登记被停的模型就绕过去了。
- 每次 `ban` 在 `log.jsonl` 记一条 `staff-ban` 事件，并在总编排线写一行，含范围、原因和现成的解禁命令。

## 判退的责任归属

`judge --rework` 必须同时写 `--blame 模型|出题`。`模型` 表示执行方做错，会照常累计模型判退；`出题` 表示任务书或判据本身写错，执行方照做无误，不计模型账，只记入该单所属总监位的出题账。判过时不要写 `--blame`。

判语首行也必须把同一结论写给人看：`--blame 模型` 时首行以“模型责任”开头，`--blame 出题` 时首行以“出题责任”开头；两处不一致会拒绝判卷。例如：

```powershell
python tools/tickets/ticket.py judge T-000001 --rework "实际结果不符合验收" --blame 模型 --by 前端 --verdict "模型责任：实现漏掉了验收项。"
python tools/tickets/ticket.py judge T-000002 --rework "任务书引用了错误入口" --blame 出题 --by 前端 --verdict "出题责任：执行方已按任务书完成，但任务书入口写错。"
```

模型记账不区分大小写，并把连续空白与下划线统一成连字符，所以 `Opus  High`、`opus high`、`opus_high` 都记成 `opus-high`；`opus`、`opus-high`、`opus-xhigh` 仍是三个互不相加的键。实际模型未填时不再回落并混入工具名，而是单记为 `<工具名>-未标`。模型名不在「模型名册」（配置 `core/desk_config.json`，库里存于 `slots.json`）时不会挡住判退，只会提醒已按规范化后的字面记账。

达到停用阈值前一次时（同位 2 次、全项目 4 次），系统先在总编排线和该单所属位线各警告一行，并提醒“若其中有出题责任判错了归属，现在用判语首行改还来得及”；到线那一次再各写一行“已到停用线”，同时写明自动停用已关、模型仍算可用。两次都不写 `模型停用`，要停请照上一节手工跑 `staff ban`。

主力模型（配置里的「主力模型集合」，默认配置是 `opus`、`fable`、`codex`）是例外，口径写死在工具里：**主力模型永不停用**，到线的通知只作质量提示（「主力模型不停用，这条只作质量提示，请核一遍归属是否记对」），不再出现“已到停用线”“停不停由…”这类措辞；`staff ban` 对主力模型收紧到只有 `--by 设计者` 能落笔，总编排署名也拒。出处：设计者当面定——主力模型不能停，只能加算力，绝对不能停用。

## 一张单建完之后还能改什么

建完就改不了曾经是四位总监同时撞上的一堵墙。
现在有两条通道：`set` 改口径，`void` 一笔勾销。两条都只认「本位总监或总编排」。

```powershell
python tools/tickets/ticket.py set T-000001 --taskbook "<工作区>/_office/平台/任务书/T-000001_建完就改不了.md" --by 平台
python tools/tickets/ticket.py set T-000001 --assign "平台-06" --by 总编
python tools/tickets/ticket.py set T-000001 --window vscode --by 平台
python tools/tickets/ticket.py void T-000001 --reason "单号猜错了，另建一张" --by 平台
```

| | `set` | `void` |
| --- | --- | --- |
| 能改哪些 | `--taskbook` 任务书路径、`--assign` 指派给、`--source` 真源指针、`--body` 正文、`--consumer` 实机消费者、`--deliverable` 交付项、`--internal`/`--player-facing`、`--window` 建议窗口（claude/codex/vscode/zcode 四选一，改的是标题开头的 `【X】`，已有前缀是替换不是叠加；给空串就是撤回建议。建议不是硬闸）；另有 `--blame` 单独改判退责任 | 状态改为「作废」 |
| 允许的状态 | 新建 / 已认领 / 返工（`--blame` 相反：判过之后的单都行，唯独「待判」不行） | 新建 / 已认领 / 阻塞 |
| 允许谁 | 该单所属总监位 或 总编排 | 该单所属总监位 或 总编排 |
| 必填 | 至少一个可改项（`--blame` 则必须带 `--reason`） | `--reason` |


### 判过了但不并线怎么结

`close <单号> --not-merged --reason "<为什么不并>" --by <位名>`。
用在「判过了,但正确的处置就是不并线」这一类:画风被设计者判废、需求被后来的单取代、探路单的产物是结论不是代码、两支互斥只留一支。
只给派单、只从「待复检 / 待判」走;能这么结的是该单所属位、复检位、总编排位、设计者。
★`--reason` 必填——没有原因的「不并线」,事后和「忘了并」分不清;原因会落进备注与事件日志。
★**从「待判」结要带 `--verdict "<判语>"`**:待判就是还没判过,不带判语这么一关,
单子落成终态却**判卷人与判语都是空**,事后没人说得出这活行不行、是谁看过的。
两条路二选一:先 `judge` 判过再 `close --not-merged`,或者本条命令带 `--verdict` 一并落。
从「待复检」结不要带 `--verdict`——那一态判语已经在单上,带了会被拦。
不并线的单**不套**判卷那道「怎么打开它」的措辞闸:不并线本来就没有「打开它」这回事。

### 本位自有单的并线

三方互斥闸(复检人 ≠ 执行员工 ≠ 判卷人)在别位是对的,但复检位的部署单与平台位的工单台单没有第三个人可选,数学上无解。
现在:所属位、判卷人、复检人三者是同一个位名时放行,落库把复检人写成「<位名>(自记·待设计者终验)」——
不伪装成第三方,谁看都知道这一笔没有第三只眼。别位的三方互斥闸一个字没动。
**`set --blame` 改判退责任归属**。`judge` 只认「待判」态，一判完就再也进不去，
而模型判退是会累计到停用线的硬账 —— 判卷人事后发现自己把出题责任记成了模型责任，以前没有任何路径改回来，
等于让模型替出题人背停用风险。

```powershell
python tools/tickets/ticket.py set T-000001 --blame 出题 --reason "复核后确认是任务书判据写错，执行方照做无误" --by 前端
```

- 状态闸与改口径正好相反：**判过之后的单都能改，唯独「待判」拒**（待判态就该用 `judge --blame` 一次填对，不给第二条路）。
  单上根本没有判退责任的（判过的单不记）也拒。
- 允许 该单所属总监位 与 总编排，别位署名拒；`--reason` 不能为空。
- 一次改三处：单上的「判退责任」、「返工原因列表」最后一条的归属、两本账。
  账的方向是 模型→出题 时模型记分在该位与合计各 −1、出题记分该位 +1，反向则反过来；**两本账都不许减成负数**。
- **停用名单不动**：自动写 bans 已关掉，现在只通知不停用，回滚只管记分；停不停由总编排核过归属后手工决定。
  账一动就往总编排与所属位的对话线各落一行。
- `--blame` 不能和其他可改项写在同一条命令里（两道状态闸相反，混在一起必然打架），要改口径请分两条跑。

边界写死在这几条上：

- 交了板的单（待判及以后）既不许改口径，也不许一笔勾销；要否掉就走判退返工，判过之后只能关闭。
- `--assign` 沿用 `require_active_staff`：必须是本位在册且在岗的员工，别位的员工和已收窗的员工都拦下。
- `--source` 是整条替换，不是追加；全给空值会被拦下，因为真源指针一空这张单就认领不了。
- 每次 `set` 往 `log.jsonl` 追一条 `set` 事件，逐字段记下旧值与新值——只记新值日后查不清是谁改坏的。
- 「作废」是终态：设计者队列不再列它，`deskOpened`/`deskDone`/`deskReviewed` 三键自动清掉，
  总监位页把它归进「已办」，卡片上不再有任何下一步动作。

### `unblock` 一律落「返工」：换书不换号

`unblock` 不再把单还原成「阻塞前状态」，**一律落到「返工」**。理由很直接：单子会被阻塞，
多半正说明任务书要改；而还原成「已认领」就换不了书，总监只能 `void` 掉再建新号，
断点、返工次数、模型账全丢，员工还得从头读一遍。落「返工」之后单号不变，
总监就地 `set <单号> --taskbook <新路径>`（`--body` 同样可改），员工 `claim` 一次即回「已认领」。

- 「阻塞前状态」字段**不再清空**——落点统一之后，这一格是唯一还记得「这张单当初卡在哪一档」的地方，
  查因要靠它；下一次 `block` 会原地覆盖。事件线上也照原样写着「阻塞前是 X」。
- 本来就在返工态被阻塞的单，`unblock` 之后仍是返工，不报错。
- 返工态的卡片会多一行「换书后再认领」，连同当前任务书路径一起摆出来。
- **★「已开窗」戳记同时清掉**：与 `judge --rework` 同一条口径。
  前端 `isOpened()` 判的是「`已开窗.轮次` == `返工次数`」，`wantsDispatch()` 又要求 `!isOpened`；
  `unblock` 从前这两个数一个都不动，`0 == 0` 恒成立，于是**解完阻塞的单根本不进「要你传达的」**，
  要熬过返工那 8 小时线才从折叠着的「卡住了」段冒出来——设计者曾当面撞到：
  一张单解阻塞后他一直反映没看到重新派发的工单。
  旧窗既然按本节口径「不要复用」，旧戳记就不该还算数。**`返工次数` 不动**：那是模型账，
  只有真判退才加一次，不能借着解阻塞悄悄记一笔。

## 任务书路径与 `{ticket}` 占位符

工单记录有一个顶层字段「任务书路径」，开窗指令只认这个服务端字段，不再从真源指针猜，也不读浏览器本地缓存。总监在卡片里填写并点“保存路径”后会通过服务端 `set` 写回；换一台机器或清空浏览器缓存，仍能看到同一个值。

过渡期老单若只在真源指针里写过 md 路径，服务端字段仍算空：总监位页会标“缺任务书”，在卡片输入框补填一次即可。`file://` 打开的回落数据是只读快照，输入框会禁用，必须打开服务模式后再补。

建单前猜不到单号，所以 `--taskbook` 里可以写 `{ticket}`，服务端在分配到单号之后替换成真单号：

```powershell
python tools/tickets/ticket.py new --type 派单 --slot 前端 --title "资源清点" --source "需求.md:资源清点" --consumer "资源页" --deliverable "review/资源清点.csv" --tier 乙 --player-facing --taskbook "<工作区>/_office/前端/任务书/{ticket}_资源清点.md"
```

分配不到单号就根本不会有这张单，库里也永远不会留下一个没替换的 `{ticket}`。
带占位符的建单会在拿到真实单号后由提交端回核最终路径；文件还不存在时单会保留，但不会进入设计者待开队列。
建完之后要改，用上面的 `set --taskbook`。冒烟测试确需先走通命令时可加 `--taskbook-unchecked`，跳过动作、操作者、时间与最终绝对路径都会写入 `log.jsonl`。

## 跨位动作会往对方对话线写一行（设计者靠它知道该唤醒谁）

设计者队列的「要你去唤醒的窗口」只数**对话线未读**：某位对话线里发言人不是该位、且该位没标已读的行数。
所以凡是「A 位对 B 位做了动作、B 位那扇窗必须动手」的场合，服务端都会往 B 位的对话线落一行：

| 动作 | 往谁的对话线写 | 写成什么 |
|---|---|---|
| `new --type 派单` | 所属总监位 | `<发起人> 建了派单 T-x · <标题>` |
| `ask`（疑问/需求/阻塞/拍板） | 所属总监位 + 指派给那一方 | `<发起人> 建了<类型>单 T-x · <标题>` |
| `answer` | 所属总监位 + 跨位单的发起位 | `<答复人> 答了 T-x · <标题>` |
| `transfer` | 转出位 + 转入位 | `转交 T-x：A→B。原因：…` |

`answer` 的署名闸（谁按得动）：拍板＝设计者或总编排；疑问＝所属总监位、设计者、总编排三方；
**阻塞＝所属总监位或总编排**（后来放开，设计者仍答不动）；
**需求＝所属总监位、设计者、总编排三方**（后来放开）；总工单仍只有总编排。
转交过的单以**转交后**的所属总监位为准 —— `transfer` 会把所属总监位改成接收位。

需求单还多一道**前缀闸**：答复正文的第一句首词必须是下面三种之一，三种之外一律拒，
**设计者与总编排答需求时走的是同一条闸，不开后门**：

| 写法 | 用在什么时候 |
|---|---|
| `受理`（后面可跟预计） | 收下了，还没排 |
| `已排期→T-xxxxxx` | 已经派了单，写派单号 |
| `已完成→T-xxxxxx` | 活已经做完交板了，写交板单号 |

带单号的两种会核单号形状（`T-` 加正好六位数字），`已排期→T-12` 这种形状不对的照样拒 ——
写成那样等于没写，查过去只会查到一张不存在的单。
需求单的 `close` 也跟着放开给所属总监位（连同设计者与总编排）：
答复权交出去了、关闭权还捏在总编排手里的话，单子照样落不了地。**派单的关闭路径一个字没动。**

放开的原因（实测）：接收位把活干完了也答不动，只能另建一张疑问单回话，
原单永远挂在「待答」—— 设计者队列上看着是总编排卡了 30 小时，其实活早就做完了。

★**不落这一行，唤醒段就不亮，那扇窗永远不知道有事等它** —— 各位总监的窗口不会自己醒，
没人把话贴进去它就不运行。曾连撞两次，故有此机制。

两条改这块代码时必须守住的：

1. **发言人一律填真正的动作发起人，不能填成目标位自己**。前端过滤条件是「发言人 !== 该位」，
   填成目标位这一行永远不算它的未读，等于没写。自己给自己位建单时发言人本来就等于该位，
   那一行不计未读是对的 —— 不需要唤醒自己。
2. **这一行绕开 `say` 的三方门禁是故意的**。`say` 只收设计者/本位总监/总编排，跨位调用会被拦；
   而这一行是系统替 A 在 B 的账上记一笔，不是 A 跑到 B 的对话线里发言。别把那道门禁补到这里来。

**员工在自己那张单上留一句话**：`say` 的三方门禁之外只开一条很窄的缝——
执行方带 `--ref <自己那张单号>` 时可以往**本位**对话线写一行，落库时自动加「【员工留言】」前缀。
判据三条同时成立才放行：带了 `--ref`、他是**这个位**在册在岗的员工、那张单的「指派给」正是他本人；
不带 `--ref`、不是自己的单、或想写别位的线，一律照旧拒。
为什么开这条缝：原来员工遇到卡点没有任何一条不改状态的留言路径（`block` 会改状态、`submit` 要等活干完），
只能停在半路等人来问——曾有员工在自己的单上实撞。
设计者当日口径：闸只能拦「活没做好」，不能因为跟活无关的客观原因把员工卡住。

设计者点【已唤醒】存的是「点的那一刻最新未读的时间戳」，不是布尔值：来了更新的通知，那一位会**重新冒出来**。
CLI 的 `new` 和 `set --taskbook` 成功后会打印与卡片完全相同的三行开窗指令；三行由服务端统一生成。路径为空时只打印补路径提醒，不会拼出半截指令。

## 交板时的两类证据

`submit` 的 `--verify-command` 与 `--raw-output` **两类派单都会保存**，不再只在内部工具单里留下。
以前玩家可感知单的分支把这两个参数收下就扔：员工传了、submit 成功、状态到待判，`show` 出来却是空的，
判卷人看不到执行方到底跑了什么命令、输出是什么。证据静默丢失比报错更坏，因为没有人会发现。

两支各自的闸：

| 单的类型 | 必须有 | 两字段 |
|---|---|---|
| 内部工具单（`--internal`） | 验证命令 **和** 原样输出，缺一不能交板 | 必填 |
| 玩家可感知派单 | 一句话说明；来源为「真登录」的图选填，附了就挂在单上 | 选填，填了就保存 |

玩家可感知单不填两字段、不附图都能交板。但填了就一定留得住，附了的图也照旧挂在单上。

## 员工窗怎么接通道

1. 开工第一句先自检：`python tools/tickets/ticket.py env` —— 一行告诉你现在是本机还是远程、连哪台、令牌文件在不在、配置从哪一级取到。
2. 零配置：总监发的 `remote.env` 放在 `<仓上一级>/tasks/tickets/remote.env`（从仓根往上逐级推算，正式仓与 `_work/` 下的 worktree 都能找到）就自动接上；不在那儿就 `export TICKET_ENV=<remote.env 的正斜杠路径>`。
3. 接上后 `receipt <一个已知单号>` 能打出真标题才算连着服务器；`env` 显示「本机模式」时做的活推不动工单，先接通道再干。

两个 shell 的等价写法（**任务书第 0 步照抄这一段**，路径换成 `remote.env` 的实际位置；写甲乙档任务书的总监从这里抄）：

```bash
set -a; source <仓上一级>/tasks/tickets/remote.env; set +a
```
```powershell
Get-Content <仓上一级>/tasks/tickets/remote.env | ForEach-Object { if ($_ -match '^([A-Za-z_][A-Za-z0-9_]*)=(.*)$') { Set-Item "env:$($matches[1])" $matches[2].Trim() } }
```

默认窗就是 PowerShell 的走下面那段——`set -a; source …` 在 PS 里跑不通，
曾有五张单实撞。值逐窗不同，按 `remote.env` 自读置 `$env:键`，**别把键值抄死**。
★写 `.ps1` 且含中文的存 UTF-8 **带 BOM**（无 BOM 的 PS 5.1 会把中文读成乱码）；临时粘命令不受此限。
★这一段**只放在任务书第 0 步与丙档模板 §0**，不进工单卡片的「开窗指令」——
  卡片那三行是给设计者贴窗用的，重复一遍任务书里已有的东西只会把卡堆长（设计者 2026-09-14 当窗定）。

取配置的顺序写死为四级，前面取到就不再往下找：① 环境变量 `TICKET_REMOTE` / `TICKET_TOKEN_FILE` / `TICKET_CA_SHA256`
→ ② `TICKET_ENV` 指向的配置文件 → ③ 仓根推算的 `tasks/tickets/remote.env` → ④ 都没有才是本机模式，
并在 stderr 打一行「本机模式(未接通道):本机库 …」。任意位置加 `--local` 强制本机模式、忽略前三级，
测试与离线自查用它。配置找到了但用不了（缺 `TICKET_TOKEN_FILE`、令牌文件不存在……）会直接拦下并说清缺哪一样，
不会悄悄退回本机；`remote.env` 里路径一律写正斜杠。

本机模式下找不到某单，回话是两句：`本机模式(未接通道):本机库 <路径> 里没有 T-xxx。` 与
`如果这张单在服务器上,先接通道:<最短接法>。`；远程模式下则说 `服务器 <host> 上没有这张单 T-xxx。`

跑 `tools/tickets/tests` 前请确认 shell 里没有 `TICKET_REMOTE`：测试子进程只用干净环境加 `--local`，
但守门用例发现测试进程自己带着 `TICKET_REMOTE` 会直接报红，提示 `unset` 之后再跑。

`test_cli_and_http_write_same_ticket_without_overwrite` 守住 CLI 附图与 HTTP 阻塞写同一张单时，状态、图片和事件序号都不被覆盖。
它历史上被报过「全量首跑 CLI 偶发退出码 2」（退 2 = `ticket.py` 把 `TicketError` 或 `OSError` 兜住后的统一出口）。
后来在当时的基点上没能复现：单用例 100 次、全量 20 次（共 4860 条）、同场景高频探针 600 次，红 0 次。
因此没有猜根因，也没有动 `store.py` 的写路径。已做的只有两件让下一次真失败能自证的事：
失败断言带出 `cli.stderr`，`run_local_cli` 加 `errors="replace"` 保证 stderr 不会因解码失败整条丢掉。

同时量到一个要留档的事实：栅栏放行后 HTTP 那一支中位 30 毫秒就写完了，CLI 那一支光启动 Python 子进程最少也要 204 毫秒。
两次写在正常机器上并不重叠——这条用例名义上并发、实际接近串行，它能守住「不覆盖」的结论，但守不住真正的写竞态。
要拿它当并发闸，得先让两边在同一时刻真的撞上（例如让子进程先起好再握手），那是另一张单的事。

## 远程模式怎么确认自己连的是服务器

远程模式靠三个环境变量：`TICKET_REMOTE`（服务器地址）、`TICKET_TOKEN_FILE`（令牌文件路径）、
`TICKET_CA_SHA256`（证书指纹，可选）。令牌只放文件里，永不进 git、日志、工单和聊天。

**开工第一件事：先跑一次 receipt 核通道。**

```powershell
python tools/tickets/ticket.py receipt T-000001
```

拿一个你确定服务器上有的单号去 receipt。能打出这张单的标题和状态，说明你这一条命令
确实是打到服务器上的；打不出来就别往下做，先把通道修好。

**这张单是「返工」态时，`receipt` 还会把上一轮为什么被退一并打出来**：返工次数、
判卷人、**判语全文**（首行就是判卷要求写明的责任归属，「模型责任」还是「出题责任」一眼可见）、
以及最近一条返工原因。开窗指令只有三行、只带任务书路径，判语从前只留在卡片上，新窗根本看不见——
曾有一张单就是这么空转两轮的：判语要求「补四条守门用例」，新窗照着旧任务书又交了一模一样的板。
其余状态一个字都不加：`receipt` 是每次开工都要跑的，把它堆成一堵墙就没人读了。
判语文本只在服务端 `TicketService.receipt` 一处生成，网页与 CLI 消费的是同一份，前端不另拼。

不核通道会出什么事：远程不可达时读命令曾经只在 stderr 打一行提示、照常打印本机旧数据、
退出码还是 0。总监位据此把本机快照当成服务器数据，误判 staff list 全项目崩，开了一张
假警报工单。现在这条路已经堵上：

- 远程不可达时，读命令**默认直接报错退出，退出码 3**，明说远程不可达、失败原因和本机快照时间；
- 确实要看本机旧快照，得显式加 `TICKET_ALLOW_STALE=1`，**给了也仍然退 3**，
  且提示会在数据前后各出现一次，stdout 与 stderr 都有；
- 写操作在远程不可达时一律硬报错，永不落回本机，防止数据分叉。

所以：**退出码 3 = 你看到的不是服务器上的数据**，不要据此判断、建单或报障。

## 协议版本、探测与安全降级

客户端与服务端会在每次 `/api/cli` 往返里交换一个整数协议版本：`0` 是没有版本握手的旧版，
`1` 是认识 `--taskbook-client-checked` 的版本，`2` 是加入握手、版本回显和安全降级后的版本。
`receipt` 会在回执末尾同时显示客户端与服务端协议；两者不同时，还会明确提醒新开关可能被降级或拦下。

普通 `env` 永远不出网、不碰工单库，也不读取令牌内容，只显示客户端协议，并提示用 `--probe` 才查服务端。
只有显式执行 `python tools/tickets/ticket.py env --probe` 时才会发起一次探测；探测失败只显示
`服务端版本没查到:<原因>`，不改变 `env` 原有的成功退出规则。

`DEGRADABLE_OPTIONS` 是安全降级白名单，只能放“省掉后不改变工单内容”的优化开关。
`--deliverable`、`--internal`、`--tier` 等会改变工单内容或验收规则的开关绝不能放进去，否则省略它们等于写错单。
目前白名单只有 `--taskbook-client-checked`：协议较旧的服务端不认识它时，客户端会省掉该开关并且只重发一次。
工单仍能建或改，但“任务书校验”会是“待回核”，不会进入设计者队列；等平台位上服后，重跑
`set <工单号> --taskbook <同一个路径> --by <所属总监位>` 即可回核。

交板（`submit`）在远程模式下还有一层：交付项写的是你这台机器上的路径，
服务器上没有 `D:` 这个盘，所以「文件存不存在」由**你本机**逐个核，核齐了才发请求，
核验结论记进工单的「接线证据·文字」里，形如 `交付项本机核验:6/6 齐`。
少一个就在本机报错，请求根本不会发出去。图片类交付项（工单 `img/` 里的）仍由服务端核。

## 上服：三道前置闸和一道后置闸

这一节属于扩展 `server_deploy`：上服脚本（`install.sh` / `update.sh` / `pack.sh` / `backup.sh`）都在 `core/extensions/server_deploy/` 下，脚本直接跑，不用在配置里启用。

`extensions/server_deploy/update.sh` 在替换线上代码之前先跑三道闸，**任一不过就退出 2，一个字节都不动线上**；每道闸打一行 `前置闸 ① PIL … 过/拦`，三道全过才打 `三闸全过,开始替换。`

| 闸 | 探什么 | 不过时 | 跳过开关 |
| --- | --- | --- | --- |
| ① PIL | 当前用户与服务账号（`sudo -n -u $SERVICE_USER`）各 `from PIL import Image, ImageOps` 一次 | 退 2，并提示系统 python 受 PEP 668 管控，用 `apt install python3-pil`，不要 `pip` | 无 |
| ② pytest | 在 `--source` 里跑 `python3 -m pytest tools/tickets/tests -q -rs -p no:cacheprovider`（包里有 `extensions` 时连它一起跑） | 退 2，打出 pytest 的**真退出码**和最后 30 行；跳过超过 15 条也退 2 并列出清单 | `--skip-tests` |
| ③ node | `node --check <SOURCE>/tools/browser/tickets.js` | 退 2，打出语法错误 | `--skip-node-check` |

- 闸 ① 探的是**服务端运行环境**，不是源码里有没有那几个字。2026-09-05 图片压缩挪到服务端后上服，线上 python 没装 Pillow，16 张带图的 `live` 全被拦——当时的探针只 grep 源码特征字符串，一条都没探过运行环境。
- 闸 ② 的退出码是 pytest 自己的：输出重定向进临时文件，`TEST_RC=$?` 直接接在那条命令后面，**全程不建管道**。`| tail -1` 之所以能把红吞成绿，是因为管道的退出码默认只取最后一节，`tail` 永远是 0，pytest 的非零码在那一步就丢了（有一次还被 `echo` 抢走了 `PIPESTATUS`）。脚本开头的 `set -euo pipefail` 已含 pipefail，但那只是第二重保险。
- 服务器没装 pytest 或 node 时**明确报错退出，不静默跳过**，并指出对应的跳过开关；要跳必须是人明写的。
- **闸 ② 跑的是上服包树，不是完整仓树**：`--source` 指向的包（`pack.sh` 打的）里只有 `tools/tickets`、`tools/browser`、`extensions`、`desk_config.json` 四样，读包外文件的用例在那里没有前提。这类用例统一走 `repository_file_or_skip()`——**包树里干净跳过并写清人话理由，仓树上照常真跑**。目前只有一类：读 `review/ticket-system/MOVE-VERIFY.md` 对照表的那条，加上守着它的 `PackageTreeGateTests`，包树里共跳 2 条。
  - 跳过不是免检：`PackageTreeGateTests` 两条一起钉——一条钉「包树里是 skipped 不是 failed」，另一条反过来钉「仓树上是真跑了」。把跳过条件改成永远跳过，第二条立刻红。
  - 闸 ② 自己还有一道**跳过上限**（`MAX_SKIPPED`，默认 15）：跳过条数超过上限就当作没跑，照拦处理并打出 `SKIPPED` 清单。否则「跳过」会变成下一个静默漏洞——今天这个坑正是「闸看起来在，其实从没真跑过」。
  - 闸 ② 用 `-p no:cacheprovider`，**不在包目录里落 `.pytest_cache`**。用 `sudo` 跑过一次后包里会留下 root 属主的缓存，下一个普通账号写不进去，pytest 只打一条 `PytestCacheWarning` 就过去了，闸看着在跑其实已经半瞎。
- 闸 ① 会在 `sudo` 与服务账号都在时，用 `sudo -n -u $SERVICE_USER` 再 import 一次 Pillow。服务器上这两样都真在，开发机上通常都没有，**同一份脚本在两处走的是不同分支**。
- 后置闸：`systemctl restart` 之后用 `ss -ltn` 循环最多 10 秒等 `$DESK_PORT`（默认 8443）真在听，没听到退 3 并打 `journalctl` 最后 20 行。判据是端口，不是日志里的 `READY` 行——journal 是追加的，上一次的旧 `READY` 照样 grep 得到。
- 后置闸通过后脚本会尝试建一张上服记录单（`deploy-record`）。这个子命令在扩展 `deploy_record`（`core/extensions/deploy_record/`）里，默认不加载；服务端要在 `core/desk_config.json` 的「启用扩展」里写 `"deploy_record"` 才有。

不替换、只验闸用 `--check-only`：

```bash
sudo bash extensions/server_deploy/update.sh --source /srv/ticket-desk/checkout --check-only
sudo bash extensions/server_deploy/update.sh --source /srv/ticket-desk/checkout
```

`PYTHON_BIN` / `NODE_BIN` / `SERVICE_USER` / `SERVICE_NAME` / `INSTALL_ROOT` / `DESK_PORT` 可用环境变量覆盖；服务账号、服务名、安装根、端口默认 `ticket-desk` / `ticket-desk` / `/srv` / `8443`。

### 谁答哪张:「指派给」与 inbox 尾巴

需求/阻塞改由**所属总监位**自答之后,所以建单时「指派给」也落到那一位——从前一律落「总编排」,收件位按指派给扫**看不见本该自己答的单**,发的人以为没发出去(全台面待答 40 张里 22 张这么错位)。
· 拍板仍送设计者;总工单仍归总编排;疑问的跨位规则不变(跨位给收件位、自问给设计者);发给总编排的需求仍归总编排。
· `inbox` 跑完会在末尾自动追加一行 `★你位当前待答 N 张:T-xxxxxx / …`,一张都不欠时不打这一行。每位第 0 步都跑 inbox,这是全台面唯一保证会被执行的命令。
  ★数的判据是「**指派给** == 本位」而不是所属位:拍板单与非跨位疑问送的是设计者,发起位不欠它们(总编排第一轮判退时点出过真例)。
· `list --slot <位名> --pending-mine` 等价于「这一位还欠着没答的单」。
· 历史错位单回填:`migrate --backfill-assign` **默认只打清单不写**,看过清单再加 `--apply` 才动;判据是 类型∈{需求,阻塞} 且 状态=待答 且 所属位不是总编排 且 指派给=总编排。

### 内部单并线即到头

内部工具单(建单时标 `--internal`)一旦「已合并」就是**终态**:它没有玩家可见的产出,也就没有真登录图那一步。
工具从此不再让它老化,也不再把它算进「上服」那一格与设计者队列的「卡住了」段。
★玩家可感知单不适用——它们仍要 `live`（实机复验）过才算到头。
★判据在两处必须一致:服务端 `service.py is_terminal()`、前端 `tickets.js isTerminal()`,改一处必须两处一起改(有钉测守着)。

## 网页刷新为什么快了:压缩 + 增量

设计者 2026-09-08 报「刷新工单页至少多等十秒」。**先量后改**,量出来的结论与「数据太多算得慢」相反:

| | |
|---|---|
| 服务端取数 + 序列化 | **1.1 秒**,不是瓶颈 |
| 一次刷新下行 | **11.17 MB**(工单 7.48 MB / 1292 张 + 13 条对话线 3.59 MB / 5470 行) |
| 远端线路 | 波动极大,同一个 7.49 MB 的包实测 1.72 ~ 15.41 秒 |

两刀下去:**11.17 MB → 约 1 MB**(稳态)。

**① 响应 gzip**(`http_server._json`,唯一出口):中文 JSON 压到 32%。
只对主动发 `Accept-Encoding` 的客户端压——**命令行(`remote.py` 用 `http.client`)默认不发,一个字节不受影响**,有钉测守着。
阈值看**压之前**的正文长度,1 KB 以下不压。

**② 工单增量**(`GET /api/changes?since=<行号>`):稳态下这一趟只回**几十字节**,而整份是 2.45 MB(压后)。

书签用的是**服务端流水行号**,不是「最后更新时间」:
每写一次单必写一行流水,两件事在 `save_ticket` 的**同一把锁**里完成、行号严格递增——
一笔改动在物理上躲不过去;而时间戳会撞「同一秒两笔写入」的边界。

★**为什么不按「已关闭的不再读」缓存**(设计者提过这个想法,方向对、实现不该那么写):
查实过——进过「关闭」的 254 张里 **0 张**再离开过关闭态,所以那条规矩今天成立。
但它是靠**约定**成立的,不是靠机制:工具里没有任何东西拦着一张关闭单被改
(`rework` 就是判过之后还能退回)。而按行号做,关闭的单不变 ⇒ 永远不出现在增量里 ⇒ 自动不重传,
**同样的省流,少赌一件事**;哪天真有人重开了一张关闭单,它会自己回来。

**三道护栏**(缓存最坏的毛病是「安静地显示旧数据」):

1. **总数对不上就整份重取** —— 单确实会消失过:线上 `T-000001`~`008` 只剩流水、工单表里已经没有了(建台那天的演示数据被归档命令清掉的)。
2. **维护类操作带「整份重取」标** —— `migrate --backfill-state-time` 是唯一绕过 `save_ticket` 直接改盘的路,它故意不动业务时间;现在它会补写一行流水,否则那批改动对所有缓存着的页面**隐形**。
3. **顶栏【强制重取】** —— 任何缓存都该有一条一键回到干净状态的退路。

★**对话线故意不缓存**:它看着只追加,其实 `inbox --mark-read` 会回头改已有行的「已读标记」,
而那一格正是「要你去唤醒的窗口」的判据——按行数切片会让唤醒名单安静地变旧。
对话线是小的那一半,不值得为它冒这个险。要省它得另做一个「每位未读几条」的计数接口,让服务端每次现算。

★**增量的两条判据必须在 SQLite 后端也有用例**:线上跑的是 SQLite,不是文件后端。
第一版只测了文件后端,变异检验把 SQLite 那边的「坏书签整份回退」改坏了,八条用例**一条都没红**。

## 非业务闸不停车

设计者 2026-09-08 当面点的病:**近两日停过的窗几乎全是账面闸**——交付项写 `.jpg` 台面存 `.webp`、
目录型交付项、工作树路径 vs 主检出路径、任务书「待回核」、远端镜像滞后、本机 CLI 不认新参数。
**没有一件是活没做好**,而每一件都停掉了一整扇窗。

★**这不是把闸拆了,是把闸分成两种**:

| | 什么算 | 怎么处置 |
|---|---|---|
| **业务** | 真源缺、接口对不上、判据不达、测试红 | 照旧**停车**:`block --kind 业务`(默认),单子进「阻塞」等人解 |
| **非业务** | 交付项写法、路径前缀、待回核、远端滞后、CLI 版本 | **记一行继续做**:`block --kind 非业务`,**状态一个字不改**,员工不等答复 |

判据只有一句:**这条闸拦住的,是「活没做好」还是「字没写对」。** 字没写对的,不该停一整扇窗。

**① 交付项按写法归一**(`model.deliverable_key` / `resolve_under_root`,服务端与客户端共用一处):
后缀不同按去扩展名的编号比(`T-000001-01.jpg` ↔ 台面存的 `.webp`);目录型交付项用 `exists()` 不是 `is_file()`,目录算数;
工作树路径、主检出路径、仓相对路径三种写法一律折回仓相对再核,从整条往后逐段掐、取最长匹配。
★**只放行写法,不放行「活没做」**:文件真的不存在仍然照拦。

**② 员工可以改自己单交付项的写法**(不改语义):`set --deliverable` 对「指派给=本人」放行,
落一条 `worker-reshape-deliverable` 日志给判卷人看。语义由两条同时判定——
去扩展名的文件名相同 **且** 路径段互为后缀;换成另一个文件(`tools/tickets/service.py` → `别处/service.py`)
两条对不上,当场落回原来的署名闸。

**③ 任务书「待回核」不再挡设计者队列**:它的意思只是「建单那台机器当时核不到那个路径」,
路径本身写着、员工照常 claim 照常做。单子照常进「要你传达的」,卡片上挂一行黄字提醒补核;
`receipt` 也对员工说一句「不影响你开工」。★「没指派员工」那一条**仍然拦**——那是真的活没准备好。

**④ 非业务阻塞不改状态**:`block --kind 非业务` 只往单上追一条记录,状态留在原处。
于是它不进老化告警、不占设计者队列、不用等谁答复——这正是「员工不等」。
代价是没人主动看得见它,所以 `ticket.py list --nonbiz` 与日览里那个 `非业务 N` 是它**唯二**的出口,两处都不折叠。

**⑤ 版本差一律警告不拦**:服务端旧、本机 CLI 旧,都只在 stderr 打一行「不影响这次操作 / 命令已经生效 / 不要为此停车等谁」。

### 判过之后要退回重做:`rework`

`judge` 只吃「待判」,于是**判过之后**才发现要重做的单谁都翻不动——设计者曾当面否了某位一批画,
该位说「待复检态只有复检位能翻」,复检位手上也没有这个动作,最后只能 `close --not-merged` 一刀切成终态。
这与 `close --not-merged` 是同一个缺口的两半:那边「这活到此为止」(终态),这边「这活还要接着做、单号要留住」。

```bash
python tools/tickets/ticket.py rework T-xxxxxx --reason "设计者当面否了这一批的画" --by 复检
```

- **受理态只有「待复检」**;待判的仍走 `judge --rework`。不去放开 judge 的受理态——judge 是「判卷」那个动作,
  把待复检塞进去,「谁在什么时候判的」这条线就糊了。事件单独记 `rework-from-review`。
- **四个署名位都放行**:该单所属总监位、复检位、总编排位、设计者。当初那一张正是「本位翻不动、复检位也翻不动」卡住的。
- 落「返工」,**单号、任务书、断点全留住**,返工次数累计;「已开窗」戳记一并清掉,单子当场回到「要你传达的」。
- `--reason` 必填(同 `--not-merged`:没有原因的退回,事后与「判错了重判」分不清)。
- ★**`--blame` 默认「出题」不是「模型」**:触发这条边的典型情形就是任务书口径被否、执行方照做没错。
  默认记模型账等于凭空给执行方记一次判退,模型合格率就脏了。要记模型账必须显式写 `--blame 模型`。

### 到终态自动退役

单子进**终态**时,若执行方**不是固定工位**、手上又没有别的在办单,工具自动把他收窗,
并在事件线记一行 `staff-auto-retire`;命令行与网页的回执上当场多一句「名册已自动收窗:…」。
理由很实在:「窗关了顺手跑一次 `staff retire`」这件事,上线到今天一次都没人跑过,
名册里堆着一批早就不在的窗,总监照着派单下拉派过去,单子就那么停在「新建」。

* **这里的终态是** `关闭` / `作废` / `实机复验过` / **内部单**`已合并`。
* **★`阻塞` 不算**,它与 `is_terminal()` 的口径在这一点上**故意不同**:
  那一条问「还需不需要有人再动它」(阻塞单没人该动,所以不报老化);
  这一条问「执行方还要不要回来」——阻塞解开之后原员工还得接着做,而 `claim` 只认在岗,
  退了他就再也认领不回来。两条判据分别是 `is_terminal()` 与 `is_done_for_staff()`,**不许合并成一个**。
* **固定工位一律不退**:它跨窗复用,退了下一窗连 `claim` 都进不来。
* **「手上没有别的在办单」只数现在仍指派给他的单**:「经手工单号列表」是履历,
  单子被转走或改派之后不会从里面撤回;照履历数,凡被改派过一次的员工永远退不掉。
* **收窗是附加动作,不许弄挂主流程**:名册这一步出任何问题都只多一行提示,
  关闭 / 作废 / 实机复验 / 并线本身照常落库成功(与记忆件重刷同一条口径)。
* 收错了就 `staff reopen <员工名>` 拉回来;编号不复用,历史不删。

**名册默认只显示在岗**:`staff list` 与网页员工名册默认只列在岗,
命令行加 `--all`、网页点开「已收窗 N 位」才看全量。
退役编号**仍在册**——`history`、`memory export`、模型合格率一律读全量,
账按**模型**统计不按编号,一分不丢。

## 固定工位与工位记忆

窗是一次性的，**固定工位**却跨窗复用。没有记忆件，下一窗要么从零翻工单，要么把上一窗踩过的坑再踩一遍。这一节把这件事从「靠员工手写接管件」变成工具产出。

**三条命令**

```bash
# ① 名册记「固定工位」与记忆 md 路径。只有该员工所属的总监位或总编排能落笔。
python tools/tickets/ticket.py staff fix 后端-04 \
    --memory "<工作区>/_office/后端/工位记忆/后端-04.md" --by 后端
python tools/tickets/ticket.py staff unfix 后端-04 --by 后端   # 取消标记，路径保留便于回看

# ② 从这位**已交板**的单生成/重刷记忆 md。
python tools/tickets/ticket.py memory export --staff 后端-04 [--out <路径>] [--max-lines 400]

# ③ 交板留「给下一窗」；判卷人可以把写错的行划掉。
python tools/tickets/ticket.py submit T-xxxxxx --evidence … --handoff "这条链的真源在 X
Y 那个数是错的,别信"
python tools/tickets/ticket.py judge T-xxxxxx --pass --by <位名> --verdict … --strike-handoff "2"
```

**路径约定**：`<工作区>/_office/<位名>/工位记忆/<位名-编号>.md`。工具**不**替人建目录、也**不**校验文件必须已存在——记忆件是 `memory export` 生成的，先有标记才有第一次导出；`staff fix` 时父目录不在只提醒一句，不拦。`staff list` 会在固定工位后面打一个 `· 固定工位`。

**开窗指令自动插「先读记忆」**：`dispatch_instructions()` 仍是开窗三行的唯一生成处。指派给固定工位且记了路径时，第二行末尾接上一句 `…;开工前先读 <路径>(本工位的底数与坑,先核分支头与绿数再干活)。`；**非固定工位的单三行逐字不变**，有钉测守着。三行里仍然一个平台名都不许出现。

**骨架自动生成，自述只占一小节**：记忆件的正文由工具从「这位经手过、且**已交板**（状态到过待判及以后）」的单里生成，每一条都回指到某张单——单号、标题、状态、分支与提交号（从证据里取到什么写什么，取不到写「证据里没写」）、判语首行、交付项、被判退过几次的断点。每一节标着**是哪个模型写的**（取单上的「实际模型」，空则写「未标」）。员工能填的只有 `--handoff` 那一小节：只写底数与坑，不写流水账。非固定工位的单也能填 `--handoff`，只是没人导出。

**划掉不是删除**：`judge --strike-handoff "2,3"` 把写错的行标上「判卷人 · 时间」，**原文保留**，导出时以 `~~已划掉~~` 呈现。理由是「谁在什么时候认为它错了」本身就是下一窗要知道的事。行号越界会拒，并说明这一节共有几行。

**封顶与归档**：`--max-lines` 默认 400。超出时把**最旧**的条目**追加**（不覆盖）到同目录的 `<文件名>.archive.md`（`X.md` → `X.archive.md`），主文件顶部留一行「更早的 N 条已归档到 <路径>」。这是为了 300K 的员工窗装得下——记忆件无限长就等于没有记忆件。第 0 步那一段永远不被挪走。

**★记忆是快照，会过期**：生成物顶部**写死**一段「第 0 步（每次开窗必做，不许跳）」——先 `git fetch` 核主干分支头、在自己的工作树上跑一次全量拿**当下**的绿数，文件里的分支头、绿数、行号**只当线索不当事实**，对不上以现在跑出来的为准并在本单里报一行。真源是 `service.MEMORY_STEP_ZERO`，改它等于改掉这道提醒。

**自动重刷，且失败不许拖垮交板**：`submit` 与 `judge` 落库之后，若执行方是固定工位且记了路径，自动重跑一次导出，在返回文本里加一行 `记忆 md 重刷完成:<路径>`。**重刷失败一律吞掉**，只把 `记忆 md 重刷失败:<原因>` 记进返回文本——工具的附加动作不能反过来卡住员工交板。手工跑 `memory export` 则相反：那是人主动要的动作，失败照常报错。

远程模式下记忆件由**客户端**落盘（走 `memory data` 取原料，与 `export` 同一条路子）：记忆件在工作机的 `D:` 盘上，服务器上根本没有这个盘。客户端会把服务端那条必然失败的重刷行换成本机自己这一次的结果。

## 导出任务书

- 新工单一律进入数据根（默认仓内 `core/data/`）。导出到指定文件用 `python tools/tickets/ticket.py export T-xxxxxx --out "<目标目录>/任务书.md"`；远程模式下由客户端取得工单后在本机写文件，不依赖服务器上的 Windows 路径。
- 不写 `--out` 时默认落到 `_office/<所属总监位>/任务书/T-xxxxxx_<主题>.md`；标题里的 `< > : " / \\ | ? *` 与控制字符会替换为 `-`。旧参数 `--inbox codex|codely|dsh` 已废弃，使用时会明确报错并提示改用 `--out`。

数据根里的工单图片与 JSON 永不进入 Git（默认数据根 `core/data/` 已由 `core/.gitignore` 排除）。网页回落 bundle 是本机生成物，也由 `.gitignore` 排除。
